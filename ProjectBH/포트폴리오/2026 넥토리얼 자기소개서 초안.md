# 2026 넥토리얼 자기소개서 초안

> 작성 기준: Project BH와 Project OCH에서 문서와 코드로 확인되는 경험만 사용한다. 각 문항은 제한 글자 수보다 약간 짧게 작성해 최종 지원서에서 표현을 조정할 여지를 남긴다.

## 1. 지원 동기와 게임 프로그래머가 되기 위해 노력해 온 과정 (1,000자)

게임 프로그래머가 되고 싶은 이유는 머릿속의 규칙을 실제로 반응하는 세계로 만드는 과정이 즐겁기 때문입니다. 입력 하나가 애니메이션과 판정, 네트워크 동기화, 적의 의사결정까지 이어질 때 게임의 재미가 완성된다고 생각합니다. 넥토리얼은 클라이언트·서버·엔진을 아우르는 단일 공고에서 C++·C# 구현뿐 아니라 기존 코드 분석, 디버깅과 리팩터링, AI를 활용한 검증 과정까지 본다는 점이 인상적이었습니다. 제가 개인 프로젝트에서 쌓은 역량을 실제 프로젝트와 동료의 기준 안에서 검증하고 확장할 기회라고 판단해 지원했습니다.

이를 위해 서로 다른 문제를 가진 두 프로젝트를 직접 설계하고 구현했습니다. Project OCH에서는 Unity 클라이언트와 C++ IOCP 서버를 연결한 헥사 전술 전투를 만들었습니다. 클라이언트는 행동 의도만 보내고 서버가 소유권, 턴, 거리와 대상을 검증한 뒤 결과를 확정하도록 구성했으며, Protocol Buffers 코드 생성과 방 단위 JobQueue를 통해 통신 규격과 동시성 문제를 관리했습니다. 캐릭터가 늘며 전투 클래스가 비대해졌을 때는 상속 구조와 CSV 기반 효과 파이프라인으로 책임을 분리했습니다.

Project BH에서는 Unreal Engine 5와 C++로 3연속 근접 콤보, 타격 판정, 체력·피격·사망 흐름을 구현하고, 다수의 적이 플레이어를 포위하는 군중 AI를 개발했습니다. 단순히 기능을 붙이는 데 그치지 않고 재현 조건과 디버그 지표를 만들고, 원인을 상태와 책임의 범위로 좁힌 뒤 빌드와 플레이 테스트 항목을 기록하는 습관을 들였습니다. 넥토리얼에서는 이 집요함을 실제 팀의 코드와 피드백 속에서 확장해, 재미를 안정적인 시스템으로 완성하는 게임 프로그래머로 성장하겠습니다.

## 2. 프로젝트와 가장 어려웠던 문제 및 해결 결과 (1,000자)

Project BH는 Unreal Engine 5로 개발 중인 협동 액션 전투 프로젝트입니다. 저는 플레이어의 근접 전투와 다수 적의 추격·포위 시스템을 구현했습니다. 가장 어려웠던 문제는 적이 많아질수록 서로 밀고 막히며, 공격할 자리가 비어 있는데도 누구도 진입하지 못하는 교착이었습니다. Detour Crowd의 회피 설정만 조정해서는 현상이 잠시 줄 뿐 다른 지형에서 반복됐습니다.

먼저 문제를 감각적으로 판단하지 않기 위해 화면에 공격·대기 슬롯 수, 빈자리 지속 시간, 이동 단계와 경로를 표시했습니다. 재현 장면에서는 공격 슬롯이 0/4인데 대기 슬롯은 8/8이었고, 공격 자리가 9.7초 동안 비어 있었습니다. 동시에 한 적만 `CoreEscape`, 즉 전투 중심부 탈출 상태에 오래 머무는 것을 확인했습니다. 코드를 추적한 결과, 한 개체가 탈출 중이면 모든 적의 대기 슬롯→공격 슬롯 승격을 중단하는 전역 조건이 원인이었습니다. 개별 복구 상태가 전체 전열의 진행 조건으로 잘못 확대된 것입니다.

해결을 위해 `CoreEscape`를 해당 적만의 로컬 이동 상태로 축소하고 전역 승격 차단을 제거했습니다. 다른 적은 정상 승격하거나, 공격 자리가 0.25초 이상 비면 도착 조건을 완화한 보완 규칙으로 진입하게 했습니다. 또한 중간 탈출 경로를 진행 중인데 최종 슬롯과 가깝다는 이유로 도착 처리되던 문제를 막기 위해, 좌표뿐 아니라 현재 이동 단계까지 확인하도록 도착 조건을 고쳤습니다. 이후 공격 진입, 대기 진입, 양보 등 이동 역할과 우선순위도 분리해 좁은 길에서 같은 문제가 재발할 경로를 줄였습니다.

그 결과 한 적의 경로 복구 실패가 전체 공격 대형을 잠그던 구조를 제거했고, 교착을 단순 수치 조절이 아닌 상태 범위와 불변식의 문제로 해결할 수 있었습니다. 이 경험을 통해 복잡한 AI 문제일수록 관찰 가능한 지표를 먼저 만들고, 실패를 국소화하는 설계가 중요하다는 것을 배웠습니다.

## 3. 반대 의견이나 솔직한 피드백을 전했던 경험 (500자)

Project BH를 AI와 페어 프로그래밍 방식으로 개발하던 중, 충돌을 안전하게 피하기 위해 한 적이 `CoreEscape` 상태이면 전체 공격 슬롯 승격을 멈추자는 설계가 제안되었습니다. 저는 구현 의도에는 동의했지만 플레이 테스트에서 `A:0/4`, `W:8/8` 상태가 지속되는 근거를 제시하며, 한 개체의 예외가 전체 전투를 중단시키는 것은 받아들일 수 없다고 피드백했습니다. 단순히 “좋지 않다”고 말하는 대신 재현 위치, 화면 지표, 지켜야 할 조건을 문서로 공유하고 전역 조건을 로컬 복구로 바꾸는 대안을 제안했습니다. 수정 뒤에는 같은 기준으로 코드를 다시 검토했습니다. 이 경험을 통해 솔직한 피드백은 상대의 제안을 부정하는 일이 아니라, 관찰 사실과 공동 목표를 분리해 더 나은 판단 기준을 만드는 일임을 배웠습니다.

## 4. 자신 있게 활용할 수 있는 핵심 역량과 사례 (500자)

저의 핵심 역량은 복잡한 동작을 관측 가능한 상태로 나누고 C++로 구현·검증하는 능력입니다. Project OCH에서는 IOCP 네트워크와 방 단위 JobQueue를 구현하고 Unity C# 클라이언트와 Protocol Buffers로 연동해, 여러 요청이 들어와도 전투방의 상태 변경이 순서대로 처리되는 서버 권한 구조를 만들었습니다. Project BH에서는 Unreal C++로 근접 전투와 Detour Crowd 기반 포위 AI를 구현하며 디버그 지표로 교착 원인을 좁혔습니다. AI는 코드 작성자가 아닌 검토 가능한 협업 도구로 사용합니다. 제가 요구사항, 불변식, 변경 금지 범위를 정하고 AI가 낸 설계와 코드는 직접 diff·빌드·플레이 테스트로 검증합니다. 결정과 실패 원인은 Obsidian에 남겨 다음 판단의 근거로 재사용합니다.
