# Slot 간 연속 이동 구현

> 상태: C++ 구현과 `ProjectBHEditor Win64 Development` 빌드 완료. PIE 연속성 검증 대기. 정식 규칙은 [[몬스터 이동 시스템 규칙]]을 기준으로 한다.

## 증상

- Enemy가 Holding→Wait, Wait→Attack 또는 Initial 배치 확정 뒤 새 Slot으로 이동할 때 잠깐 정지했다가 다시 출발했다.
- 화면에서는 격자 타일 하나씩 이동하는 것처럼 `이동 → 정지 → 이동`이 반복됐다.

## 확인한 원인

### 강제 정지

- Pursuit에서 Formation으로 들어갈 때 Controller가 `StopMovement()`를 호출했다.
- Formation Revision 변경을 발견할 때도 기존 Move를 먼저 정지했다.

### Assignment 통지 지연

- Slot 승격과 재배정은 Player의 Slot Component에서 먼저 결정된다.
- Enemy Controller는 별도 통지가 없어 자기 정기 갱신 주기 `0.35~0.65초` 뒤에야 새 Slot을 확인했다.
- 그 사이 기존 경로가 이전 Slot에서 완료되면 Enemy가 멈춘 뒤 다음 Slot로 출발했다.

## 구현

### 속도 보존형 경로 교체

- Pursuit→Formation 전환에서 `StopMovement()`를 제거했다.
- Formation Revision 변경에서도 `StopMovement()`를 제거했다.
- 현재 Velocity를 유지하고 같은 갱신에서 새 목적지 Move 요청으로 교체한다.

### 다음 프레임 Assignment 알림

- Wait→Attack 승격
- Holding→Wait 승격
- Pending→Holding 배정
- Initial Formation 배정 완료
- 선택적 Formation Reform 완료

위 사건이 발생하면 Slot Component가 대상 Enemy Controller에 Assignment 변경을 알린다. Controller는 중복 알림을 한 번으로 합치고 다음 프레임에 새 Slot을 조회해 경로를 갱신한다.

다음 프레임으로 미루는 이유는 Slot Component가 예약 배열을 갱신하는 도중 Controller가 같은 배열을 다시 조회하는 재진입을 피하기 위해서다. 기존 최대 `0.65초` 지연은 한 프레임 지연으로 줄어든다.

## 유지한 정지 규칙

다음 상황에서는 실제 정지가 필요하므로 `StopMovement()`를 유지한다.

- 최종 Slot 도착 후 속도 `5 cm/s` 이하 정착
- 공격·회복 이동 잠금
- 경직·사망
- 타깃 소실 또는 유효 Slot 없음
- 경로 실패와 교착 복구

## PIE 확인

1. Holding→Wait 승격 시 기존 진행 속도가 0으로 떨어지지 않고 새 Wait Slot 방향으로 이어지는지 확인한다.
2. Wait→Attack 승격 시 Wait Slot에서 멈추지 않고 Attack Slot 방향으로 이어지는지 확인한다.
3. Enemy 위 `Speed`가 승격 순간 한 프레임 이상 `5` 이하로 떨어지지 않는지 확인한다.
4. 역할 색과 Slot 표기가 바뀐 다음 프레임에 경로 디버그 선도 새 목적지로 바뀌는지 확인한다.
5. 최종 Slot에서는 기존처럼 감속 후 정확히 정지하는지 확인한다.
6. 공격·경직·사망과 실패 복구의 필수 정지가 유지되는지 확인한다.

## 남은 구분

- Attack Slot이 가득 차 있어 Wait에서 실제로 대기한 뒤 빈자리가 생긴 경우에는 정지 후 재출발하는 것이 정상이다.
- 빈자리가 이미 있어 연속 승격되는 상황에서만 중간 Slot 정지가 없어야 한다.
- Initial Charge는 편성 확정 전 Combat Core 관통을 막기 위해 별도 `450 cm` 정지 반경을 사용한다. 이 연출까지 제거할지는 Initial Formation 규칙으로 따로 판단한다.
