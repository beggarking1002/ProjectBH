# 근접 공격 판정 방식 검토

> 상태: 결정 전. `BH Melee Trace` 소켓 Sweep 구현은 후보 중 하나이며, 이 문서의 선택이 끝날 때까지 Greystone Montage에 적용하지 않는다.

## 공통 전제

- 실제 피해와 명중 결과는 리슨 서버가 최종 결정한다.
- 클라이언트는 공격 입력과 애니메이션·이펙트 연출을 재생하지만, 자체적으로 피해를 확정하지 않는다.
- 첫 대상은 본체에 검+방패가 일체형인 Greystone이며, 검의 기준 본은 `sword`다.
- 한 공격 활성 구간에서 같은 대상은 한 번만 피해를 받는 것을 기본 규칙으로 한다.

## 후보 비교

| 방식 | 동작 | 장점 | 한계 | Greystone 적합성 |
| --- | --- | --- | --- | --- |
| 1. 캐릭터 전방 고정 Shape Trace | 공격 Notify 시 캐릭터 앞에 Sphere/Box/Capsule Sweep | 가장 빠르고 에셋 설정이 거의 없음 | 검 위치·방향과 무관해 사거리와 타격감이 부정확 | 임시 더미 검증용만 적합 |
| 2. 애니메이션 Notify 단발 Trace | 타격 프레임 한 번에 정해진 Shape Trace | 타격 타이밍을 애니메이션에 맞추기 쉽고 구현이 단순 | 빠르게 휘두르는 검의 경로와 다수 대상 처리가 거칠다 | 첫 공격 1타만 급히 검증할 때 가능 |
| 3. 활성 구간 Shape Overlap | 공격 구간에 Box/Capsule Collision을 켜고 Overlap 이벤트 처리 | 디버깅이 직관적이고 지속 접촉 표현이 쉽다 | 빠른 무기에서 놓침이 생길 수 있고 Collision 설정·복제 관리가 복잡 | 방패 밀치기·넓은 둔기에는 보조 후보 |
| 4. 물리 충돌 기반 | 검 메시의 Physics Collision 접촉으로 명중 판정 | 실제 접촉처럼 보이는 결과를 기대할 수 있다 | 물리 시뮬레이션, 프레임 차이, 네트워크 권한에서 결과 일관성이 낮다 | PvE 서버 권한 판정에는 비권장 |
| 5. 소켓/본 기반 연속 Sweep | Notify State 동안 검의 이전·현재 위치 사이를 매 Tick Sweep | 검 궤적과 잘 맞고, 일체형 무기도 본·소켓으로 사용 가능하며 서버 판정에 적합 | 칼날 끝 소켓과 공격 구간 설정이 필요 | **주력 후보** |
| 6. 데이터 기반 공격 호(arc) | 무기 위치 대신 공격별 거리·각도·부채꼴·캡슐 범위를 데이터로 판정 | 밸런싱과 예측 가능성이 뛰어나며 다양한 캐릭터 비율에 독립적 | 실제 검 모션과 어긋날 수 있고 공격별 데이터 작성이 필요 | 정식 데이터화 단계의 강한 후보 |
| 7. 하이브리드 | Notify State로 시간 창을 열고, 소켓 Sweep과 공격 데이터 범위를 함께 제한 | 시각적 정확성과 게임플레이 제어를 함께 확보 | 초기 구조가 가장 복잡 | 여러 무기·콤보 확장 후 권장 |

## 방식별 세부 설명

### 1. 캐릭터 전방 고정 Shape Trace

현재 과거 도끼 코드가 사용하던 방식이다. 캐릭터 위치에서 전방으로 일정 거리만큼 Sphere Sweep을 한 번 수행한다. 빠르게 기능을 확인할 수 있지만, 칼끝이 닿지 않아도 맞거나 칼끝이 닿았는데 빗나갈 수 있다.

### 2. 애니메이션 Notify 단발 Trace

공격 Montage의 특정 프레임에 Notify를 하나 두고, 그 순간에만 Sphere·Box·Capsule·Cone 계열 판정을 한다. 피해 시점은 명확하지만, 검이 이동한 전체 경로를 보장하지는 않는다.

### 3. 활성 구간 Shape Overlap

검 또는 손에 보이지 않는 Collision Component를 붙이고 공격 활성 구간에만 켠다. 지속적으로 닿는 표현에는 편하지만, Overlap은 빠른 이동에서 누락될 수 있어 무기 스윙의 주 판정으로는 보완 장치가 필요하다.

### 4. 물리 충돌 기반

검의 Physics Asset 또는 물리 시뮬레이션 충돌을 명중으로 사용한다. 물리 결과가 프레임·네트워크 상태에 영향을 받으므로, 서버와 클라이언트가 같은 결과를 봐야 하는 ProjectBH의 피해 판정에는 적합하지 않다.

### 5. 소켓/본 기반 연속 Sweep

`AnimNotifyState`가 켜진 동안 매 프레임 검의 이전 위치와 현재 위치를 Sphere 또는 Capsule로 Sweep한다. Greystone에서는 `sword` 본을 시작점으로, 칼날 끝 Mesh Socket을 끝점으로 쓴다. 칼날 길이를 여러 점으로 나눠 Sweep하면 넓은 스윙에서도 누락을 줄일 수 있다.

서버만 Trace하고, 타격한 액터 집합을 공격 창이 끝날 때까지 보관하면 다단히트를 막을 수 있다. 현재 C++의 `BH Melee Trace`는 이 후보의 초안이다.

### 6. 데이터 기반 공격 호

각 공격에 `거리`, `반경`, `각도`, `높이`, `전진량`, `활성 시간`을 데이터로 둔다. 예를 들어 "전방 130cm, 100도 부채꼴"처럼 설계자가 결과를 고정할 수 있다. 무기 메시 위치와 완전히 일치하지 않을 수 있지만, 네트워크와 밸런싱 측면에서 안정적이다.

### 7. 하이브리드

Notify State가 공격의 유효 시간을 정하고, 소켓 Sweep이 실제 칼날 경로를 찾은 뒤, 데이터 기반 거리·각도 조건으로 최종 유효 대상을 제한한다. 정식 전투 시스템에는 가장 유연하지만 첫 검증 단계에는 과할 수 있다.

## 판단 기준

| 기준 | 확인할 내용 |
| --- | --- |
| 시각적 일치 | 칼날이 닿지 않은 대상이 맞거나, 닿은 대상이 빠지는 빈도가 낮은가 |
| 서버 일관성 | 호스트와 클라이언트가 같은 피해·사망 결과를 보는가 |
| 에셋 비용 | 본·소켓·Montage 설정이 캐릭터마다 과도하게 늘지 않는가 |
| 밸런싱 | 무기별 사거리·범위·다단히트를 수치로 조절하기 쉬운가 |
| 확장성 | 도끼·창·단검·방패·엘리트 적에도 같은 구조를 적용할 수 있는가 |

## 현재 추천안

첫 Greystone 검+방패 수직 슬라이스는 **5. Notify State 기반 소켓/본 연속 Sweep**을 추천한다.

- 일체형 검에 별도 무기 액터나 물리 충돌을 요구하지 않는다.
- 애니메이션의 실제 타격 구간과 검의 위치를 함께 반영한다.
- 서버만 실행해 권한 원칙을 유지할 수 있다.
- `sword` 본이 이미 확인돼 있어, 칼끝 Socket 하나만 추가하면 시작할 수 있다.

단, 공격별 사거리·각도 밸런싱이 중요해지는 시점에는 6의 데이터 기반 공격 호를 결합한 7로 확장한다. 현재는 어느 방식도 확정하지 않았으며, 사용자의 선택 후 그 방식만 남기도록 C++를 정리한다.

## 선택 후 작업

- 1 또는 2 선택: 현재 `BH Melee Trace` 초안을 제거하거나 보류하고, 공격 Notify 기반 단발 판정으로 정리한다.
- 3 선택: Collision Component 활성화/비활성화와 서버 Overlap 처리를 구현한다.
- 4 선택: 권장하지 않으며, 채택 시 서버 물리 판정의 재현성 검증을 별도 수행한다.
- 5 선택: `SwordTraceTip` Socket, `BH Melee Trace` Notify State, 2인 PIE 피해 검증을 진행한다.
- 6 선택: 공격 정의 데이터 에셋과 서버 Shape 판정부터 만든다.
- 7 선택: 5를 안정화한 뒤 공격 정의 데이터 조건을 추가한다.
