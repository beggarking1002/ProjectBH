# 몬스터 이동 시스템 규칙

> 문서 상태: **현행 단일 기준 문서(SSOT)**  
> 최종 대조일: 2026-09-03
> 기준 코드: `ABHCrowdEnemyAIController`, `UCombatEngagementSlotComponent`, `ABHEnemy`  
> 이 문서는 사람이 읽는 현행 규칙의 단일 기준이다. 런타임의 실행 결과는 현행 C++이 결정한다. 문서와 코드가 충돌하면 임의로 하나를 정답 처리하지 말고 코드가 실제로 하는 동작을 불일치로 기록한 뒤 둘을 함께 정정한다. 과거 기획·작업 기록은 현행 판단 근거로 사용하지 않는다.

## 1. 문서 목적과 범위

이 문서는 ProjectBH의 몬스터가 **누구를 목표로 삼고, 어디로 이동하고, 다른 몬스터와 어떻게 공간을 나누며, 언제 멈추고 다시 움직이는지**를 하나의 규칙으로 정의한다.

다음 범위를 포함한다.

- 플레이어 탐색과 추적 대상 변경
- NavMesh 전역 경로 탐색
- Detour Crowd 근거리 회피
- Attack·Wait·Holding Slot과 Pending Queue
- 초기 포위 대형과 전투 중 승격
- Combat Core 회피와 Ring 진입 경로
- 플레이어 이동에 따른 목적지 갱신과 대형 재편
- 경로 실패와 교착 복구
- 공격·회복·경직·사망 중 이동 제어
- 이동 애니메이션과 Root Motion 원칙
- 디버그 표시와 검증 조건
- 시체 누적형 Enemy Pool과 아직 구현하지 않은 벽면 Traversal
- 검토 후 폐기하거나 보류한 방식

공격 판정의 크기·피해·가드·패리 같은 전투 판정 자체는 이 문서의 범위가 아니다. 단, 공격 때문에 이동이 정지하거나 슬롯이 유지·반납되는 규칙은 포함한다.

## 2. 상태 표기

| 표기 | 의미 |

## 3. 시스템의 기본 원칙

### 3.1 이동 책임의 계층

몬스터 이동은 세 계층이 역할을 나눠 가진다.

```text
NavMesh
  정적 지형에서 목적지까지 갈 수 있는 전역 경로를 계산한다.

Detour Crowd
  같은 NavMesh 위에서 이동하는 Agent끼리 근거리 속도와 회피 방향을 조정한다.

Combat Engagement Slot
  각 몬스터가 플레이어 주변의 어느 자리로 가야 하는지 결정하고 예약한다.
```

- NavMesh는 벽·통로·바닥을 고려하지만 다른 몬스터의 현재 Capsule을 영구 장애물로 삼아 대형을 설계하지 않는다.
- Detour Crowd는 주변 Agent를 피하는 **로컬 조향**을 담당한다. 닫힌 병목이나 잘못 설계된 목적지 배열 자체를 해결하지는 못한다.
- Slot 시스템은 몬스터가 플레이어 본체로 한꺼번에 달려들지 않도록 **전투 자리와 진입 순서**를 통제한다.
- 현재 일반 지상 이동은 이 세 계층을 함께 사용한다. ProjectBH가 직접 구현하는 차별화 영역은 Slot·대기열·승격·진입 경로·교착 복구다.

### 3.2 서버 권한

**현행**

- 타깃 선정, 슬롯 예약, 승격, 이동 요청, 공격 개시, 경직, 사망과 슬롯 반납은 서버가 결정한다.
- AI Controller의 주기 갱신도 서버에서 실행한다.
- 클라이언트는 복제된 위치·전투 상태·Montage 결과를 표현한다.
- 동일 몬스터를 여러 클라이언트가 서로 다른 슬롯에 있다고 판단해서는 안 된다.

### 3.3 수평면 기준

**현행**

- 타깃 거리, 슬롯 거리, Ring 반경, Combat Core 교차, Reform 이동량과 간격 진단의 핵심 계산은 XY 평면의 2D 거리를 사용한다.
- 각 슬롯의 최종 Z는 NavMesh 투영 결과를 사용한다.
- 따라서 완전히 다른 층이 XY상 겹치는 다층 전투장은 현재 구조의 취약 지점이다.

## 4. 구성 요소와 책임

### 4.1 `ABHCrowdEnemyAIController`

- 가장 가까운 유효 플레이어를 찾는다.
- Detour Crowd 설정을 적용한다.
- 전투권 밖에서는 Slot 없이 플레이어의 이동을 예측해 직접 추격한다.
- 전투권 안에서만 대상 플레이어의 Slot Component에 예약을 요청한다.
- Pursuit·Attack Ingress·Wait·Holding별 속도와 바라보는 방향을 적용한다.
- 예약된 위치까지 단계별 `MoveToLocation`을 요청한다.
- 도착, 공격 거리 불일치, 이동 실패와 교착을 판정한다.
- 타깃 변경·경직·사망 등 외부 사건에 맞춰 슬롯을 반납한다.

### 4.2 `UCombatEngagementSlotComponent`

- 각 플레이어가 하나씩 소유한다.
- Attack·Wait·Holding Ring과 Pending Queue를 관리한다.
- 슬롯의 월드 위치를 계산하고 NavMesh에 투영한다.
- 초기 대형, 런타임 승격과 교착 시 Attack↔Wait 교대를 중앙에서 결정한다.
- Wait·Holding·Pending은 플레이어에게 바로 붙지 않는 Engagement Anchor를 중심으로 배치한다.
- 0.1초마다 예약 정리와 승격을 처리한다.

컴포넌트는 예약 상태의 **소유자이자 오케스트레이터**다. 측정값 분류, Large Enemy 우선권 계산, 공용 경로 판정처럼 Actor 상태를 직접 바꾸지 않아도 되는 정책은 아래의 무상태 협력 객체에 위임한다.

#### 4.2.1 `FBHCombatSpaceClassificationPolicy`

- 공간 프로브가 측정한 폭·종횡비·개방각을 OPEN·POCKET·CORRIDOR 후보로 분류한다.
- 진입·이탈 임계값과 전환 대기시간을 한곳에서 적용한다.
- 슬롯이나 Actor를 직접 변경하지 않고 분류 결과만 반환한다.

#### 4.2.2 `FBHLargeEnemyEngagementPolicy`

- Large Enemy의 부채꼴 점유 공간을 계산한다.
- Large Enemy가 반드시 Attack Slot을 얻기 위해 어떤 일반 Enemy가 양보해야 하는지 계획한다.
- 실제 예약 배열 변경과 Enemy 알림은 Slot Component가 계획을 받은 뒤 한 번에 적용한다.

#### 4.2.3 `FBHNavigationQuery`

- Controller와 Slot Component가 함께 사용하는 완전 경로 판정을 제공한다.
- 유효하지 않거나 부분적인 NavMesh 경로를 공통 기준으로 거부한다.
- 경로와 점 사이의 2D 거리 같은 공용 기하 계산을 제공한다.

### 4.3 `ABHEnemy`

- `Chasing`, `Attacking`, `Recovering`, `Staggered`, `Dead` 전투 상태를 관리한다.
- 공격 데이터와 기본 이동속도는 Enemy Data Asset에서 읽되, 실제 AI 이동 중에는 Controller의 상태별 속도를 적용한다.
- 공격 시작 시 이동을 잠그고 대상을 바라본다.
- 경직과 사망 시 이동을 중단하고 Controller에 슬롯 반납을 요청한다.

### 4.4 Enemy Data Asset과 Attack Definition

- Enemy Data Asset의 `MaxWalkSpeed = 300 cm/s`는 기본·복구값이다. AI 이동 중에는 Controller가 Pursuit `500`, Attack Ingress `450`, Wait `350`, Holding/Pending `320 cm/s`를 적용한다.
- `AttackStartRange`는 Attack Definition 행에 둔다. 현재 Guardian 시작값은 `150 cm`다.
- Slot 반경이나 공격 거리 값을 바꿀 때는 둘을 독립적으로 보지 말고 실제 NavMesh 투영 위치가 공격 개시 범위 안에 들어오는지 함께 검증한다.

### 4.5 Enemy AnimInstance

- `GroundSpeed`: 실제 월드 Velocity의 수평 크기
- `Direction`: 캐릭터 전방을 0도로 한 이동 방향 각도
- `bShouldMove`: `GroundSpeed`의 진입·이탈 임계값을 분리한 Enemy 이동 상태
- `bHasAcceleration`: 공통 AnimInstance에서는 현재 가속 여부다. Enemy AnimInstance에서는 기존 ABP 연결을 보존하기 위해 현재 `bShouldMove`와 같은 값으로 제공한다.
- `CombatState`, `bIsStaggered`, `bIsDead`: 전투 상태 표현

AnimInstance는 목적지를 결정하지 않는다. 이동 결과를 애니메이션으로 표현한다.

### 4.6 `ABHEnemyPoolManager`

- 서버에서 고정 수의 Enemy Actor를 미리 생성한다.
- 살아 있는 Active Enemy, 월드에 남은 Corpse, 숨겨진 Free Reserve를 구분한다.
- 살아 있는 수를 Active Limit 이하로 유지하고 사망마다 지연된 교체 스폰 요청을 만든다.
- Free Reserve가 있으면 시체를 건드리지 않고 Free Enemy를 활성화한다.
- Free Reserve가 없을 때만 가장 오래된 eligible Corpse 한 구를 회수해 재사용한다.
- 명시적 Spawn Point를 순환 사용한다. 배열이 비면 현재 World의 TargetPoint를 자동 발견하며, 발견된 Point도 없을 때만 Manager 주변 fallback grid를 사용한다.

## 5. NavMesh와 Crowd 전제 조건

### 5.1 NavMesh 조건

**에디터 조건**

- 전투 가능한 모든 바닥과 이동 통로가 `NavMeshBoundsVolume` 안에 들어와야 한다.
- 바닥 Collision이 Navigation에 기여해야 한다.
- 에디터에서 `P` 키를 눌렀을 때 Enemy와 목표 Slot 사이에 연결된 녹색 NavMesh가 보여야 한다.
- Enemy Capsule이 지나갈 수 없는 폭의 통로는 NavMesh가 끊기거나 지나치게 좁게 생성될 수 있다.
- Slot이 NavMesh 밖으로 계산되더라도 투영에 성공할 때만 사용할 수 있다.

### 5.2 Slot NavMesh 투영

**현행**

- 모든 Slot과 Ring Waypoint는 사용 전에 NavMesh에 투영한다.
- 기본 투영 범위는 `X 50, Y 50, Z 200 cm`다.
- 투영에 실패한 Slot은 예약 후보가 될 수 없다.
- Ring Waypoint 투영에 실패해 유효한 이동 목표를 만들지 못하면 해당 예약을 무효로 처리한다.
- Reform 중 한 Ring의 새 Slot 위치를 전부 계산하지 못하면 그 Ring의 기존 예약을 성급하게 지우지 않는다.

### 5.3 Detour Crowd 설정

**현행 기본값**

| 항목 | 값 |
| --- | ---: |
| Obstacle Avoidance | On |
| Separation | On |
| Separation Weight | 2.0 |
| Avoidance Quality | High |
| Anticipate Turns | On |
| Collision Query Range | 500 cm |
| Avoidance Range Multiplier | 1.2 |

- Controller가 Enemy를 Possess할 때 `UCrowdFollowingComponent`에 위 값을 적용한다.
- Separation Weight가 너무 높으면 슬롯 도착 후 미세 진동이나 과도한 밀어내기가 발생할 수 있다.
- 미세 진동이 생기면 `2.0 → 1.5 → 1.0` 순으로 낮춰 비교한다.
- 성능 부담이 크면 Avoidance Quality를 `High → Good` 순으로 낮춰 비교한다.
- 너무 일찍 크게 우회하면 Avoidance Range Multiplier를 `1.2 → 1.0`으로 낮춰 비교한다.

### 5.4 RVO 규칙

**현행 원칙**

- Enemy Character Movement의 `Use RVOAvoidance`는 끈다.
- Detour Crowd와 Character Movement RVO를 동시에 사용하지 않는다.
- 두 회피 시스템을 함께 켜서 서로 다른 조향 결과가 경쟁하게 만들지 않는다.
- Epic의 UE 5.7 공식 가이드도 RVO와 Detour Crowd가 독립적으로 동작하므로 한 프로젝트에서 배타적으로 사용할 것을 안내한다.

### 5.5 Crowd Manager

**에디터 조건**

- `Project Settings → Engine → Crowd Manager`의 `Max Agents`는 동시에 활성화할 Enemy 수보다 여유 있게 둔다.
- 첫 검증값은 `32`다.
- `Max Agent Radius`는 가장 큰 Enemy Capsule 반지름 이상이어야 한다.
- Enemy별 Separation과 Avoidance Quality는 Crowd Manager가 아니라 AI Controller의 Crowd 설정에서 조절한다.

## 6. 타깃 선정 규칙

### 6.1 최초 타깃 획득

**현행**

- Controller가 Enemy를 Possess하면 즉시 타깃과 이동을 한 번 갱신한다.
- 이후 `Chasing` 상태에서 Controller마다 `0.35~0.65초`로 분산된 고정 주기로 다시 갱신한다. 최초 반복 시점도 서로 다르게 둔다.
- 유효한 Player Controller가 조종하는 `ABHHeroCharacter` 가운데 2D 거리가 가장 가까운 대상을 고른다.
- 타깃 획득과 바라보기는 분리한다. 포위 범위 밖 Pursuit에서는 이동 방향을 보고, Engagement Formation 상태에서는 모든 이동 단계에서 타깃을 본다.

현재 타깃 후보는 다음 조건을 모두 만족해야 한다.

- `IsValid`이며 Player Controller가 조종하는 `ABHHeroCharacter`다.
- 플레이어 위치를 기본 `X 100, Y 100, Z 250 cm` 범위로 NavMesh에 투영할 수 있다.
- Enemy 현재 위치에서 투영 위치까지 완전하고 비부분적인 Nav 경로가 있다.

현재 타깃이 도달 가능하면 기본 `2초` 동안 유지한다. 유지시간 뒤에도 다른 후보가 Enemy-Hero Actor 위치의 2D 직선거리 기준으로 현재 타깃보다 최소 `200 cm` 가까워야 교체한다. 현재 타깃이 무효이거나 도달 불가능해지면 유지시간을 무시하고 가장 가까운 도달 가능한 플레이어로 즉시 바꾼다. 타깃 유지시간은 선택 순간 0초로 초기화되며 디버그의 `Held`는 선택 후 경과시간이다.

아직 플레이어의 생존·다운·타게팅 불가 상태와 Line of Sight는 검사하지 않는다. 도달 가능성도 Combat Slot별 경로가 아니라 NavMesh에 투영한 플레이어 중심까지의 대표 경로로 판정한다.

### 6.2 타깃 변경

**현행 조건과 결과**

1. 새로 선택한 플레이어가 현재 타깃과 다르면 기존 슬롯을 반납한다.
2. 진행 중인 Move 요청과 경로 단계, 실패 슬롯 제외 상태를 정리한다.
3. 기존 Focus를 지우고 새 타깃을 저장한다.
4. 새 타깃의 Slot Component에 새 예약을 요청한다.

한 플레이어의 Slot을 점유한 채 다른 플레이어를 공격하지 않는다.

`Attacking`, `Recovering`, `Staggered`, `Dead`에서는 Controller가 타깃 탐색보다 먼저 이동 잠금으로 반환한다. 그러므로 공격·회복 중에는 주기적인 최근접 타깃 교체가 일어나지 않으며 기존 Focus와 공격 시작 시 고정한 `AttackTarget`을 유지한다.

### 6.3 타깃 소실

- `Chasing` 갱신에서 현재 타깃이 무효가 되면 슬롯과 중앙 대기 순번을 반납한다.
- 이동을 중지하고 Focus를 지운다.
- 다음 갱신에서 다시 유효한 플레이어를 찾는다.
- 공격·회복 중에는 타깃 재평가보다 이동 잠금이 먼저이므로 그 도중의 타깃 무효화는 현재 별도 처리하지 않는다.

## 7. Enemy 전투 상태와 이동 허용

| 상태 | AI 이동 | 슬롯 | 공격 |
| --- | --- | --- | --- |
| `Chasing` | 허용 | 요청·유지·승격 가능 | Attack Slot 도착 시 개시 가능 |
| `Attacking` | 정지 | Attack Slot 유지 | 진행 중 |
| `Recovering` | 정지 | Attack Slot 유지 | 재공격 금지 |
| `Staggered` | 정지 | 즉시 반납 | 취소 |
| `Dead` | 영구 정지 | 즉시 반납 | 불가 |

**현행 핵심 규칙**

- `Chasing` 이외의 상태는 모두 `IsAttackLocked()`에 걸리며 Controller가 이동을 중지한다.
- `Chasing` 안에서는 타깃 거리로 Pursuit와 Formation Participation을 다시 구분한다.
- 타깃 `700 cm` 밖에서는 Slot을 점유하지 않고 Pursuit하며, Formation 참여 뒤 `900 cm` 밖으로 이탈하면 Slot과 Queue를 반납하고 Pursuit로 돌아간다.
- 공격이나 회복이 끝났다고 Attack Slot을 자동 반납하지 않는다.
- 정상적인 전열 교대는 매 공격마다 일어나지 않는다.
- 경직·사망·경로 실패·타깃 변경·큰 위치 변화에 따른 Reform이 전열 변화의 주된 계기다.

## 8. 전투 자리 구조

### 8.1 기본 Ring 구성

**현행 기본값**

| 구역 | 개수 | 반경 | 각도 오프셋 | 역할 |
| --- | ---: | ---: | ---: | --- |
| Attack | 5 | 125 cm | 45° | 공격 권한을 가진 전열 |
| Wait | 8 | 250 cm | 22.5° | 다음 Attack 승격 후보 |
| Holding | 16 | 400 cm | 11.25° | Wait 바깥의 생존 대기열 |
| Pending | 제한 없음 | 575 cm부터 | 7.5° | Holding도 받지 못한 외곽 분산 대기 |

- 기본 예약 가능 자리는 총 29개다.
- 30번째 이후 Enemy는 Pending Queue 순번과 가상 Pending 위치를 받는다.
- Attack Ring은 플레이어 현재 위치를 중심으로 한다. Wait·Holding·Pending은 이동 중 플레이어를 최대 `175 cm` 뒤따르는 Engagement Anchor를 중심으로 한다.
- Anchor는 Dead Zone을 벗어나면 최대 `350 cm/s`로 플레이어를 따라간다. 플레이어가 `15 cm/s` 이하로 `0.35초` 정지하면 Anchor는 `200 cm/s`로 플레이어 중심에 복귀하고, `7.5 cm` 안에서 정확히 일치한다.
- 중앙 복귀 중 플레이어가 `40 cm/s` 이상으로 이동하면 지연 추종으로 즉시 복귀한다. 정지·재이동 임계값을 다르게 두어 미세한 속도 변화에 상태가 반복 전환되지 않게 한다.
- 모든 Ring은 월드 축 기준이라 플레이어 회전만으로 회전하지 않는다.
- 각 Ring의 오프셋을 엇갈리게 둬 인접 Ring의 Slot이 같은 방사선에 겹치는 경우를 줄인다.
- Slot 인덱스 `i`의 각도는 `AngleOffset + 360° × i / SlotCount`다.
- `0°`는 월드 `+X`, 양의 각도는 XY 평면에서 `+Y` 방향으로 증가한다.
- 거리나 경로 비용까지 같은 후보가 남으면 배열을 먼저 순회한 낮은 Slot 인덱스가 유지된다.

### 8.2 역할별 행동

#### Attack

- 슬롯에 도착한 Enemy만 공격을 시작할 수 있다.
- 공격과 회복 동안 자리를 유지한다.
- 전투 조건이 유지되면 같은 자리에서 다시 공격한다.

#### Wait

- 공격하지 않는다.
- 자신의 Wait Slot에 도착한 뒤에만 Attack 승격 후보가 될 수 있다.
- Attack Slot이 비어도 아직 도착하지 않았다면 승격하지 않는다.

#### Holding

- 공격하지 않는다.
- 빈 Wait가 생기면 Holding 도착 여부와 무관하게 Holding·Pending 전체 후보 중 해당 Wait까지의 경로 비용이 가장 낮은 Enemy가 Wait로 직행할 수 있다.

#### Pending

- Attack·Wait·Holding 예약은 없지만 Queue 순번에 따른 고유 외곽 목적지를 받는다.
- Open 상태의 첫 Pending Ring은 반경 `575 cm`, Ring당 `24개`, Ring 간격 `150 cm`, 각도 오프셋 `7.5°`다.
- Open 상태에서 24명을 초과하면 다음 `725 cm` Ring을 사용하고 같은 규칙으로 바깥 Ring을 계속 추가한다.
- Pending 순번은 현재 미예약 Queue 중 앞선 Sequence의 수로 계산하므로 앞선 Pending이 Holding으로 승격되면 나머지 목적지 인덱스가 앞으로 당겨질 수 있다.
- 목적지는 NavMesh에 투영되며 Controller는 일반 Slot과 마찬가지로 해당 위치까지 이동하고 정지한다.
- 중앙 대기 Sequence는 유지한다.
- Holding Slot이 비면 Pending 전체와 빈 Holding 조합 중 경로 비용이 가장 낮은 조합부터 배정한다.
- Pending 위치 투영이나 이동이 일시 실패하면 Sequence는 유지하지만 같은 순번에서 계산한 목적지를 다시 시도한다. Pending 전용 실패 위치 제외는 아직 없다.

## 9. 중앙 대기 순번

### 9.1 등록

**현행**

- Enemy가 처음 Slot을 요청할 때 증가하는 고유 Sequence를 받는다.
- 예약 종류가 Attack·Wait·Holding 사이에서 바뀌어도 같은 등록을 유지하는 동안 Sequence는 유지한다.
- Pending도 Sequence를 유지한다.
- Sequence는 Hero 한 명의 Slot Component 안에서 단조 증가하며 재사용하지 않는다. 타깃 Hero가 바뀌면 기존 Queue에서 제거되고 새 Hero의 Queue에서 새 Sequence를 받는다.

### 9.2 제거

- 타깃 변경, 타깃 소실, UnPossess, 경직과 사망에서는 Slot과 Queue 등록을 함께 제거한다.
- `ReservationInvalid`, 공격 거리·시작 실패, Move 요청 실패, Path Following 실패와 Watchdog 교착처럼 일시적인 이동 실패에서는 Slot만 반납하고 기존 Queue Sequence를 보존한다.
- 무효 Weak Reference는 Slot Component가 정리한다.
- Queue가 완전히 비면 다음 웨이브를 위해 초기 대형 단계로 돌아간다.

## 10. 초기 대형 편성

### 10.1 Initial 단계 진입

**현행**

- Queue가 비어 있다가 새 Enemy가 들어오기 시작하면 Initial 단계다.
- 마지막 신규 요청이 들어온 뒤 `0.5초` 동안 추가 등록을 기다린다.
- 이 기간에는 예약 계산을 위해 신규 Enemy를 임시 Wait/Holding에 등록하지만, Controller는 임시 Slot으로 가지 않고 플레이어 방향으로 `500 cm/s` 돌진한다.
- Initial Charge는 플레이어 약 `450 cm` 앞에서 멈춰 편성 확정 전에 Combat Core를 관통하지 않는다.
- 초기 Attack을 요청 도착 순서대로 즉시 확정하지 않는다.
- 임시 Wait 8개와 Holding 16개가 모두 차면 추가 Enemy는 Ring 예약 없이 Pending 위치를 사용한다.
- 신규 요청이 들어올 때마다 마지막 등록 시각이 갱신된다. `0.5초`보다 짧은 간격으로 Enemy가 계속 유입되면 Initial 종료도 계속 뒤로 밀리며, 현재 별도의 최대 Initial 대기시간은 없다.

### 10.2 Attack Admission

`0.5초`의 정착 시간이 끝나면 다음 순서로 초기 대형을 다시 만든다.

1. 임시 예약을 모두 해제한다.
2. 전체 요청 Enemy와 사용 가능한 Attack Slot의 모든 조합을 검사한다.
3. NavMesh에 투영된 Attack Slot이 Enemy의 공격 가능 거리 안에 있는지 검사한다.
4. Attack 재진입 가능 시간이 아직 오지 않은 Enemy는 제외한다.
5. Enemy에서 Slot까지 완전하고 비부분적인 Nav 경로가 존재하는 조합만 남긴다.
6. Nav 경로 길이에 경로 `110 cm` 이내 같은 층 Queue Agent 한 명당 `200 cm` 패널티를 더한다.
7. 경로와 혼잡 패널티의 합산 점수가 가장 낮은 Enemy-Slot 조합을 하나 선택한다.
8. 선택된 Enemy와 Slot을 후보에서 제거한다.
9. Attack Slot 5개가 차거나 유효 조합이 없어질 때까지 반복한다.
10. 합산 점수가 `1 cm` 이내로 같으면 Sequence가 빠른 Enemy를 우선한다. 같은 Enemy의 여러 Slot까지 Sequence와 점수도 같으면 낮은 Attack Slot 인덱스가 유지된다.

### 10.3 나머지 배치

- Attack을 받지 못한 Enemy는 빈 Wait까지의 경로 비용이 낮은 순서로 Wait를 채운다. 남은 Enemy는 빈 Holding까지의 경로 비용이 낮은 조합부터 Holding을 채우고, 나머지는 Pending이 된다.
- 합산 경로 비용이 `1 cm` 이내로 같을 때만 Sequence가 빠른 Enemy를 우선한다.
- 예를 들어 동시에 16마리가 등록되고 모든 Slot이 유효하면 `Attack 5 + Wait 8 + Holding 3`이 된다.
- 편성 완료 시 `FormationRevision`을 증가시킨다.
- Controller는 Revision 변경을 감지하면 임시 경로를 버리고 새 슬롯 기준으로 이동을 다시 요청한다.
- 이후 Runtime 단계로 전환한다.

## 11. Runtime 신규 진입 규칙

**현행 공간 우선 진입 규칙**

- 신규 Enemy의 첫 요청에서는 이미 외곽에서 기다리는 Enemy를 건너뛰어 Attack을 직접 받지 않는다.
- 유효한 Wait와 Holding 예약자가 모두 없을 때만 신규 Enemy의 Attack 직접 배정을 허용한다.
- Holding 예약자가 없을 때만 첫 요청에서 Wait 직접 배정을 허용하고, 그 외에는 Holding을 먼저 요청한다.
- Holding까지 가득 찼으면 Pending이 된다.
- 이후 빈 Wait 보충에서는 Holding·Pending의 등록 시점보다 실제 Wait까지의 경로 비용을 우선한다. 뒤늦게 온 Enemy라도 현저히 가까운 빈자리가 있으면 Wait로 직행할 수 있으며, Sequence는 경로 비용 동점에만 사용한다.

첫 요청의 무제한 Attack 새치기는 막되, 외곽 계층에서는 오래된 순번 때문에 가까운 Enemy가 파란 Holding을 찍고 멈추는 현상보다 빠른 대형 완성을 우선한다.

## 12. Runtime 승격 규칙

Slot Component는 기본 `0.1초`마다 아래 순서로 가능한 승격을 반복한다.

```text
1. Wait → Attack
2. Holding/Pending → Wait 직접 배정
3. Pending → Holding
```

안쪽 자리를 먼저 채운 다음 그 결과로 빈 바깥 자리를 채운다.

### 12.1 Wait → Attack

후보가 되려면 다음 조건을 모두 만족해야 한다.

- 빈 Attack Slot이 있다.
- 현재 Wait 예약을 가지고 있다.
- 자신의 Wait Slot에서 `60 cm` 이내에 도착했다.
- Attack 재진입 쿨다운이 끝났다.
- 대상 Attack Slot이 해당 Enemy의 공격 개시 거리 안에 있다.
- 현재 위치에서 Attack Slot까지 완전하고 비부분적인 Nav 경로가 있다.

정상 승격은 위 조건을 그대로 사용한다. 다만 활성 Attack Slot이 `0.25초` 이상 비어 있으면 빈자리 fallback을 한 번 더 검사한다. 이 검사에서는 `자신의 Wait Slot에서 60 cm 이내` 조건만 면제한다. Attack 재진입 쿨다운, 공격 개시 거리, 완전한 Nav 경로 조건은 계속 적용한다. `CoreEscape`는 해당 Requester의 로컬 이동 상태이며 다른 Wait Requester의 정상 승격과 fallback을 중단하지 않는다.

Pocket과 Corridor에서 공간 분석으로 비활성화된 Attack Slot 인덱스는 승격 후보, 초기 배정, 디버그 표시와 활성 수 집계에서 제외한다. 따라서 화면에 그려진 초록색 Attack Slot은 실제로 점유 가능한 활성 빈자리만 뜻한다.

선정 규칙은 다음과 같다.

1. 모든 유효한 Wait Enemy-Attack Slot 조합의 완전한 Nav 경로를 구한다.
2. 경로 `110 cm` 이내 같은 층 Queue Agent 한 명당 `200 cm`를 더한 합산 점수가 가장 낮은 조합을 고른다.
3. 합산 점수가 `1 cm` 이내로 같으면 Sequence가 빠른 Enemy를 고른다. Sequence까지 같으면 먼저 순회한 낮은 Slot 인덱스 조합이 유지된다.
4. 승격된 Enemy는 기존 Wait 예약을 해제하고 Attack Slot을 예약한다.
5. Slot Manager는 승격된 Enemy Controller에 Assignment 변경을 알린다.
6. Controller는 정기 갱신 주기 `0.35~0.65초`를 기다리지 않고 다음 프레임에 새 Slot 경로를 요청한다.
7. 기존 Velocity는 유지하며, 승격 자체로 `StopMovement()`를 호출하지 않는다.
8. Controller는 경로 단계를 초기화하고 새 목적지로 이동한다.

혼잡 Agent는 Requester 자신을 제외한 해당 Hero의 전체 Queue Enemy다. Agent 중심과 Nav 경로 각 선분의 2D 거리를 검사하며, 한 Agent가 여러 선분의 반경 안에 있어도 한 번만 센다. 두 Enemy 캡슐 반높이 중 큰 값보다 Z 차이가 크면 다른 층으로 제외한다.

### 12.2 Holding/Pending → Wait 직접 배정

- 빈 Wait Slot이 있으면 Holding과 Pending을 하나의 외곽 후보군으로 검사한다.
- 후보의 현재 위치에서 빈 Wait까지 완전한 Nav 경로를 구하고, 혼잡 패널티를 포함한 경로 비용이 가장 낮은 Enemy-Slot 조합을 선택한다.
- 기존 Holding Slot 도착 여부는 요구하지 않는다. 따라서 Holding으로 이동 중이던 Enemy가 파란 Slot에 정차했다가 다시 출발하지 않고 Wait로 바로 방향을 바꾼다.
- Corridor에서는 Enemy의 현재 Side와 Wait Slot Side가 같아야 한다.
- 경로 비용이 `1 cm` 이내로 같으면 Queue Sequence가 빠른 Enemy를 선택한다.
- 기존 Holding 예약자는 Holding을 반납하고 Wait를 받는다. Pending은 바로 Wait를 받는다.

### 12.3 Pending → Holding

- 빈 Holding Slot이 있을 때만 실행한다.
- 모든 Pending Enemy와 빈 Holding Slot 조합의 완전한 Nav 경로와 혼잡 비용을 비교한다.
- 경로 비용이 가장 낮은 조합을 먼저 예약한다. `1 cm` 이내 동점일 때만 Sequence를 사용한다.
- Corridor에서는 같은 Side 조합만 허용한다.

## 13. Slot 후보 선정 규칙

### 13.1 공통 유효 조건

Slot은 다음 조건을 모두 만족해야 후보가 된다.

- 해당 인덱스가 비어 있다.
- NavMesh 투영에 성공한다.
- 해당 Enemy가 일시적으로 제외한 실패 Slot이 아니다.
- Attack Slot이면 플레이어로부터의 실제 투영 거리가 공격 가능 기준 안에 있다.

### 13.2 우선순위

**현행**

1. 현재 Enemy 위치에서 Slot까지의 2D 선분이 Combat Core를 가로지르지 않는 후보를 우선한다.
2. 같은 분류 안에서는 현재 위치와 2D 거리가 가까운 Slot을 우선한다.

이는 플레이어를 관통하는 직선 이동을 덜 선택하게 하는 1차 규칙이다. 최종 이동 경로는 별도의 Ring 경유 규칙으로 다시 계산한다.

### 13.3 Attack Slot 안전 거리

**현행 통일 기준**

- 모든 Attack 직접 예약, Initial Admission, Wait→Attack 승격과 교착 교대는 하나의 계산 함수를 사용한다.
- 최대 Slot 중심 거리는 `AttackStartRange - 해당 Enemy Controller의 SlotAcceptanceRadius`다.
- 기본값은 `150 - 20 = 130 cm`다.
- 판정 거리는 플레이어 Actor 위치와 NavMesh 투영이 끝난 Slot 위치의 2D 거리이며 경계값을 포함한다.
- 계산 결과가 음수면 `0 cm`로 제한한다. Controller를 찾지 못하면 도착 허용오차는 `20 cm`를 사용한다.
- 기본 Attack Ring `125 cm`는 안전 최대 거리 `130 cm`보다 `5 cm` 안쪽에 둔다. NavMesh 투영과 부동소수점 오차가 있어도 네 Attack Slot이 경계값 때문에 탈락하지 않게 하기 위한 여유다.
- 공격 개시 순간의 최종 검사는 Enemy Actor 중심과 타깃 Actor 중심 사이의 2D 거리를 전체 `AttackStartRange`와 비교한다.
- Slot 중심에 안전 여유 `20 cm`를 미리 빼므로 허용오차 바깥쪽에서 멈춰도 기본 공격 거리 `150 cm`를 넘지 않는 것을 목표로 한다.

## 14. Combat Core

### 14.1 목적

Combat Core는 Enemy가 반대편 Slot으로 가면서 플레이어 Capsule을 가로질러 멈추는 상황을 줄이기 위한 수평 원형 금지 구역이다.

### 14.2 기본값과 유효 반경

- 설정 기본값은 `100 cm`다.
- 실제 계산 반경은 `CombatCoreRadius`와 `AttackRingRadius - 5 cm` 가운데 작은 값이다.
- 따라서 Combat Core가 Attack Slot 자체를 도달 불가능하게 만들지 않도록 제한한다.

### 14.3 교차 판정

- 현재 Enemy 위치에서 목표점까지의 2D 선분과 플레이어 중심 원의 최근접점을 계산한다.
- 최근접점이 유효 Combat Core 안에 들어오면 직행이 안전하지 않다고 판정한다.
- 직행이 안전하지 않으면 Wait 또는 Holding Ring을 이용한 우회 Waypoint를 만든다.

### 14.4 Core 내부 침입 복구

**현행 C++ 구현, 급반전 PIE 검증 필요**

- Player의 급격한 방향 전환으로 Enemy 중심과 Player Actor 중심의 2D 거리가 유효 Combat Core 반경 미만이면 일반 Slot 경로보다 `CoreEscape`를 우선한다. 기본 진입 반경은 `min(Combat Core 100, Attack Ring 125 - 5) = 100 cm`다.
- 탈출 완료도 같은 두 Actor 중심의 2D 거리로 판정하며 기본 종료 반경은 Player 중심에서 `200 cm`다. Attack Ring `125 cm`와 Enemy 보수 반경 `45 cm`보다 바깥이므로 Attack 점유자 뒤까지 빠져나가는 것을 목표로 한다.
- 현재 방사 방향을 기준으로 Player 주위 `16방향`의 탈출 후보를 검사한다.
- 후보는 NavMesh 투영 오차 `35 cm` 이하, 주변 `45 cm` NavMesh 여유와 완전한 비Partial 경로를 만족해야 한다.
- 현재 Attack Slot 점유자와 탈출 선분 사이의 거리가 `105 cm` 미만인 수를 세고, 가로막는 점유자 수가 가장 적은 후보를 우선한다. 동률이면 경로 비용과 현재 방사 방향으로부터의 회전량이 작은 후보를 사용한다.
- `CoreEscape`가 시작되면 Enemy 중심이 Player 중심에서 `200 cm` 이상 떨어질 때까지 Formation 변경으로 일반 경로로 조기 복귀하지 않는다.
- 정상 탈출 중에는 기존 Attack·Wait·Holding·Pending 예약을 유지하고 해당 Slot 대신 탈출 목표를 우선한다. 경로 실패나 교착으로 예약을 반납할 때만 Queue에 남으며 기존 Sequence를 보존한다.
- Core 내부 Enemy 또는 `CoreEscape` 중인 Enemy가 있어도 Wait→Attack 승격은 계속한다. 한 Requester의 탈출 지연이 모든 Attack Slot을 전역 잠그지 않아야 한다.
- 승격된 다른 Enemy는 정상 Attack 경로를 사용하고, 탈출 중인 Requester는 기존 `CoreEscape` Waypoint를 계속 우선한다. 탈출 Requester 자신이 바깥쪽 Attack Slot으로 승격되어 같은 방사 방향으로 바로 빠질 수 있으면 직접 출구 경로를 사용한다.
- Attack 교착 교대는 탈출 중 적용하지 않는다.

### 14.5 Attack 전열 안쪽 끼임 강제 교대

**현행 C++ 구현, PIE 검증 필요**

Attack Slot 점유자와 Player 사이에 비Attack Enemy가 끼어 일반 `CoreEscape`만으로 빠져나오지 못하는 경우에는 해당 Enemy를 바깥으로 밀어내는 대신 앞의 전열을 열어 준다.

- 후보는 `Chasing` 상태인 Wait·Holding·Pending Enemy다. 이미 Attack Slot을 점유했거나 공격 재진입 Cooldown 중인 Enemy는 제외한다.
- 양보 후보도 `Chasing` 상태인 Attack Slot 점유자만 허용한다. 공격 또는 회복 Montage 중인 전열은 강제로 끊지 않는다.
- Player 중심과 Attack 점유자 중심을 이은 2D 선분에서 좌우 `70 cm` 이내, 양 끝점에서 각각 `20 cm`보다 안쪽에 있는 Enemy만 침입 후보로 본다.
- 두 Actor의 높이 차이가 `100 cm`를 넘으면 다른 층의 Enemy로 보고 제외한다.
- 여러 조합이 동시에 성립하면 침입 Enemy와 가장 가까운 Attack 점유자 조합을 선택한다.
- 같은 조합이 유지되는 동안 침입 Enemy가 `20 cm` 이상 이동하면 정체 시간이 초기화된다. `0.35초` 동안 의미 있는 전진이 없을 때만 실제 끼임으로 확정한다.
- 확정 시 침입 Enemy가 해당 Attack Slot을 즉시 받고, 기존 점유자는 침입 Enemy가 가지고 있던 Wait 또는 Holding Slot을 이어받아 후퇴한다. 침입자가 Pending이었다면 기존 점유자도 예약 없는 Pending으로 내려가되 중앙 Queue Sequence는 보존한다.
- 두 Controller에는 같은 Tick에 예약 변경을 통지한다. 교체된 침입자는 Core 바깥 같은 방사 방향의 Attack Slot으로 바로 이동하며, 전체 `CoreEscape` 반경까지 불필요하게 넘어갔다 돌아오지 않는다.
- 기존 Attack 점유자에게 `1초` Attack 재진입 Cooldown을 주고 해당 Attack Slot의 다른 빠른 교대도 `1초` 막아 즉시 원상복귀하는 핑퐁을 방지한다.
- 이 강제 교대는 일반 Attack 교착 교대와 별도인 Combat Core 복구 예외다. 전체 기능은 `bEnableCoreIntrusionHandover`로 끌 수 있다.

## 15. 분산형 Ring 진입 경로

### 15.1 경로 단계

**현행**

| 단계 | 의미 | 디버그 색 |
| --- | --- | --- |
| `Direct` | 최종 Slot으로 직접 이동 | 흰색 |
| `ExitDecompression` | 통로·코너 출구를 직진 통과하며 분산 | 에메랄드 |
| `ApproachRing` | 현재 각도를 유지하며 정렬용 바깥 Ring으로 이동 | 청록 |
| `AlignOnRing` | Ring을 따라 목표 Slot 각도에 맞춘다 | 파랑 |
| `Ingress` | 각도 정렬 후 안쪽 Slot으로 방사형 진입 | 주황 |

### 15.2 역할별 정렬 Ring

- Attack으로 이동하는 Enemy는 Wait Ring을 정렬 Ring으로 사용한다.
- Wait로 이동하는 Enemy는 Holding Ring을 정렬 Ring으로 사용한다.
- Holding은 더 바깥의 별도 정렬 Ring이 없다. 직행이 Combat Core를 가로지르면 Holding Ring을 이용해 우회한다.

### 15.3 단계 전환 조건

Attack과 Wait처럼 안쪽 Ring으로 들어가는 경우 다음 규칙을 적용한다.

1. Enemy가 최종 Ring보다 `35 cm` 이상 바깥에 있으면 분산 진입 절차를 사용한다.
2. 정렬 Ring 반경에서 `35 cm`보다 멀면 현재 각도의 정렬 Ring 지점으로 `ApproachRing` 이동한다.
3. 정렬 Ring에 들어오면 플레이어 기준 현재 각도와 목표 Slot 각도를 비교한다.
4. 각도 차이가 `10°`보다 크면 목표 방향으로 최대 `45°`만 전진한 Ring Waypoint를 만들어 `AlignOnRing` 이동한다.
5. 각도 차이가 `10°` 이내이고 최종 Slot까지의 선분이 Combat Core를 가로지르지 않으면 `Ingress`로 전환한다.
6. `Ingress`가 시작된 뒤 같은 Slot 예약을 유지하고 최종 Slot 직선이 계속 Combat Core에 안전하면 바깥 Ring으로 되돌아가지 않는다. 플레이어 이동 등으로 직선이 다시 Core를 가로지르면 Route를 재계산한다.
7. 최종 Ring 바깥 조건을 벗어났고 직행이 안전하면 `Direct`로 최종 Slot을 향한다.

모든 Enemy가 하나의 공용 Gate로 모이지 않고 각자의 최종 Slot 각도에 맞는 Waypoint를 사용한다.

Enemy가 플레이어 중심과 정확히 같은 XY 위치에 있으면 현재 방향을 계산할 수 없으므로 목표 Slot의 정반대 방향을 임시 진입 방향으로 사용한다.

`ExitDecompression`, `ApproachRing`, `AlignOnRing`, `BypassCorePositive`, `BypassCoreNegative`, `CoreEscape`는 정지 지점이 아니라 통과용 Waypoint다. 이 단계에서는 Detour Crowd의 목표 감속을 끄고, Waypoint 도착 이벤트에서 정기 AI 갱신을 기다리지 않고 즉시 다음 경로 단계를 요청한다. 최종 Slot 좌표와 가까워도 중간 Route Stage가 남아 있으면 Slot 도착으로 판정하지 않는다. `Direct`와 `Ingress`처럼 최종 Slot으로 향하는 단계에서만 목표 감속과 Slot 도착 판정을 다시 켠다.

### 15.4 일반 Combat Core 우회

분산 진입 조건이 아니더라도 최종 목적지 직선이 Combat Core를 가로지르면 다음을 적용한다.

- Holding 목적지는 Holding Ring을 우회 Ring으로 사용한다.
- Attack·Wait 목적지는 Wait Ring을 기본 우회 Ring으로 사용한다.
- 우회 반경은 최소한 `AttackRingRadius + 35 cm`와 `EffectiveCombatCoreRadius + 35 cm`보다 작지 않게 보정한다.
- 먼저 우회 Ring 반경에 접근하고, 이후 목표 각도로 최대 `45°`씩 선회한다.

### 15.5 Pocket 코너 우선 점유와 점유 전열 우회

Pocket에서는 단순히 Requester와 가장 가까운 Slot부터 배정하지 않는다.

- 각 빈 Slot에서 기본 `8방향 × 180 cm` NavMesh Clearance를 검사한다.
- 벽이나 코너 때문에 짧게 막힌 탐침 길이의 평균에 기본 `2.0` 배율을 곱해 Nav 경로 비용에 더한다.
- 따라서 코너에 눌린 Slot보다 열린 공간 쪽 Slot이 먼저 점유된다. Slot이 실제로 도달 불가능하면 기존과 같이 후보에서 제외한다.
- 이 우선순위는 Pocket에만 적용한다. Open의 원형 분배와 Corridor의 고정 Side·Queue 순서를 바꾸지 않는다.

이미 도착한 Slot 점유자가 후속 Enemy의 경로를 물리적으로 막는 경우에는 다음 우회 규칙을 적용한다.

1. 후속 Enemy에서 최종 Slot까지의 완전한 Nav 경로를 구한다.
2. 다른 Attack·Wait·Holding 점유자 중 자기 Slot `70 cm` 안에 있고 속도 `30 cm/s` 이하인 Enemy만 고정 Blocker 후보로 본다.
3. 경로가 양쪽 Capsule 반지름 합과 여유 `8 cm` 이내로 Blocker를 통과하면 직행을 취소한다.
4. 후속 Enemy는 현재 방사 방향으로 점유 전열보다 기본 `140 cm` 바깥의 우회 Ring에 먼저 접근한다.
5. 우회 Ring을 따라 목표 Slot 각도까지 한 단계 최대 `45°`씩 이동한다.
6. 각도 차이가 `10°` 이하가 되면 `Ingress`로 전환해 바깥에서 안쪽으로 Slot에 진입한다.

`ApproachRing`과 `AlignOnRing`은 기존 통과용 Waypoint 규칙을 그대로 사용하므로 중간 지점에서 감속하거나 멈추지 않는다. 움직이는 점유자는 Detour Crowd가 처리하고, 실제로 도착해 통로를 고정적으로 막는 점유자만 명시적 우회를 유발한다. 적합한 우회 Waypoint 또는 완전한 경로를 만들 수 없으면 순간이동하지 않고 기존 직접 경로와 교착 Watchdog으로 복귀한다.
- 직행이 안전해지면 최종 Slot으로 진입한다.

### 15.6 경로 단계 초기화

다음 사건이 발생하면 경로 단계를 `Direct`로 초기화하고 다시 계산한다.

- Slot 종류 또는 인덱스 변경
- Formation Reform
- Slot 완전 반납
- Attack 교착으로 Wait 후보와 역할 교대
- 타깃 변경

## 16. Move 요청 규칙

### 16.1 요청 속성

**현행**

- Attack·Holding·Pending 최종 Slot Acceptance Radius: `20 cm`
- Wait 최종 Slot Acceptance Radius: `50 cm`
- Ring Waypoint Acceptance Radius: `30 cm`
- Pathfinding: 사용
- 목적지 NavMesh 투영: 사용
- Partial Path: 허용하지 않음
- Stop on Overlap: 사용하지 않음
- Path Following은 `CharacterMovement`의 가속·감속을 사용한다. AI가 속도를 직접 계단식으로 덮어쓰는 방식은 사용하지 않는다.
- 통과용 ExitDecompression·Ring·Combat Core Waypoint는 `Slowdown At Goal`을 끄고 도착 즉시 다음 Move를 연결한다. 최종 Slot과 Pursuit 목적지는 `Slowdown At Goal`을 켠다.
- 회전: 포위 범위 밖 Pursuit만 진행 방향을 바라본다. Engagement Formation 상태에 있는 동안 InitialCharge·Ring 이동·Ingress·정지 대기는 모두 Player Focus를 유지한다.

### 16.2 재요청 조건

다음 중 하나면 기존 Move를 그대로 두지 않고 다시 요청한다.

- 아직 해당 Slot로 Move를 요청하지 않았다.
- Slot 종류나 인덱스가 바뀌었다.
- 경로 단계가 바뀌었다.
- Attack 이동 목표가 마지막 요청 위치에서 `80 cm` 이상 움직였다.
- Wait 이동 목표가 `150 cm`, Holding/Pending 목표가 `250 cm` 이상 움직였다.
- Path Following이 더 이상 이동 중이 아니다.
- Player 또는 지연 Engagement Anchor가 마지막 제한형 Reform 기준점에서 `75 cm` 이상 이동했다. 이 경우 Slot Component가 예약자에게 다음 프레임 갱신을 직접 통지하므로 역할별 거리 임계값을 기다리지 않는다.

Slot 종류·인덱스 변경, Initial 배치 확정과 선택적 Reform은 목적지 변경이다. 기존 Move를 먼저 정지하지 않고 현재 Velocity를 유지한 채 새 Move 요청으로 교체한다. `StopMovement()`는 최종 Slot 도착, 공격·경직·사망과 실패 복구처럼 실제 정지가 필요한 경우에만 사용한다.

### 16.3 Slot 도착

- Enemy와 예약 Slot의 2D 거리가 기본 `20 cm` 이내면 위치상 도착 후보로 본다. Slot은 정확히 밟아야 하는 점이 아니라 허용 구역이다.
- Wait만 `50 cm` 이내를 도착 후보로 보고 `80 cm/s` 이하에서 정지한다. Wait 주변에서 Crowd 감속 때문에 마지막 몇 cm를 발을 끌며 이동하지 않게 하기 위한 예외다.
- 위치상 도착한 동안에는 같은 위치로 0거리 Move 요청을 반복하지 않고 `CharacterMovement`가 자연 감속하게 둔다.
- Wait가 아닌 Slot은 수평 속도가 `5 cm/s` 이하가 되었을 때 최종 도착으로 확정하고 `StopMovement()`를 호출한다.
- Wait와 Holding은 최종 도착 후 대기한다.
- Attack은 최종 도착 후 실제 타깃 거리를 다시 검사한다.
- Wait·Holding·Pending은 Engagement Formation 상태 동안 Player Focus를 유지하므로 감속·최종 도착 시 회전 정책을 바꾸지 않는다.

### 16.4 Formation 이동 역할과 Attack 우선 통행

Controller는 목적지 계층과 도착 여부로 현재 Traffic Role을 분류한다.

- `AttackIngress`: Attack Slot으로 이동 중
- `WaitIngress`: Wait Slot으로 이동 중
- `WaitIngressDeferred`: Attack 진입 통로와 충돌하여 출발 보류 중
- `HoldingTransit`: Holding Slot으로 이동 중
- `StationaryHolding`: Holding Slot에 도착해 정지 중
- `HoldingYield`: 실제 교착 경로를 비우기 위해 예약을 유지한 채 임시 위치로 양보 중
- `PendingTransit`: Pending 목적지로 이동 중

새 Wait 이동 구간을 시작하기 전에는 Wait 현재 위치부터 다음 Move Goal까지의 완전한 Nav 경로와, 이동 중인 각 Attack Owner부터 최종 Attack Slot까지의 완전한 Nav 경로를 비교한다.

- Attack Owner는 `Chasing` 상태이며 최종 Attack Slot에서 `55 cm`보다 멀 때만 활성 Attack 진입자로 본다.
- 두 경로의 선분 간 거리가 양쪽 Capsule 반지름 합과 여유 `20 cm` 이내이면 이동 통로가 충돌한 것으로 본다.
- 경로 선분의 평균 높이 차이가 `100 cm`를 넘으면 다른 층으로 보고 충돌에서 제외한다.
- 충돌하면 Wait 예약은 유지하지만 `StopMovement()`로 새 출발을 보류하고 `WaitIngressDeferred`로 표시한다.
- 보류된 Wait는 기본 `0.2초`마다 다시 검사한다. Attack Owner가 도착하거나 공격·회복 상태로 전환되어 진입자가 아니게 되면 Wait가 즉시 출발한다.
- 이미 Move 요청을 받아 이동 중인 Wait는 새 Attack 통로가 생겼다는 이유로 중간에서 정지시키지 않는다. 새 Slot·Waypoint 이동 구간을 시작할 때만 우선권을 검사한다.
- 이 규칙은 고정 Gate나 공통 집결점을 만들지 않는다. 실제 두 Nav 경로가 겹치는 동안에만 Attack의 출발 우선권을 보장한다.

### 16.5 Stationary Holding 최소 양보

Attack 또는 Wait 이동자가 Move Goal까지의 거리를 기본 `0.75초` 동안 줄이지 못했을 때만, 현재 Nav 경로를 실제로 막는 `StationaryHolding`을 검사한다. 단순히 가까이 있다는 이유로 양보시키지 않는다.

- 이동자의 현재 위치부터 즉시 Move Goal까지 완전한 Nav 경로를 구한다. Partial Path는 사용하지 않는다.
- 경로 전방 `260 cm` 안에서 경로와의 거리가 두 Capsule 반지름 합과 여유 `10 cm` 이내인 Holding만 후보로 본다.
- `Chasing`, 속도 `10 cm/s` 이하, `StationaryHolding`인 후보 중 경로를 따라 가장 먼저 만나는 한 명만 선택한다.
- 한 Player의 포위망에서는 동시에 한 명의 Holding만 양보한다.
- 양보 위치는 방해한 로컬 Nav 경로의 좌우 수직 방향 `130 cm` 후보 중에서 고른다. Nav 투영 오차 `70 cm`, 경로 여유, Player 쪽으로의 과도한 이동, 다른 Enemy와의 깊은 중첩을 검사하고 완전한 Nav 경로가 있는 후보만 허용한다.
- 적합한 양보 위치가 없으면 Holding을 강제로 움직이거나 순간이동시키지 않고 기존 교착 복구에 맡긴다.
- 양보하는 Holding은 Slot 예약을 반납하지 않는다. `HoldingYield` 상태로 임시 위치에 도착한 뒤, 이동자가 해당 로컬 경로 단면을 `45 cm` 통과하면 원래 Holding Slot 로직으로 복귀한다.
- 통과 판정은 최소 `0.3초` 이후에만 허용하며, 판정 실패에 대비해 `1.5초` 뒤에는 복귀한다.
- 성공·실패 여부와 관계없이 이동자의 다음 양보 탐색은 기본 `1초` 동안 막아 동기 Nav 경로 검사가 반복되지 않게 한다.
- 양보 중 사망·경직·Slot 반납·Controller 해제 등이 발생하면 임시 이동을 즉시 종료한다.

디버그에서는 `Traffic:HoldingYield`와 양보 위치까지의 보라색 선·구를 표시한다.

## 17. Attack Slot 도착과 공격 이동 잠금

### 17.1 공격 개시 조건

Attack Slot에 도착한 것만으로 무조건 공격하지 않는다. 다음 조건을 모두 만족해야 한다.

- 서버 권한이다.
- Enemy 상태가 `Chasing`이다.
- 유효한 현재 타깃이 있다.
- 유효한 Enemy Config, 공격 설정, Attack Definition, Montage가 있다.
- 현재 구현된 Hit Detection Mode다.
- Enemy Actor 중심과 타깃 Actor 중심의 2D 거리가 `AttackStartRange` 안에 있다.

### 17.2 거리 불일치 또는 시작 실패

- Attack Slot에 도착했지만 타깃이 공격 개시 거리 밖이면 현재 슬롯을 `AttackRangeMismatch` 사유로 반납한다.
- 공격 설정 오류 등으로 공격을 시작하지 못하면 `AttackStartFailed`로 반납한다.
- 두 경우 모두 해당 Enemy에게 실패한 Slot을 기본 `2초` 동안 다시 배정하지 않는다.

### 17.3 공격 중 이동

공격은 `StationaryFullBody`와 `MovingUpperBody` 두 표시 모드를 사용한다. 두 모드 모두 공격 시작 시 타깃을 `AttackTarget`으로 고정하고, `Attacking → Recovering → Chasing` 전투 상태와 서버 판정·회복 시간은 공유한다.

**StationaryFullBody**

- Attack Slot에 도착하고 수평 속도 `5 cm/s` 이하로 정착한 뒤 시작한다.
- AI 이동을 정지하고 전신 공격을 재생한다.
- DataTable의 `RecoveryDuration` 동안 이동과 재공격을 막는다.
- 정상 공격이었다면 Attack Slot을 유지하고, 회복 종료 후 같은 자리에서 다음 공격 조건을 검사한다.

**MovingUpperBody**

- Attack Slot 소유자가 아직 Slot으로 이동 중이고, Core Escape 상태가 아니며, 유효한 Move 요청과 완전한 경로를 따라가는 동안에만 시작한다.
- `BHAttackDefinition`의 `bAllowMovingAttack`을 명시적으로 켜야 하며 Player와의 거리가 `MovingAttackStartRange` 이하여야 한다. 기존 공격 행은 자동 적용하지 않는다. 거리 기본값은 `300 cm`다.
- Montage와 Recovery 중에도 기존 Slot·추격 Move를 중지하지 않는다. 하체 Locomotion은 계속 이동하고 상체에만 공격 Montage를 합성한다.
- 공격·회복 중에는 새 공격을 시작하지 않는다. Player가 계속 이동해 Attack Slot 추격이 이어지면 회복 후 다시 MovingUpperBody 공격이 가능하다.
- Enemy가 Slot에 정착하면 진행 중인 이동 공격·회복이 끝난 다음 공격부터 StationaryFullBody를 사용한다.
- Wait·Holding·Pending Enemy는 이동 공격을 시작하지 않는다. Attack Slot 동시 공격 인원 정책을 우회하지 않는다.

Enemy AnimInstance는 `bUseMovingUpperBodyAttack`을 제공한다. AnimGraph는 이 값이 참이면 Locomotion Cache와 `UpperBody` Slot을 척추 기준 `Layered Blend per Bone`으로 합성하고, 거짓이면 같은 Slot 결과를 전신 Pose로 사용해야 한다.

### 17.4 공격 Root Motion

**현행 운용 원칙**

- 현재 Slot과 CharacterMovement가 위치의 주도권을 가진다.
- 일반 공격 Montage가 Capsule을 앞으로 이동시키는 Root Motion을 사용하면 Slot 거리와 실제 Actor 위치가 어긋나 공격 반복이 멈추거나 교착 판정이 왜곡될 수 있다.
- 따라서 현재 기본 공격 애니메이션은 수평 이동이 없는 In-place를 사용하고 공격 Root Motion은 끈다.
- 예외인 Troll Charge는 별도 Component가 Root Motion 이동 권한을 독점하고 기존 Attack Slot 예약은 유지한다. 구체 규칙은 37장의 `Troll Root Motion Charge`를 따른다.

## 18. 정상 공격 후 전열 유지

**현행**

- 공격을 한 번 마칠 때마다 Attack과 Wait가 자리를 바꾸지 않는다.
- Attack Enemy는 공격과 회복 뒤에도 같은 Slot을 계속 점유한다.
- 공격 횟수나 시간에 따른 순환 교대는 아직 없다.
- Wait와 Holding은 빈자리가 생길 때까지 대기한다.

이 규칙은 전열과 후열이 매 공격마다 기계적으로 자리 바꾸는 모습을 방지하고 안정적인 포위 대형을 유지하기 위한 것이다.

## 19. 플레이어 이동과 Formation Reform

### 19.1 작은 이동

- Attack Slot은 플레이어 현재 위치를 따라가지만 예약 주체와 인덱스는 유지한다.
- Wait·Holding·Pending Slot은 Engagement Anchor를 따라가며, 플레이어가 Anchor의 `175 cm` Dead Zone 안에서 움직일 때는 이동하지 않는다.
- 플레이어가 정지하면 Anchor는 지연을 영구적으로 유지하지 않고 중앙으로 부드럽게 복귀하여 외곽 Ring의 대칭을 회복한다.
- Player와 Anchor의 이동이 각각 `75 cm` 미만이면 기존 예약을 유지한다. Controller별 주기와 역할별 재경로 임계값이 미세한 변화로 인한 잦은 재요청을 막는다.

### 19.2 제한형 Reform

**현행**

- Player 또는 Engagement Anchor가 마지막 기준점에서 `75 cm` 이동하면 제한형 Reform을 실행하고 모든 예약자에게 다음 프레임 경로 갱신을 통지한다.
- Attack·Wait·Holding 역할은 바꾸지 않으며 현재 점유 중인 Slot 집합도 그대로 유지한다.
- 같은 계층의 두 Enemy가 Slot을 교환했을 때 남은 2D 이동거리 합이 기존보다 최소 `75 cm` 줄어드는 경우에만 교환한다.
- 한 번 교환한 뒤 다시 전체 후보를 계산하고, 추가로 기준을 넘는 교환이 없을 때 종료한다. 따라서 작은 위치 차이로 Slot 소유권이 왕복하지 않는다.
- 공격 또는 회복 중인 Attack Enemy는 교환 대상에서 잠근다. 공격 중 위치가 갑자기 바뀌지 않는다.
- 교환은 Queue Sequence와 승격 우선권을 변경하지 않는다. 물리적으로 누가 어느 Slot으로 이동할지만 바꾼다.
- 플레이어가 Enemy에게서 `900 cm` 이상 멀어지면 해당 Enemy가 개별적으로 Slot·Queue를 반납하고 Pursuit로 전환한다.

Pocket에서는 새 Pocket 진입, 열린 방향이 `15°` 이상 변한 순간, Player 또는 Engagement Anchor가 Reform 기준 `75 cm`를 넘긴 순간부터 `1.5초` 동안 신속 포위 재편 상태를 사용한다.

- 진입 또는 방향 전환 순간 Wait·Holding의 같은 계층 Slot 소유권을 즉시 거리 절감 기준으로 다시 계산하고 모든 예약자에게 다음 프레임 경로 갱신을 통지한다.
- Pocket Attack 계층의 같은 계층 교환은 직선거리가 아니라 완전한 Nav 경로를 기준으로 비교한다. 현재 조합에 도달 불가 경로가 있고 교환 조합은 양쪽 모두 도달 가능하면 거리 절감량보다 경로 복구를 우선한다.
- 신속 재편 중에도 `Attacking`·`Recovering` Attack 점유자는 잠근다. 진행 중인 공격을 빠른 포위 연출 때문에 중단하지 않는다.

### 19.3 Reform 안정 장치

- Reform이 발생해도 Controller는 기존 Velocity를 0으로 만들지 않고 다음 프레임에 새 Slot 경로로 교체한다.
- 총 이동거리 절감이 `75 cm` 이하인 교환은 하지 않는다.
- 빈 Slot을 새로 채우거나 계층 전체를 다시 섞지 않으므로 현재 대형의 밀도와 역할 구조가 유지된다.
- Corridor에서도 Sequence 압축으로 확보된 점유 Slot 집합은 유지한 채 소유자끼리만 제한적으로 교환한다.

### 19.4 Attack Slot 빠른 인계

Attack Slot이 논리적으로 예약되어 있어도 예약자가 멀리 있어 전열이 실제로 비어 보이는 경우에는 Wait Enemy와 예약을 교환한다. Crowd 조향이나 이동속도를 변경하지 않고 중앙 Slot Manager가 역할만 원자적으로 교환한다.

- 현재 Attack 예약자는 `Chasing`이어야 한다. `Attacking`과 `Recovering`은 공격 위치를 보존하므로 인계 대상이 아니다.
- 거리 비교는 Enemy Actor 중심과 투영된 Slot 좌표 사이의 2D 직선거리다. 현재 예약자가 Attack Slot에서 `120 cm` 이상 떨어지고, Wait 후보가 현재 예약자보다 `100 cm` 이상 가까우면 경계값을 포함해 거리 조건을 만족한다. Pocket 신속 재편 `1.5초` 동안에는 필요한 거리 우위를 `25 cm`로 낮춘다.
- Attack 재진입 Cooldown이 끝난 Wait Enemy만 후보가 된다. Corridor에서는 해당 Attack Slot과 실제로 같은 Side에 있는 Wait Enemy만 후보가 된다. 반대 Side 후보를 끌어와 Player와 군집 사이를 통과시키지 않는다. 같은 Side 후보 중 가장 가까운 후보를 고르고, 거리가 `1 cm` 이내로 같으면 Queue Sequence가 빠른 Enemy를 우선한다.
- 후보 Attack Slot은 해당 Enemy의 공격 가능 거리 안에 있어야 한다.
- 같은 후보가 모든 조건을 연속 `0.3초` 만족한 뒤에만 교환한다. Pocket 신속 재편 중에는 이 시간을 `0.1초`로 줄인다. 후보가 바뀌거나 조건을 잃으면 누적 시간을 초기화한다.
- 인계 직전에 Wait 후보에서 Attack Slot까지 완전한 Nav 경로를 확인한다. 최초 거리 후보가 도달할 수 없으면 도착 여부와 무관하게 모든 Wait 후보 중 완전한 Nav 경로 점수가 가장 낮은 후보를 대신 선택한다.
- 한 서버 Tick에서 후보는 Attack Slot을 받는다. 기존 Attack 예약자가 후보의 Wait Slot까지 갈 수 있으면 그 Slot으로 후퇴하고, 갈 수 없으면 예약 없는 Pending으로 내려간다. Queue Sequence는 어느 경우에도 보존한다.
- 교환 순간부터 기존 예약자는 모든 Attack Slot 재진입이 `0.75초` 제한되고, 해당 Attack Slot도 새로운 빠른 인계가 `0.75초` 제한된다.
- Combat Core 탈출은 해당 Enemy의 로컬 이동 상태다. 한 Enemy의 `CoreEscape`는 반대편 Attack Slot의 빠른 인계뿐 아니라 일반 빈자리 승격도 전역 중단하지 않는다.
- 정상 공격 종료와 회복만으로는 기존 Attack Slot을 반납하지 않는 규칙을 유지한다. 빠른 인계는 실제 Slot이 멀리 비었고 더 가까운 Wait 후보가 있을 때만 발생한다.

## 20. 경로 실패와 교착 Watchdog

### 20.1 즉시 실패

다음 경우에는 2초를 기다리지 않는다.

- `MoveToLocation` 요청 자체가 실패
- Path Following 결과가 Abort가 아닌 실패
- 예약 Slot이나 계산된 Route가 무효

Wait·Holding·Pending은 다음 결과를 사용한다.

1. 현재 슬롯을 반납한다.
2. 실패 Slot을 해당 Enemy에게 `2초`간 제외한다.
3. 이동 상태를 초기화한다.
4. 다음 갱신에서 다른 Slot을 요청한다.

Attack 점유자의 Move 요청 또는 Path Following이 실패하면 바로 반납하지 않고 20.3의 중앙 교대를 먼저 호출한다. 도달 가능한 Wait 후보가 없을 때만 위 일반 실패 절차로 내려간다.

`Aborted` 결과는 경로 실패로 취급하지 않는다. 공격·정지·새 Move 요청처럼 시스템이 기존 이동을 의도적으로 중단하는 경우가 포함되기 때문이다. 이후 Controller 상태와 다음 주기 조건에 따라 정상 Move를 다시 요청한다.

### 20.2 Watchdog 측정

**현행 기본값**

- 측정 주기: `0.5초`
- 의미 있는 진전: Slot까지 남은 거리가 이전 기준보다 `20 cm` 이상 감소
- 저속 기준: `10 cm/s` 미만
- 저속 교착 확정: 저속이며 의미 있는 진전이 없는 상태가 누적 `2초`
- 강제 미진행 교착 확정: 속도와 무관하게 목표까지의 거리가 `20 cm` 이상 줄지 않은 상태가 누적 `4초`
- Attack Slot 이동의 강제 미진행 교착 확정: 보행 종류와 무관하게 `1.5초`

첫 표본의 Move Goal 잔여 거리를 진행 기준으로 저장한다. 기본 `0.5초` 갱신마다 `기준 거리 - 현재 거리`가 누적 `20 cm` 이상이면 기준을 현재 거리로 바꾸고 두 누적 시간을 초기화한다. 매 표본마다 `20 cm`를 전진해야 하는 규칙은 아니다. 줄을 서서 느리게 움직이더라도 누적 목표 거리가 계속 줄면 교착으로 확정하지 않는다. 반대로 두 Enemy가 서로 밀어 실제 속도만 발생하고 목적지에는 가까워지지 않는 경우에는 강제 watchdog이 복구를 시작한다. 같은 Slot 종류와 인덱스를 유지한 Formation Revision은 즉시 경로만 갱신하고 교착 표본은 보존한다. 실제 Slot 종류·인덱스가 바뀌거나 Route Stage 또는 Move Goal이 계층별 재경로 거리 이상 변한 경우에만 이전 이동 구간의 진행 표본을 폐기한다. 따라서 반복 Reform이 움직이지 않는 Attack 점유자의 `1.5초` 판정을 영구적으로 미루지 않는다.

#### 원거리 Pursuit Watchdog

- Formation 밖에서 Path Following 상태가 `Moving`인데 Enemy Actor가 기준 위치에서 누적 `50 cm`도 이동하지 못한 상태가 `2초` 지속되면 원거리 추격 교착으로 확정한다.
- 움직이는 Player 때문에 목표까지 거리가 줄지 않는 정상 추격을 오판하지 않도록, 목표와의 거리 대신 Enemy 자신의 실제 변위를 측정한다.
- 확정 시 현재 Move를 중단하고 오래된 경로와 추격 방향 보간값을 폐기한 뒤 즉시 현재 Player 예측 위치와 기존의 고정 Lane·Row를 기준으로 새 Nav 경로를 요청한다. Lane·Row 소유 자체는 바꾸지 않는다.
- 복구 후 `1초` 동안 Watchdog 재발동을 막는다. 이 기능은 막힌 NavMesh를 생성하거나 순간이동시키는 기능이 아니라, 유효한 길이 있는데 Crowd 경로 상태가 정체된 경우를 위한 재탐색 안전망이다.
- 디버그 문자열의 `PWatch:누적시간/복구횟수`로 상태를 확인한다.

### 20.3 Attack 예약자의 교착

Attack Slot으로 이동 중인 Enemy가 교착되거나 Move 경로를 만들지 못하면 중앙 교대를 먼저 시도한다.

1. Wait 예약자 전체를 검사한다. 강제 교대에서는 자기 Wait Slot 도착 조건을 요구하지 않는다.
2. 해당 Attack Slot까지 완전한 Nav 경로가 있는 후보만 남긴다.
3. Nav 경로 길이에 경로 주변 같은 층 Queue Agent 패널티를 더한 점수가 가장 낮은 후보를 고르고, `1 cm` 이내 동률이면 Sequence가 빠른 후보를 고른다.
4. 한 서버 처리 안에서 Wait 후보를 기존 Attack Slot으로 승격한다.
5. 교착 Enemy가 후보의 Wait Slot까지 갈 수 있으면 해당 Slot으로 강등한다. 그 경로도 만들 수 없으면 Pending으로 내려가 더 이상 Attack Slot을 붙잡지 않는다.
6. 강등된 Enemy의 Queue Sequence는 유지한다.
7. 강등된 Enemy는 `2초` 동안 Attack 재승격 후보가 될 수 없다.

적합한 Wait 후보가 없으면 일반 실패와 같이 Slot을 반납하고 실패한 Attack Slot을 `2초`간 제외한다.

권위 Combat State가 `Attacking`이면 이동을 고정한다. `Recovering`에 들어간 뒤 각 Controller 갱신에서 Enemy ActorLocation과 현재 Attack Slot의 XY 거리가 적용 Leash보다 큰지 검사한다. 기본 Leash는 `60 cm`이며 정확히 같은 거리는 허용한다. 이 조건이면 일반 watchdog을 기다리지 않고 `Stalled` 사유의 교착 교대를 실행하되 Combat State는 `Recovering`으로 유지한다. 회복 중 Capsule 밀림으로 Slot 밖에 있는 Enemy가 Attack 예약을 유지한 채 정지하는 상황을 막기 위한 규칙이다. 도착한 Wait 후보가 있으면 한 서버 처리 안에서 두 예약을 원자적으로 교환하고, 없으면 Attack 예약을 반납한다. 교대된 Enemy는 남은 Recovery가 끝난 뒤 후보가 비운 Wait 목적지로 이동한다. 사망·경직·타깃 무효화 등 기존 상위 취소 규칙은 별도로 계속 적용한다.

### 20.4 Wait·Holding 예약자의 교착

- 중앙 Attack 교대 대상이 아니다.
- 현재 Slot을 반납하고 실패 Slot을 `2초`간 제외한다.
- Queue Sequence는 보존하므로 오래 기다린 우선권을 잃지 않는다.
- 다음 Controller 갱신에서 다시 Slot을 요청한다.

### 20.5 Enemy 중첩 탈출 복구

Slot 예약 여부와 무관하게 살아 있는 Enemy Capsule 중심의 XY 거리가 두 Capsule 반지름 합의 `90%`보다 작고 높이 차가 `100 cm` 이하이면 중첩 후보로 판정한다. 같은 좌표에 스폰된 경우도 포함한다. Enemy끼리 물리 Block하지 않으므로 이 판정은 충돌 이벤트가 아니라 각 Controller의 주기 검사로 수행한다.

중첩된 둘이 동시에 같은 회피를 실행하지 않도록 다음 우선순위가 높은 Enemy는 기존 이동·행동을 유지하고 낮은 Enemy 하나만 양보한다.

1. `Staggered`
2. `Attacking`
3. `Recovering`
4. Controller가 없는 살아 있는 Enemy
5. Attack 예약자
6. Wait 예약자
7. Holding 예약자
8. Pending 예약자
9. 예약 없는 Chasing Enemy

우선순위가 같으면 Actor Unique ID가 큰 쪽만 양보한다. 따라서 한 쌍이 서로를 동시에 밀어 대칭 교착을 반복하지 않는다. 정확히 같은 Transform에 여러 Enemy가 생성된 경우에는 Unique ID 기반 Golden Angle 방향으로 탈출 방향을 분산한다.

양보 Enemy는 현재 Combat Slot과 Queue Sequence를 유지한다. 주변 Enemy와 반대 방향을 기본으로 `0°, ±45°, ±90°, ±135°, 180°` 후보를 NavMesh에 투영하고, 주변 Enemy와의 최소 여유가 크며 완전한 Nav 경로가 있는 지점을 선택한다. 기본 탈출 거리는 `110 cm`, Capsule 반지름 합 바깥 여유는 `20 cm`, 1회 제한 시간은 `0.75초`다. 이 짧은 이동 동안 양보 Enemy의 Detour Crowd Obstacle Avoidance와 Separation만 임시로 끄되 NavMesh Path Following과 World·Player 물리 충돌은 유지한다. 중첩 해소·목표 도착·시간 초과 중 하나가 발생하면 Crowd 설정을 원복하고 기존 Slot 또는 Pursuit 목표를 즉시 재탐색한다. 재시도 간격은 `0.25초`다.

공격·회복·경직 중인 Enemy 자신은 탈출 이동을 시작하지 않는다. 겹친 이동 가능 Enemy가 대신 양보한다. 디버그 상태의 `Overlap:Escape`와 주황색 선·구는 현재 탈출 목표를 뜻한다.

### 20.6 고지대 병목 낙하 복구

- 낙하 실행 권한은 실제 `Wait` Slot을 예약한 Enemy에게만 있다. Attack·Holding·Pending 예약자와 Slot 진입 전 Pursuit Enemy는 낙하하지 않는다.
- 기존 Wait Slot 이동의 순진행이 기본 `0.75초` 동안 없거나, Wait 경로 요청·Path Following이 실패하거나, 다른 Enemy와 실제로 겹친 병목이 감지됐을 때 낙하 복구를 검사한다. Attack 진입 통행 때문에 Wait 이동이 보류된 경우에는 첫 재시도부터 낙하 가능성을 검사한다.
- Enemy가 `Chasing`이고 지상에 있으며 예약한 Wait Slot보다 기본 `80 cm` 이상 높은 경우에만 후보가 된다. 공격·회복·경직·사망 및 이미 낙하 중인 상태에서는 사용하지 않는다.
- Player까지 완전한 NavMesh 경로가 끊겨 있어도 아래쪽 유효 착지 후보가 있으면 해당 Player를 임시 타깃으로 유지할 수 있다. 그러나 실제 낙하는 Wait Slot 예약을 얻은 뒤에만 실행한다.
- 착지 목표는 Player 중심이 아니라 해당 Enemy가 예약한 실제 Wait Slot이다. Wait Slot 위치를 다시 NavMesh에 투영하며, 착지 높이 차는 기본 `80~650 cm`, 수평 거리는 Capsule 지름 이상이면서 최대 `900 cm`여야 한다. 조건을 만족하지 않으면 기존 경로 복구를 사용한다.
- 착지점은 NavMesh 표면에 투영한 뒤 Enemy Capsule 반높이를 더한 Actor 중심 좌표로 환산한다. 낙하 높이와 중력을 사용해 착지점에 도달하는 비행시간을 계산하고, 수평 속도가 기본 `700 cm/s`를 넘지 않도록 포물선 초기 속도를 만든다.
- 낙하를 시작해도 Wait Slot과 Queue Sequence를 반납하지 않는다. AI 경로 요청만 멈추고 `bHighGroundDropActive`를 유지한다.
- 착지하면 `bHighGroundDropActive`를 해제하고 다음 프레임에 보존한 Wait Slot을 즉시 재탐색한다. 재시도 Cooldown은 기본 `2초`다.
- 착지점이 없을 때만 기존 Holding 양보, 중첩 탈출 및 watchdog 복구를 계속한다.
- 이 기능은 Wait 대형의 고지대 병목 복구다. 정상적인 층간 이동을 대신하는 범용 Traversal이 아니며, 예약한 Wait Slot 자체가 유효한 아래쪽 NavMesh 지점이 아니면 발동하지 않는다.

### 20.7 현재 한계

- 실패 Slot 제외는 Enemy별 마지막 Slot 하나만 기억한다.
- 여러 Slot이 연속으로 실패하는 복잡한 지형에서는 같은 종류의 실패가 반복될 수 있다.
- 중첩 탈출은 이미 겹친 두 Agent의 대칭 교착을 복구하는 기능이다. NavMesh 여유 공간이 전혀 없는 병목, 잘못된 지형, 막힌 NavMesh, 서로 겹친 투영 Slot 자체는 완전히 복구하지 못한다.

## 21. Slot 반납 사유와 결과

| 사유 | 발동 조건 | 재요청/결과 |
| --- | --- | --- |
| `TargetChanged` | 더 가까운 다른 플레이어로 타깃 변경 | 새 플레이어의 Queue에 등록 |
| `TargetLost` | 현재 타깃 무효 | 이동 중지 후 다음 탐색 대기 |
| `UnPossessed` | Controller가 Pawn을 놓음 | 예약과 이동 정리 |
| `ReservationInvalid` | 예약 또는 Route를 사용할 수 없음 | 다시 예약 시도 |
| `AttackRangeMismatch` | Attack Slot 도착 후 타깃이 사거리 밖 | Slot 2초 제외 후 재요청 |
| `AttackStartFailed` | 공격 데이터·Montage 등 시작 조건 실패 | Slot 2초 제외 후 재요청 |
| `MoveRequestFailed` | Move 요청 즉시 실패 | Slot 2초 제외 후 재요청 |
| `PathFollowingFailed` | 진행 중 경로가 실패 | Slot 2초 제외 후 재요청 |
| `Stalled` | 저속 Watchdog 2초 또는 강제 미진행 Watchdog 4초 확정 | Attack은 교대 우선, 아니면 반납 |
| `LeftEngagementRange` | Formation 참여 Enemy가 타깃과 900 cm 이상 멀어짐 | Slot·Queue 반납 후 직접 Pursuit |
| `Staggered` | 생존 피격으로 경직 | 즉시 반납, 경직 후 새로 요청 |
| `Died` | Health가 0 | 즉시 반납, 재요청 없음 |

`AttackRecoveryComplete` 사유는 enum에 남아 있지만 현재 정상 회복에서는 사용하지 않는다. 정상 회복 후 Attack Slot을 유지하는 규칙이 우선한다.

## 22. 경직

**현행**

1. 서버에서 살아 있는 Enemy가 경직에 들어간다.
2. 진행 중인 공격, 회복 타이머와 고정 Attack Target을 취소한다.
3. 상태를 `Staggered`로 바꾼다.
4. Slot을 즉시 반납하고 이동을 정지한다.
5. 선택적 Hit React Montage를 재생한다.
6. 명시한 경직 시간이 없으면 Enemy Config의 기본 `0.6초`를 사용한다.
7. 기본 시간을 사용하면서 Montage가 더 길면 최소한 Montage 길이만큼 경직을 유지한다.
8. 경직 종료 후 `Chasing`으로 돌아간다.
9. 다음 Controller 갱신에서 새 Queue Sequence와 Slot을 요청한다.

경직한 Enemy는 기존 Attack 우선권을 보존하지 않는다. 경직 중 빈 Attack Slot은 대기 중인 Enemy가 승격할 수 있다.

## 23. 사망

### 23.1 공통 사망 처리

1. 서버에서 Health가 0이 되면 `Dead`로 전환한다.
2. 공격과 회복을 취소한다.
3. Slot과 Queue 등록을 즉시 반납한다.
4. 이동을 멈추고 Character Movement를 비활성화한다.
5. Death Montage가 있으면 재생한다.
6. 기본 `0.2초` 후 Capsule Collision을 비활성화한다.
7. AI Controller를 분리한다.
8. Pool 관리 Enemy면 시체를 Pool Manager에 등록하며 LifeSpan을 설정하지 않는다.
9. Pool 관리 밖의 Enemy만 `DeadActorLifeSpan`이 0보다 클 때 기본 `5초` 뒤 제거한다.

### 23.2 Pool 관리 시체

- 시체는 `Dead`이면서 `PoolInWorld = true`인 상태다.
- 살아 있는 Active Enemy 수에는 포함되지 않는다.
- AI Controller, Movement와 Slot·Queue 참여는 제거되지만 Actor와 Mesh는 월드에 남는다.
- 기본 `0.2초` 뒤 Capsule Collision을 끄므로 살아 있는 Crowd의 Nav Agent로 남지 않는다.
- Free Reserve가 남아 있는 동안 사망 후 경과시간과 관계없이 회수하지 않는다.
- Free Reserve가 없고 교체 스폰 요청이 준비됐을 때만 가장 오래된 eligible Corpse 한 구를 회수한다.

### 23.3 사망 자세 유지

**에디터 조건**

- Death Montage가 끝난 뒤 Idle로 돌아가지 않도록 Montage 자동 Blend Out을 끄거나 AnimBP의 `bIsDead` 상태에서 마지막 사망 자세를 출력한다.
- 시체 유지 시간은 Death Montage 길이보다 짧아서는 안 된다.
- 군중 검증 기준에서는 사망 애니메이션의 수평 Root Motion을 우선 끄고 Slot 반납·Capsule 비활성화가 정확한지 먼저 확인한다.
- 의도적인 뒤로 밀림 Root Motion은 서버 위치·Collision·Nav Agent 제거 시점까지 별도 검증한 경우에만 사용한다.

## 24. 이동 애니메이션 규칙

### 24.1 이동 소유권

**현행 원칙**

- NavMesh와 CharacterMovement가 Capsule의 실제 이동을 담당한다.
- Idle·Walk·Jog·방향 이동 애니메이션은 모두 In-place로 통일한다.
- Locomotion에서 Root Motion과 In-place 애니메이션을 섞지 않는다.

### 24.2 AnimInstance 값

- `GroundSpeed`는 XY Velocity 크기로 계산한다.
- `Direction`은 Actor 전방·오른쪽 벡터와 Velocity의 내적으로 계산한다.
- 플레이어에게 Focus를 둔 상태로 옆으로 이동하면 `Direction`이 좌우 값을 가질 수 있다.
- 공통 `bHasAcceleration`은 입력·가속이 있는지를 보여줄 뿐 실제 이동 중인지의 단독 기준으로 쓰지 않는다. 감속 중에는 Velocity가 남아 있어도 Acceleration이 0일 수 있다.
- Enemy는 `GroundSpeed` 히스테리시스로 계산한 `bShouldMove`를 사용한다.
- 기존 Enemy ABP가 `bHasAcceleration`을 참조하고 있으므로 Enemy AnimInstance에서만 이를 `bShouldMove`와 같은 값으로 덮어쓴다. Hero의 값 의미는 바뀌지 않는다.

### 24.3 상태 전환

Enemy Idle/Jog의 현행 기준은 다음과 같다.

- Idle → Jog: `GroundSpeed >= 10 cm/s`
- Jog → Idle: `GroundSpeed <= 5 cm/s`
- 전환 Duration: `0.15~0.25초`
- Blend Mode: Cubic 또는 Ease In/Out 계열

서로 다른 진입·이탈 기준을 사용해 속도가 경계에서 흔들릴 때 State가 빠르게 왕복하지 않게 한다.

Idle 샘플이 포함된 단일 Locomotion Blend Space를 쓴다면 별도 Idle/Jog State를 중복 구성하지 않는 것이 기본 권장이다.

### 24.4 Blend Space

- `Direction`: `-180~180`
- `Ground Speed`: `0~500`. Pursuit 최고속도까지 포함하도록 Blend Space 축을 확장한다.
- 후방 경계가 거칠면 동일 Backward 샘플을 `180`과 `-180` 양쪽에 둔다.
- Blend Space Player의 Loop를 켠다.
- GroundSpeed 축 Smoothing Time은 `0.15~0.25초`에서 시작한다.

## 25. 회전과 바라보기

**현행**

- 포위 범위 밖 Pursuit에서는 `Orient Rotation to Movement`를 켜고 Focus를 지워 이동 방향을 본다.
- Engagement Formation에 들어온 순간부터 그 상태를 벗어날 때까지 `Use Controller Desired Rotation`과 Player Focus를 사용한다.
- InitialCharge, Approach Ring, Align Ring, Attack·Wait·Holding·Pending 이동, Ingress, Slot 감속과 정지까지 같은 회전 정책을 유지한다.
- 플레이어 기준 좌우 이동은 `Direction` 약 `±90°`, 후퇴 이동은 `±180°`로 AnimBP에 전달한다. Mesh는 Player를 바라본 채 게걸음·후퇴 애니메이션을 사용한다.
- 공격 시작 순간 Enemy Actor와 Controller 회전을 타깃 쪽으로 다시 맞춘다.

Animation Preview용 `bWalkLeftForAnimationPreview`는 실제 AI 검증에서 반드시 꺼야 한다. 이 기능이 켜져 있으면 서버가 왼쪽 이동을 직접 넣고 기본 `150 cm/s` Preview 속도로 실제 AI 이동을 방해한다.

### 26.4 게임 실행 중 표시 On/Off

**현행**

PIE 또는 게임 실행 중 콘솔을 열어 다음 명령을 사용할 수 있다.

| 명령 | 결과 |
| --- | --- |
| `bh.Debug.Toggle` | ProjectBH 디버그 표시 전체 On/Off 전환 |
| `bh.Debug.Enabled 0` | 전체 끄기 |
| `bh.Debug.Enabled 1` | 전체 켜기 |
| `bh.Debug.Crowd 0/1` | Enemy 머리 위 상태·이동 경로 끄기/켜기 |
| `bh.Debug.Slots 0/1` | Slot·Ring·Anchor·간격 진단 끄기/켜기 |
| `bh.Debug.Pool 0/1` | Enemy Pool 상태 끄기/켜기 |

- 전체 Master와 개별 항목이 모두 켜져 있어야 표시한다.
- 런타임 명령은 기존 인스턴스별 `Draw Crowd Debug`, `Draw Debug Slots`, `Draw Pool Debug` 설정을 덮어써서 켜지 않는다. 해당 인스턴스 체크가 꺼져 있으면 런타임 항목이 `1`이어도 계속 표시하지 않는다.
- `bh.Debug.Toggle`은 개별 항목 값을 보존한 채 Master만 전환한다.
- 기존 DrawDebug의 짧은 수명 때문에 끈 직후 이미 그려진 선이나 문자열이 약 1초 이내 잠시 남을 수 있다.
- Separate Process 네트워크 PIE에서는 AI와 Slot 디버그를 실제로 그리는 서버 프로세스 콘솔에서 명령을 실행한다.

## 27. Capsule 간격 진단

**현행 디버그 기준**

- 두 Enemy의 Actor Z 차이가 두 Capsule Half Height 중 큰 값 이하이면 같은 수직 층으로 간주한다.
- 같은 층으로 판단한 교전 Enemy끼리 2D 중심 거리를 계산한다.
- 두 Capsule 반지름 합보다 `5 cm` 이상 가까우면 간격 위반으로 기록한다.
- 이 값은 물리 충돌 자체를 해결하는 기능이 아니라 실제 공간 존중 결과를 검증하는 계측이다.

## 28. 검증 시나리오와 합격 조건

### 28.1 진행 순서

```text
4마리 넓은 평지
  → 8마리
  → 12마리
  → 14~29마리 Holding
  → 30마리 이상 Pending
  → 좁은 통로
  → 플레이어 이동과 Reform
  → 경직·사망
  → 인위적 교착
```

앞 단계가 실패하면 다음 단계의 Crowd 수치 튜닝으로 문제를 덮지 않는다.

### 28.2 수별 기대 결과

아래 수는 모든 Slot이 NavMesh에 투영되고 Attack Slot이 공격 거리 조건을 만족하며 Initial 등록이 `0.5초` 이상 끊긴 표준 평지에서의 기대값이다. 이 전제가 깨진 맵에서는 빈 Slot이 남는 것이 규칙 위반이 아닐 수 있으므로 실패 원인을 별도로 기록한다.

- 4마리: `A 4`, 각자 다른 Attack Slot
- 8마리: `A 5 + W 3`
- 12마리: `A 5 + W 7`
- 13마리: `A 5 + W 8`
- 16마리: `A 5 + W 8 + H 3`
- 29마리: `A 5 + W 8 + H 16`
- 30마리 이상: 초과분 `Q`, Open 상태에서는 반경 575 cm부터 분산된 Pending 목적지

### 28.3 필수 합격 조건

- Attack Slot 보유자는 Open에서 최대 5명이다. Pocket은 열린 호의 단일 전열 수용량을 사용하며 현행 기본값에서는 최대 4명이다. Corridor의 정상 상한은 통로 폭에 따라 양쪽 합계 2~5명이다.
- Wait·Holding·Pending Enemy는 공격하지 않는다.
- 예약된 Enemy가 플레이어 본체가 아니라 자신의 Slot으로 이동한다.
- 승격 Enemy는 정지한 외곽 Ring 점유자 사이를 무조건 직선 관통하려 하지 않는다.
- 플레이어 이동으로 목적지가 바뀌어도 이동 가능한 Enemy가 `2.5초`를 넘겨 복구 행동 없이 정지하지 않는다.
- 저속 `2초` 또는 강제 미진행 `4초` 조건을 충족하면 다음 `0.5초` 갱신 안에 교대·반납·재요청 중 하나로 전환한다.
- 경직과 사망은 같은 서버 상태 전환 안에서 Slot을 반납한다.
- 정상 공격과 회복만으로 Attack Slot을 반납하지 않는다.
- 실제 활성 Attack Slot이 비고 자격 있는 Wait Enemy가 있으면 정상 조건으로 즉시 승격하며, Wait 도착만 늦는 경우에도 빈자리 `0.25초` 뒤 fallback 승격을 시도한다.
- Attack Slot이 예약 상태지만 예약자가 `120 cm` 이상 떨어졌고 더 가까운 Wait 후보가 `0.3초` 유지되면 빠른 인계가 발생한다.
- 비활성 Attack Slot은 초록색 빈자리로 그리지 않고 `A` 집계의 분모에도 포함하지 않는다.
- RVO는 꺼져 있고 Detour Crowd만 사용한다.
- Slot 진입 시 실제 Capsule 속도가 계단식으로 바뀌거나, `20 cm` 경계에서 0거리 Move 요청과 강제 정지를 반복하지 않는다.
- Enemy의 Idle/Jog 상태가 순간적인 Acceleration 0 때문에 한 프레임 단위로 왕복하지 않는다.

### 28.4 측정 방식

- Standalone 또는 Listen Server 1인 기준부터 검증한다.
- 각 시나리오는 `30초 × 3회` 반복한다.
- 정지 플레이어, 원형 이동, 통로 통과를 나눠 기록한다.
- 영상은 연출 근거로 남기고 합격 판정은 시간·거리·상태 로그로 확인한다.
- 테스트마다 맵, Enemy 스폰 위치, Player 위치, Enemy/Player Capsule 크기, Nav Agent 설정, Collision Profile, Crowd 설정과 Data Asset 값을 함께 기록한다.
- Slot Component가 출력한 `A/W/H/Q`, Route와 Stuck 문자열은 진단 자료이지 그 자체로 합격 근거가 아니다.
- 같은 시스템이 만든 예약 카운트를 다시 읽어 “예약이 정확하다”고 판정하는 순환 검증을 피한다. 별도 관찰에서 Actor Transform, Capsule 거리, CombatState 전환 시각과 실제 피해 발생 시각을 기록해 디버그 문자열과 대조한다.
- Anchor 색과 Slot 구체는 내부 상태를 그대로 그리는 진단 표시이므로 그 자체를 중앙 복귀의 합격 근거로 삼지 않는다. 평평한 표준 맵에서 Wait 8자리를 모두 채운 뒤 플레이어가 3초 이상 정지했을 때, 실제 Wait Enemy Actor 위치의 2D 중심과 Player Actor 위치가 첫 허용값 `50 cm` 안에 드는지 별도로 확인한다.
- 1차 수동 검증 뒤에는 구현 코드와 별개의 Functional Test 또는 계측 Actor가 같은 조건을 다시 계산하도록 확장한다.

### 28.5 네트워크 검증

- Standalone 기준선이 통과하면 Listen Server 1명과 Client 1명으로 같은 시나리오를 반복한다.
- 서버에서 기록한 Slot 예약·CombatState·공격 시각과 두 화면의 Actor 위치·Montage 표현을 같은 시간축으로 비교한다.
- 클라이언트가 Slot 내부 자료를 직접 결정한다고 가정하지 않는다. 서버 권한 결과가 위치와 복제 상태를 통해 두 화면에서 일관되게 표현되는지를 확인한다.
- 늦은 접속과 최대 4인 검증은 2인 기준선 뒤의 별도 네트워크 마일스톤으로 둔다.

## 29. 현재 구현의 한계

### 29.1 검증이 더 필요한 항목

- 분산형 Ring Ingress 적용 후 8~12마리 실제 PIE 교착 감소량
- Separation을 켠 상태에서 Slot 도착 후 미세 진동 여부
- 좁은 통로에서 양보와 줄서기 품질
- 플레이어가 빠르게 이동할 때 경로 재요청과 Reform의 안정성
- 플레이어 정지 후 Anchor 중앙 복귀, 재이동 취소, 외곽 Ring 대칭 회복
- 가속 기반 Path Following과 `5 cm/s` 도착 확정 적용 후 Capsule 감속·정지 품질
- `bShouldMove` 히스테리시스 적용 후 Idle/Jog 전환 안정성
- 다층 지형에서 Slot 투영과 같은 층 판정

### 29.2 구조적 한계

- NavMesh는 정지한 Enemy Capsule을 반영해 전역 경로를 다시 설계하지 않는다.
- Detour Crowd는 이동 가능한 여유 공간이 없는 병목을 해결할 수 없다.
- 서로 다른 Slot이 같은 NavMesh 지점으로 투영되는 것을 현재 별도로 금지하지 않는다.
- 거리와 Ring 계산 대부분이 2D라 수직으로 겹친 전투 공간에 약하다.
- Pending Enemy는 외곽 목적지로 이동하지만 살아 있는 Character와 Detour Crowd Agent다. Enemy끼리 물리 Block은 하지 않지만 외곽 Ring으로 가는 경로 자체가 좁으면 Detour 조향 병목은 여전히 발생할 수 있다.
- Enemy Capsule은 전용 `EnemyPawn` Object Channel을 사용하고 같은 채널끼리 `Ignore`한다. 따라서 Enemy 간 물리 접촉 교착은 만들지 않는다. Detour Crowd와 Slot 간격이 실패해 시각적 Mesh·Capsule 중첩이 발생하면 20.5의 결정적 양보와 짧은 NavMesh 탈출 이동으로 복구를 시도한다.
- Combat Core는 선택한 직선과 Waypoint를 검사할 뿐 NavMesh에 금지 Area를 만드는 것은 아니다. Recast가 계산한 실제 경로가 Waypoint 사이에서 Core를 자르지 않는다는 보장은 없으므로 PIE에서 실제 궤적을 확인해야 한다.
- 타깃 도달 가능성은 플레이어 중심의 대표 Nav 경로로 검사하며 각 Combat Slot 경로 전체를 미리 검사하지 않는다. 생존·다운·Line of Sight도 아직 후보 조건이 아니다.
- 혼잡 Admission은 경로 주변 Agent 수를 한 명당 고정 패널티로 환산한 근사치다. Detour Crowd의 미래 속도와 실제 양보 결과를 예측하지 않는다.
- 타깃 도달 가능성과 Admission의 동기 Nav 경로 질의는 활성 Enemy·플레이어 수가 크게 늘면 프로파일링이 필요하다.

## 30. 시체 누적형 Enemy Pool

**현행 C++ 구현, 에디터 배치 및 PIE 검증 필요**

### 30.1 수량 분리

- `Pool Capacity`: 미리 생성할 전체 Enemy 수
- `Active Enemy Limit`: 동시에 살아서 AI·전투·Crowd에 참여할 최대 수
- `Corpse`: 사망 연출을 유지하며 월드에 남은 Pool Enemy
- `Free Reserve`: 즉시 활성화할 수 있도록 확보할 비활성 Enemy 수

하나의 Pool Manager가 `Enemy Class`와 선택적인 `Troll Enemy Class`를 함께 관리한다. `Normal Enemies Per Troll`의 기본값은 `10`이며 활성 순서는 `일반 10명 → Troll 1명`을 한 묶음으로 계산한다. 남는 활성 자리는 일반 Enemy로 채우므로 기본 `Active Enemy Limit = 12`에서는 일반 11명과 Troll 1명이 활성화된다.

- `Active Enemy Limit`은 Troll을 포함한 전체 생존 수 상한이고 `Pool Capacity`도 두 클래스의 합계다. Troll이 상한 밖에 추가로 생성되는 방식이 아니다.
- 일반 Enemy가 사망하면 일반 Enemy 재스폰 요청을, Troll이 사망하면 Troll 재스폰 요청을 만든다. Free Reserve와 회수할 시체도 같은 종류에서만 선택하므로 전투 도중 구성 비율이 무너지지 않는다.
- `Troll Enemy Class`가 비어 있으면 기존 단일 일반 Enemy Pool로 동작한다. `Enemy Class`와 같은 클래스를 지정하면 설정 오류로 보고 Troll 혼합 구성을 비활성화한다.

첫 검증값은 다음과 같다.

| 항목 | 값 |
| --- | ---: |
| Pool Capacity | 40 |
| Active Enemy Limit | 12 |
| Respawn Delay | 5초 |
| Minimum Corpse Display | 5초 |

항상 `Pool Capacity = Alive Active + Corpse + Free Reserve`다. 기본값에서 Alive 12를 유지하므로 장기적으로 Free가 고갈된 뒤의 시체 수는 28구를 기준으로 안정된다.

### 30.2 사망 후 상태

- 사망 즉시 Slot과 Queue를 반납하고 AI Controller와 Movement를 제거한다.
- Death Montage를 재생하고 Capsule Collision은 기본 `0.2초` 뒤 끈다.
- 시체는 살아 있는 Enemy 수에 포함하지 않지만 `PoolInWorld = true`인 개체 하나를 계속 점유한다.
- 사망 시 Active가 한 자리 부족해지며 기본 `5초` 뒤 실행 가능한 교체 스폰 요청 하나를 만든다.

### 30.3 회수 조건과 순서

- 교체 요청이 준비되면 Free Reserve를 먼저 한 명 꺼내 Spawn 위치에서 활성화한다. 이 경우 기존 시체는 계속 남는다.
- Free Reserve가 0일 때만 최소 표시시간 `5초`를 지난 시체 중 Death Sequence가 가장 빠른 한 구를 회수한다.
- eligible Corpse가 아직 없으면 최소 표시시간을 깨지 않고 교체 스폰을 미룬다.
- Manager는 기본 `0.25초` Tick마다 최대 한 명만 회수·재활성화한다. 여러 시체가 같은 프레임에 사라지지 않는다.
- 카메라 밖·거리 우선순위는 현재 구현하지 않았으며 첫 버전은 가장 오래된 시체만 사용한다.

### 30.4 재활성화 Reset 계약

1. 기존 Timer, LifeSpan, Attack Target과 공격 Context를 지운다.
2. 이전 Gameplay Effect를 제거한다.
3. Health를 현재 MaxHealth로 복구한다.
4. Combat State를 `Chasing`으로 바꾼다.
5. Death·Attack Montage를 중지한다.
6. Actor와 Mesh Tick, Capsule Collision, Character Movement를 복구한다.
7. Spawn Transform으로 Teleport한다.
8. 새 AI Controller를 생성해 다시 Possess한다.

### 30.5 Spawn 위치

- Manager 인스턴스의 `Spawn Points`에 Level Actor나 Target Point를 등록하면 순환 사용한다.
- `Spawn Points`는 초기 Enemy와 사망 후 보충 Enemy가 등장할 위치를 Level Designer가 통제할 때 사용한다. 등록은 선택 사항이다.
- 명시적으로 등록된 유효 Point가 하나라도 있으면 그 배열을 우선하며 자동 탐색은 하지 않는다.
- 배열이 비어 있고 `Auto Discover Target Points When Empty`가 켜져 있으면 BeginPlay 시 현재 World에 로드된 모든 TargetPoint를 런타임 Object Name순으로 찾아 Spawn Points로 사용한다. 인스턴스 참조 누락의 복구 수단이다.
- 초기 활성 Enemy와 보충 Enemy는 같은 배열을 순환한다. Point 수가 `Active Enemy Limit`보다 적고 `Spread Repeated Spawn Points`가 켜져 있으면 각 Point를 중심으로 `Fallback Spawn Spacing` 간격의 Grid에 분산한다.
- 정확히 Point Transform 하나에만 생성해야 하는 특수 연출에서는 `Spread Repeated Spawn Points`를 끌 수 있지만, 여러 Enemy가 같은 좌표에 겹칠 수 있다.
- 위치는 기본 `X 100, Y 100, Z 300 cm` 범위로 NavMesh에 투영을 시도한다.
- 자동 탐색까지 끝난 뒤에도 유효 TargetPoint가 없으면 Manager 주변에 기본 간격 `175 cm`의 grid를 만든다.
- Pool Storage는 Kill Z와 World Bounds를 피하도록 Manager 근처에 두며 Free Enemy는 Hidden·Collision Off·Tick Off 상태다.

### 30.6 에디터 조건

- `ABHEnemyPoolManager`를 Level에 하나 배치한다.
- `Enemy Class`에 `/Game/Enemy/BP_BHEnemy`를 지정한다.
- `Troll Enemy Class`에 준비한 Troll Blueprint를 지정하고 `Normal Enemies Per Troll`을 `10`으로 둔다.
- Manager가 관리할 전투에서는 별도로 배치한 Enemy를 제거한다. 배치 Enemy는 Pool Capacity와 Active Limit에 포함되지 않는다.
- Spawn Point와 각 Combat Slot까지 이어지는 NavMesh를 확보한다.
- Death Montage 마지막 자세 유지는 AnimBP 또는 Montage 설정에서 별도로 맞춘다.

현재 한계는 다음과 같다.

- 한 Manager는 한 Enemy Class만 관리한다.
- Active Limit을 PIE 중 낮춰도 이미 살아 있는 Enemy를 강제로 비활성화하지 않는다. 다음 사망부터 새 Limit에 맞춘다.
- Material·Dissolve·부위 파괴처럼 Enemy별로 추가한 시각 상태는 아직 Reset 계약에 포함되지 않는다.
- Replication Dormancy와 Replication Graph 최적화는 아직 적용하지 않았다.

## 31. 후속 설계: 벽면 군중 Traversal

**후속 설계 — 현재 미구현**

일반 NavMesh가 없는 벽면 이동은 지상 Crowd 이동과 별도 Traversal 구간으로 취급한다.

### 31.1 진입 구조

- 벽 아래 NavMesh와 위 NavMesh를 Smart Nav Link로 연결한다.
- `ATraversalWallLink`가 Entry, Exit와 등반 Lane을 관리한다.
- 첫 구현은 벽 하나당 Lane 4개로 시작한다.
- Lane 하나에는 동시에 Enemy 한 명만 등반할 수 있다.

### 31.2 예약과 대기

- 서버가 Lane 예약 권한을 가진다.
- 빈 Lane이 있으면 Entry에 도착한 Enemy가 하나를 예약한다.
- 모든 Lane이 차 있으면 Entry 주변의 Traversal Wait Slot에서 기다린다.
- Wait 순서는 중앙 Queue로 관리한다.
- 먼저 대기한 Enemy가 빈 Lane을 우선 예약한다.

### 31.3 등반 이동

1. 지상에서는 현재 NavMesh·Detour Crowd·Slot 이동을 사용한다.
2. Traversal Entry에 도착하면 일반 지상 Move를 정지한다.
3. 예약한 Lane의 시작 위치에 정렬한다.
4. Character Movement를 `MOVE_Custom` 등반 모드로 전환한다.
5. 정해진 벽면 경로를 따라 Exit까지 이동한다.
6. Exit 도착 후 상단 NavMesh에 안전하게 투영한다.
7. Lane을 반납한다.
8. 일반 지상 이동과 대상 플레이어의 Combat Slot 요청을 다시 시작한다.

### 31.4 실패와 반납

- 등반 중 사망·경직·Actor 제거·벽 상태 무효·Exit 투영 실패가 발생하면 Lane을 반드시 반납한다.
- 실패한 Enemy가 Lane을 영구 점유하지 않도록 서버 Fail-safe를 둔다.
- Exit가 막혔으면 아래에서 다음 Enemy를 계속 올려보내지 않는다.
- 등반 중인 Enemy는 지상 Attack·Wait·Holding Slot을 동시에 점유하지 않는다.

## 32. 폐기 또는 보류한 방식

### 32.1 공용 Attack Approach Gate

**폐기**

- Attack Enemy를 소수의 공용 Gate로 모으자 Gate 주변에 이동 수요가 집중됐다.
- 정지 Wait Enemy와 이동 Attack Enemy가 같은 공간에서 병목을 만들었다.
- 실제 PIE에서 끼임이 더 심해져 Gate 전용 코드와 경로 비용을 롤백했다.
- 현재는 Slot 각도별로 분산된 Ring Waypoint를 사용한다.

### 32.2 Detour Crowd와 RVO 병용

**폐기**

- 두 로컬 회피 시스템이 동시에 속도를 수정하는 구성을 사용하지 않는다.
- 현재는 Detour Crowd 하나로 통일한다.

### 32.3 모든 Enemy를 플레이어에게 직접 `MoveToActor`

**항상 사용하는 방식은 폐기, 원거리 Pursuit에만 한정 사용**

- 모든 Enemy를 거리와 역할에 관계없이 Player 한 점으로 보내는 방식은 사용하지 않는다.
- Formation 밖의 Enemy만 Player 속도를 `0.35초` 예측한 위치를 기준으로 Pursuit한다.
- 모든 Enemy가 그 한 점을 공유하지 않는다. Actor 생애 동안 유지되는 고정 Seed로 `3 Lane × 4 Row` 중 하나를 맡고, 기본 간격은 좌우 `120 cm`, 전후 `130 cm`다. 첫 Row는 예측 위치보다 `80 cm` 뒤에 둔다.
- Player가 `80 cm/s` 이상으로 이동하면 이동 방향을 대형 축으로 사용한다. 그보다 느리면 각 Enemy에서 Player를 향하는 기존 접근 방향을 사용하므로, 정지한 Player의 Facing 변화만으로 추격 대형 전체가 군무처럼 회전하지 않는다.
- 방향 축은 갱신마다 `0.35` 비율로 보간해 Player의 급격한 좌우 전환에도 목표가 한 프레임에 반전되지 않게 한다.
- 분산 목표는 NavMesh에 투영한다. 개별 Lane 목표를 투영할 수 없으면 해당 갱신에 한해 예측 중심점으로 복귀한다.
- 이 분산은 순수 Pursuit에만 적용한다. Engagement Formation에 진입한 뒤에는 Attack·Wait·Holding·Pending Slot과 기존 Initial Charge 규칙이 우선한다.
- 타깃 `700 cm` 안에 들어오면 직접 추격을 끝내고 Slot Formation에 참여한다.

### 32.4 Enemy 전용 물리 충돌 분리

**현행, 재도입 후 PIE 검증 필요**

- 이전 전용 Channel 실험은 기본 응답 설정이 지형 충돌까지 흔들어 롤백했다.
- 현재는 `ECC_GameTraceChannel1`을 `EnemyPawn` Object Channel로 명시하고 기본 응답을 `Block`으로 둔다.
- 살아 있는 Enemy Capsule의 Object Type만 `EnemyPawn`으로 바꾸고 `EnemyPawn → EnemyPawn` 응답만 `Ignore`한다.
- Enemy Capsule은 `WorldStatic`, `WorldDynamic`, 일반 `Pawn`을 계속 `Block`한다. 따라서 바닥·벽과 Player Capsule은 통과하지 않는다.
- Hero Capsule도 `EnemyPawn`을 `Block`하므로 Player와 Enemy의 물리적 경계는 유지한다.
- Hero 무기 Object Query는 `Pawn`과 `EnemyPawn`을 함께 검사해 공격 피격이 누락되지 않게 한다.
- 현행 C++의 `Pawn` Object Query는 Hero 무기 Trace 한 곳뿐이며 보완했다. Blueprint Trace·Overlap을 추가할 때는 `EnemyPawn` 포함 여부를 별도로 확인한다.
- 이번 설정은 Character Root Capsule만 대상으로 하며 Skeletal Mesh·무기·보조 Collision Component 응답은 변경하지 않는다.
- Enemy 사이의 실제 간격은 Detour Crowd Obstacle Avoidance, Separation과 Slot 간격이 담당한다. 물리 Block이 마지막 간격 보정 수단으로 개입하지 않는다.
- Crowd 조향이 실패해 Mesh와 Capsule이 관통하면 20.5의 중첩 탈출 복구가 양보 대상을 하나만 정하고 짧게 분리한다. Slot 예약과 Queue Sequence는 이 과정에서 유지한다.
- 이 정책은 중첩을 예방하는 것이 아니라 이미 발생한 중첩을 복구하는 안전망이다. `Spacing`, `Overlap:Escape`와 화면 관찰로 예방 품질과 복구 품질을 각각 검증한다.

### 32.5 NavMesh 대신 자체 A* 전면 구현

**보류**

- 지상 전역 길찾기는 UE NavMesh를 사용한다.
- 포트폴리오의 차별화는 전역 길찾기를 다시 만드는 것보다 Slot, 대기열, Admission, 교착 복구, Traversal 예약과 계측에 둔다.

### 32.6 공격마다 자동 전열 교대

**폐기**

- 공격 후 Attack과 Wait가 기계적으로 자리를 바꾸는 모습이 전투의 무게감과 포위 안정성을 해쳤다.
- 현재는 Attack Slot 지속 점유를 사용한다.
- Troll Charge는 Attack Slot을 교대하지 않는 별도 행동으로 구현한다. 일정 시간 뒤 선택적 교대는 계속 보류한다.

## 36. 전투 공간 분석

**현행: Open·Corridor·Pocket 판정과 대형 연결 및 MouthMixed 구현, PIE 검증 필요**

### 36.1 목적과 책임

- Player가 서 있는 주변 NavMesh를 검사해 넓은 공간 `Open`과 좁은 통로 `Corridor`를 구분한다.
- `UCombatEngagementSlotComponent`가 서버 권한으로 공간 상태 하나를 계산한다.
- Enemy마다 별도로 공간을 판정하지 않는다.
- 판정 결과는 Attack Slot 후보 수·위치, Wait·Holding·Pending Row 형태와 Enemy 이동 목표에 연결된다. Queue의 단일 Sequence 규칙은 공간 모드와 무관하게 유지한다.

### 36.2 표본 규칙

- Player 위치를 NavMesh에 투영한 지점을 분석 원점으로 사용한다.
- 기본 `0.2초`마다 원점에서 `16방향`으로 각각 최대 `500 cm` Navigation Raycast를 실행한다.
- 정반대 방향 두 개의 도달 거리 합을 하나의 축 길이로 본다.
- 가장 긴 축을 통로 축 후보로 선택한다.
- 그 축과 수직인 정반대 탐침 거리 합을 통로 폭으로 추정한다.
- `가장 긴 축 길이 / 추정 폭`을 종횡비로 사용한다.
- Probe Count가 4의 배수가 아니면 런타임에 다음 4의 배수로 올려 수직 축을 항상 구성한다.
- Player 위치가 NavMesh에 투영되지 않으면 새 분석을 `Invalid`로 본다. 단발성 실패는 기본 `0.6초` 유예 동안 마지막 확정 대형을 유지하며, 유예를 넘는 연속 실패에서만 공간 분석과 대형을 해제한다.

### 36.3 상태 전환 규칙

`Open → Corridor` 후보 조건은 다음을 모두 만족해야 한다.

- 추정 폭 `350 cm 이하`
- 가장 긴 축 길이 `600 cm 이상`
- 종횡비 `1.8 이상`
- 위 조건이 연속 `0.5초` 유지

`Corridor → Open` 후보 조건은 다음 중 하나를 만족하면 된다.

- 추정 폭 `450 cm 이상`
- 가장 긴 축 길이 `600 cm 미만`
- 종횡비 `1.4 이하`
- 위 조건이 연속 `1.0초` 유지

진입 폭 `350 cm`와 이탈 폭 `450 cm`, 진입 종횡비 `1.8`과 이탈 종횡비 `1.4` 사이를 히스테리시스 구간으로 둔다. 경계에서 표본 하나가 흔들리는 것만으로 상태를 왕복하지 않는다.

### 36.4 공개 결과

- `Get Combat Space Mode`: 마지막으로 확정된 `Open` 또는 `Corridor`
- `Has Valid Combat Space Analysis`: 최근 NavMesh 표본이 유효한지 여부
- `Get Estimated Corridor Width`: 수직 탐침으로 추정한 통로 폭
- `Get Estimated Corridor Axis`: 가장 긴 통과 가능 축의 월드 수평 방향

분석은 현재 서버에서만 갱신된다. 클라이언트 표현에서 직접 이 값을 사용하려면 추후 복제 정책을 별도로 정한다.

### 36.5 디버그 표시

- 기존 `bh.Debug.Slots 1`과 Component의 `Draw Debug Slots`가 모두 켜져 있을 때 표시한다.
- 가는 녹색 탐침은 최대 거리까지 통과 가능한 방향이다.
- 가는 적갈색 탐침은 NavMesh 경계에 막힌 방향이다.
- 굵은 청록색 선은 선택된 통로 축이다.
- 굵은 노란색 선은 추정 통로 폭이다.
- Player 위 문자열에 확정 상태, 현재 후보, 후보 누적시간, 폭, 축 길이, 종횡비를 표시한다.

### 36.6 다음 단계 연결 전 합격 조건

- 넓은 평지 중앙에서 `Open`을 유지한다.
- 기준 통로 안으로 들어간 뒤 약 `0.5초` 후 `Corridor`로 확정된다.
- 통로 경계에서 상태가 프레임 단위로 왕복하지 않는다.
- 넓은 장소로 나온 뒤 약 `1.0초` 후 `Open`으로 복귀한다.
- 대각선 통로에서도 청록색 축이 실제 통로 진행 방향과 대체로 일치한다.
- NavMesh 바깥에서는 `Invalid NavMesh sample`을 표시하고 오류나 Slot 재배치를 일으키지 않는다.

### 36.7 Corridor 선형 추격 대형

**현행 C++ 구현, PIE 검증 필요**

- 유효한 `Corridor` 상태에서는 기존 원형 Attack·Wait·Holding·Pending 배치를 통로 축 양쪽의 선형 추격 대형으로 전환한다.
- 통로 진입 순간 중앙 Queue에 등록된 각 Enemy를 Player 기준 축의 어느 쪽에 있는지 판정해 `Side 0` 또는 `Side 1`을 고정한다.
- 축의 부호는 Enemy가 더 많이 몰린 쪽을 `Side 0`으로 정하기 위한 기준일 뿐, 반대편 `Side 1`에도 동일한 대형을 만든다.
- Corridor 상태가 유지되는 동안 축의 부호를 잠근다. 분석 축이 회전해도 Side가 180도 뒤집히지 않고 같은 방향으로 완만하게 추종한다.
- 기본 축 추종 보간값은 `0.35`이며, 마지막 경로 통지 방향에서 `15도` 이상 달라지면 모든 예약 Enemy에게 새 목적지를 통지한다.
- Attack은 Player가 통로 끝이나 벽에 접근할 때 대응하도록 Side별 Nav 유효 수용량을 계속 갱신한다. Wait·Holding·Pending은 Corridor 진입 폭을 고정해 쓰지 않고 각 Row의 실제 NavMesh 횡단 폭으로 Lane 수를 계산한다.

#### Corridor Mouth와 축 안정화

**현행 C++ 동작**

- 단일 방사형 탐침만으로 Corridor 출구를 판단하지 않는다. 현재 단면과 함께 확정된 Corridor 대형 축 기준 전방·후방 `250 cm` 위치의 횡단면을 추가 측정한다. Player 시선 방향은 사용하지 않는다.
- 추가 단면은 중심에서 좌우로 각각 최대 `350 cm`까지 Navigation Raycast하고, 두 도달 거리의 합을 단면 폭으로 사용한다. 따라서 측정 가능한 최대 총폭은 `700 cm`다.
- 전방과 후방 단면을 독립 판정한다. 유효한 단면이 폭 최소 `500 cm`이면서 좁은 기준 폭의 `1.4배` 이상이면 해당 방향의 `Corridor Mouth` Raw 증거가 된다. 두 폭 조건은 모두 만족해야 한다.
- Player 주변 단면이나 반대쪽 표본 중 적어도 하나가 좁아야 Mouth로 인정한다. Player 주변과 전후 단면이 모두 넓은 일반 Open에서는 Mouth를 유지하지 않는다.
- 이미 Corridor인 동안 Mouth 단면은 새 방사형 축이 아니라 현재 확정된 대형 축을 사용한다. 따라서 넓은 공간을 향한 대각선 탐침이 Mouth 검출 축 자체를 돌리지 못한다.
- 전방·후방 증거는 각각 기본 `0.5초` 동안 유지한다. 공간 분석 주기 `0.2초`에서 한 표본이 누락되어도 다른 방향으로 즉시 뒤집지 않는다.
- 방향별 Mouth `Raw` 증거가 `0.3초` 연속 유지되면 최상위 모드를 Open/Pocket으로 바꾸지 않고 Corridor 내부 Layout 하위 상태 `MouthMixed`에 진입한다. `Held`는 진입 근거가 아니라 이탈 유예에만 사용한다.
- Mouth 증거가 사라지면 MouthMixed를 해제하고 일반 Corridor/Open/Pocket 후보 판정으로 돌아간다. 공간 모드 자체의 기존 히스테리시스는 유지한다.
- 디버그는 `Mouth F:Raw/Held/No 폭 R:Raw/Held/No 폭 Mixed:상태`로 표시한다. 각 횡단면은 평소 하늘색, Raw는 빨간색, Held는 주황색이다.

#### Corridor Mouth 양면 균형 대형

**현행 C++ 구현, PIE 검증 필요**

- `Mouth`는 Enemy를 열린 공간 쪽으로 모으는 목적지가 아니라, 통로 단면이 넓어지는 위치를 나타내는 공간 분석 정보다.
- Mouth 증거가 `0.3초` 유지되면 공간 모드 전체를 바꾸는 대신 Corridor 내부 Layout 하위 상태 `MouthMixed`에 진입한다.
- Player가 긴 Corridor의 Mouth 앞에 서더라도 통로 안쪽과 열린 공간 쪽에 각각 하나의 전선을 유지한다. 대형 전체를 Mouth 또는 열린 공간 한쪽으로 전환하지 않는다.
- 전방·후방 Mouth의 Raw/Held 판정과 횡단면 중심을 독립 저장한다. 단일 Mouth에서는 임계값을 통과한 축 방향을 `Open Side`, 반대 방향을 `Corridor Side`로 확정한다. 활성 종류와 다른 `Raw` 종류가 기본 `0.6초` 연속 유지될 때만 Side0·Side1·Double 사이를 전환해 작은 표본 변화로 월드 Side 정체성이 뒤집히지 않게 한다.
- Attack은 Player를 원점으로 유지한다. Wait·Holding·Pending은 기존 지연 추종 `Engagement Anchor`를 공통 원점으로 사용한다.
- 통로 안쪽 Side는 Engagement Anchor에서 Corridor 안쪽 축 방향으로 기존 동적 Row를 만든다. 열린 공간 Side는 Engagement Anchor에서 Open Side 방향을 중심으로 기존 Pocket의 최대 반각 `80도` 부채꼴 Row 생성기를 재사용하되, Open Side 반평면을 넘지 않게 자른다. 서로 형태는 달라도 동일한 중앙 Queue의 양쪽 Side로 취급한다.
- 양쪽이 모두 이동 가능하면 각 계층의 Slot 수는 Side별 차이가 최대 `1개`가 되도록 생성한다. 실제 Enemy 점유 수는 각 Enemy가 현재 위치한 Side의 수요를 따르며, 반대편 Slot을 채우기 위해 강제 균등 배정하지 않는다.
- 기본 목표는 Attack `3:2`, Wait `4:4`, Holding `8:8`이며 Pending도 `floor(N/2) : ceil(N/2)`로 나눈다. MouthMixed의 Attack 후보 조합은 `활성 수 최대 → Side 수 차이 최소 → Corridor 축 정렬도 최대 → 기존 Sample 유지 최대` 순으로 선택한다. Attack의 홀수 한 칸은 기존 Sample 유지 기준으로 작은 Player 이동 중 같은 월드 Side를 우선 보존한다.
- 열린 공간 Side의 수용량이 더 크더라도 통로 Side의 목표 몫을 먼저 확보한다. 한쪽의 유효 후보가 실제 목표보다 부족할 때만 부족분을 반대 Side로 넘긴다.
- Attack 및 Wait·Holding의 새 후보 토폴로지가 한쪽 부족을 나타내더라도 기존 Layout이 있다면 각각의 확정 대기 동안 같은 결과가 유지된 뒤에만 Spillover를 확정한다. Pending은 예약 Layout을 갖지 않으므로 Side별 Pending Sequence 순위를 기준으로 요청 시 생성하고 자기 Side의 안쪽 Row부터 채운다. 일시적인 Player Nav 투영 실패는 기본 `0.6초` 동안 마지막 정상 양면 Layout을 유지한다.
- Player가 Mouth를 통과해 완전히 Open으로 진입하거나 Corridor 안쪽으로 충분히 복귀하면 해당 공간 모드의 일반 대형으로 전환한다. Mouth 경계에 머무는 동안은 이 혼합 대형을 유지한다.
- 짧은 통로 양끝이 모두 Mouth인 Connector에서는 확정된 Corridor 축의 양방향을 `Exit A / Exit B` 방향으로 고정하고, 공통 Engagement Anchor 원점에서 양쪽 Fan을 만들어 같은 균형 규칙을 적용한다.
- 디버그의 두 방향 화살표는 Corridor Row Side를 보라색, Fan Side를 주황색으로 표시한다. 첫 문자열의 `Mixed / Next / 시간`은 현재 확정 종류와 전환 후보 및 누적시간이다. 두 번째 문자열은 Wait·Holding의 `Layout`, Attack·Wait·Holding의 실제 `Assigned`, 예약 전 Queue의 `TargetQ`, 각 목표 반경 안의 `NearTarget` 수를 표시한다.
- 검증은 내부 카운터만 읽지 않는다. 긴 단일 Mouth와 짧은 Double Mouth에서 실제 Enemy Actor 위치를 고정된 월드 Side 평면으로 다시 분류하고, 양쪽이 유효한 동안 각 계층의 `Assigned`와 도착 후 `NearTarget` 차이가 최대 `1명`인지 영상 시점과 함께 대조한다.

#### Corridor 변의 Pocket 전환

- Corridor 상태에서는 16개 탐침의 모든 반대 방향 쌍을 비교한다. 각 쌍의 가까운 경계 거리와 `반대쪽 거리 - 가까운 거리`를 계산하고, 거리 차이가 가장 큰 쌍을 현재 변 후보로 사용한다.
- 가까운 경계가 `100 cm 이하`이고 반대쪽 여유가 `100 cm 이상 더 크면` Player가 통로 변이나 끝에 치우친 것으로 보고 `Pocket` 후보로 전환한다.
- 폭 `450 cm 미만`, 긴 축 `600 cm 이상`, 종횡비 `1.4 초과` 같은 Corridor 형태 조건은 변 판정의 선행 조건으로 사용하지 않는다. 따라서 반대쪽이 크게 열린 변이나 긴 축 끝에서도 전환할 수 있다.
- 이미 이 규칙으로 Pocket에 들어왔다면 가까운 경계 `130 cm 이하`, 반대쪽 여유 차이 `60 cm 이상`의 완화된 조건을 사용한다.
- 양쪽 경계가 모두 비슷하게 가까운 좁은 통로 중앙은 거리 차이 조건을 만족하지 않으므로 Corridor를 유지한다.
- Pocket 진입에는 기존 `0.4초`, 이탈에는 기존 `0.6초`의 연속 판정 시간이 적용된다.
- 디버그 공간 문자열의 `Edge:가까운 거리/+반대쪽 여유 차이`로 현재 판정값을 확인한다.

#### Attack 전열

- Attack Slot은 Player 중심의 동일한 `Attack Ring Radius` 전체를 `16개` 방향으로 균등 샘플링한다. 고정된 두 원호 조합은 더 이상 사용하지 않는다.
- 모든 Attack Slot은 기존 공격 시작 거리 규칙을 계속 만족한다.
- 각 후보는 NavMesh 투영, 투영 오차 `35 cm 이하`, 투영된 Player 중심에서 후보까지의 직접 Navigation Raycast, 후보 중심 주변 `8방향 × 45 cm` 벽 여유를 모두 통과해야 한다.
- 유효 후보 중 서로 `90 cm` 이상 떨어진 조합만 허용하며 전체 Attack Slot 상한 `5개`까지 선택한다.
- 조합 선택 우선순위는 `활성 수 최대 → Corridor 축 정렬도 최대 → 양쪽 수 차이 최소 → 기존 Sample 유지 최대`다. 따라서 통로 중앙에서는 축 앞뒤가 우선되지만, 측면이나 후방에 실제 공간이 열리면 그 방향 후보도 선택될 수 있다.
- 초기 Attack 배정과 전열 재편은 Enemy 위치에서 후보까지 완전한 Nav 경로가 존재하는 경우만 허용한다. Wait 승격도 기존 도착·Cooldown 조건과 함께 완전한 Nav 경로를 검사한다.
- 폭이나 Nav 유효성 때문에 비활성화된 Attack 예약자는 Wait, Holding, Pending 순서로 내려가며 기존 중앙 Queue 순서를 잃지 않는다.
- 새 Sample 조합은 `0.3초` 동안 같은 결과가 유지돼야 실제 예약에 반영한다. 조합이 같으면 월드 좌표만 갱신하고 Slot Index는 유지한다. Nav 시스템 또는 Player 원점 투영 조회 자체가 일시적으로 실패하면 마지막으로 확정한 배치를 유지한다.
- 공격 또는 회복 중인 Enemy가 한 명이라도 있으면 Attack 후보 조합 전체를 잠근다. 해당 Enemy는 기존 Slot Index를 우선 보존하며, 모든 공격·회복 잠금이 끝난 뒤 새 후보 조합을 반영한다.

#### Wait·Holding·Pending 종대

- `Side 0`은 `CorridorFormationRearDirection` 방향, `Side 1`은 그 반대 방향이다. 여기서 양쪽은 Corridor 축의 앞뒤이며 한 Row 안의 횡방향 Lane 좌우와 다른 개념이다. 축 부호는 Corridor 상태 동안 유지한다.
- Player에서 Corridor 축의 양쪽 방향으로 거리별 Row를 만든다. 각 Row 중심에서 축에 수직인 양쪽 NavMesh 경계까지 최대 `350 cm`씩 횡단면을 측정한다.
- 각 Row는 양쪽 경계에서 Enemy 보수 반경 `45 cm`를 제외한 폭을 사용한다. Lane 수는 `floor(사용 가능 폭 / 95) + 1`이며 Row마다 독립적으로 `1~4`개를 허용한다.
- 같은 Row의 Lane 중심 간격은 `95 cm`이고 사용 가능 횡단면 중앙에 정렬한다. 투영 전후 차이가 `35 cm`를 넘는 후보는 해당 Row에서 제외한다.
- 다음 Row까지 종방향 간격은 `100 cm`다. Attack, Wait, Holding, Pending 계층 사이에는 기본 `100 cm` 간격을 둔다.
- Wait `8개`를 안쪽 Row부터 만든 뒤 마지막 Wait Row 바깥에서 Holding `16개`를 만들고, Pending은 마지막 Holding Row 바깥에서 같은 규칙으로 계속 생성한다.
- 각 계층은 양쪽 Side 후보를 따로 수집한다. 양쪽 수용량이 충분하면 Wait는 `4:4`, Holding은 `8:8`, Pending은 요청 수의 절반씩을 우선 확보한다.
- 가까운 한쪽만으로 계층 전체 수가 차더라도 그 총 수용량을 처음 달성한 Row 다음부터 기본 `6개` Row를 추가 검사해 반대쪽 유효 공간을 찾는다. 반대쪽 수용량이 목표보다 적을 때만 부족분을 유효한 쪽으로 넘긴다.
- 각 Side 안에서는 가까운 Row와 중앙 Lane을 먼저 선택한다. Slot 배열 자체는 양쪽 Side를 교대로 보관하지만 Enemy는 자기 Side의 Slot만 점유한다.
- Wait·Holding 예약은 고정 Lane 채널을 사용하지 않는다. 공통 Queue Sequence는 동점과 Attack 승격 우선권용으로 유지하며, 같은 Side 안에서는 현재 위치에서 Slot까지의 이동 거리가 가장 작은 조합으로 재배치한다. 자기 Side 수용량이 가득 찬 Enemy는 반대편 빈 Slot으로 넘어가지 않고 다음 외곽 계층 또는 Pending에 남는다. 제한형 Reform도 같은 Side 안에서만 소유자를 교환한다.
- Row의 Lane 수나 유효 Lane 조합이 달라지는 구조 변화는 같은 결과가 `0.35초` 유지된 뒤 확정한다. 구조가 같으면 실제 월드 좌표만 갱신하고 Slot Index는 유지한다.
- 양쪽 후보를 합쳐도 계층의 전체 필요 수보다 적으면 불완전한 새 Layout을 확정하지 않고 마지막으로 확정한 Layout을 유지한다.
- Corridor Slot으로 이동할 때 원형 Ring 경유와 Orbit은 사용하지 않는다. 이미 통로 축에 정렬된 직접 목적지로 NavMesh 경로를 요청한다.

#### Formation 이탈 반경

- 좁은 통로에서 16개 Holding을 종대로 놓으면 뒤쪽 Slot이 기존 `900 cm`보다 멀어질 수 있다.
- 각 AI는 현재 예약 Slot의 Player 거리와 `150 cm` 여유를 기존 Engagement Exit Radius와 비교해 더 큰 값을 임시 이탈 반경으로 사용한다.
- 예약이 없는 Enemy의 진입·이탈 기준은 기존 `700 / 900 cm`를 유지한다.

#### 디버그

- `bh.Debug.Slots 1`에서 두 보라색 화살표가 Corridor 대형의 양쪽 Side를 가리킨다.
- 공간 문자열의 `AttackCand:유효/전체`, `Selected`, `ActiveA`, `Side 0/Side 1`로 360도 후보 검사 결과와 확정 전열을 확인한다. `AttackLanes`는 기존 Queue 채널 선호 Lane 수, `RowLanes`는 현재 Wait·Holding Row에서 측정된 최대 실제 Lane 수다. `RowSides W:A/B H:C/D`는 점유 Enemy 수가 아니라 생성된 동적 Row Slot 수다. 기본 전체 수가 유효하면 `W:4/4 H:8/8`이다.
- Enemy 머리 위에는 `Side`와 `Lane`이 따로 표시된다.
- Attack 후보 중 탈락 후보는 어두운 빨강, 유효하지만 미선택 후보는 흰색 작은 구체다. 선택 후보는 기존 Attack Slot 색상인 빈 Slot 초록, `0.25초` 이상 빈 fallback 대상 주황, Corridor에서 같은 Side 후보가 없어 의도적으로 보류한 Slot 밝은 파랑, 점유 Slot 빨강으로 표시된다.
- Corridor Combat Core의 동적 우회 Ring은 얇은 보라색 원으로 표시한다. Enemy의 선택 Move Goal 선은 양의 회전이 자홍색, 음의 회전이 보라색이다.

#### 동적 Side 전환과 Combat Core 우회

- Corridor Side는 Attack·Wait·Holding·Pending 배정의 금지 조건이다. Lane은 같은 Side 안에서 안쪽과 중앙을 고르는 정렬 정보다.
- 초기 Attack 배정은 Queue Sequence가 빠른 도달 가능 Enemy 중 해당 Attack Slot과 같은 Side인 Enemy만 선택하고, 같은 Side 안에서는 기존 채널과 경로 점수를 비교한다.
- Wait 승격은 같은 Side에서 도착·Cooldown·완전 경로 조건을 만족하는 후보만 찾는다. 활성 Attack 빈자리가 `0.25초` 이상 유지되면 같은 Side 조건을 유지한 채 Wait 도착 조건만 면제한다. 반대 Side fallback은 없다.
- 전열 재편, 직접 Attack 예약과 교착 교대도 같은 Side 안에서만 수행한다. 단, 이미 공격 또는 회복 잠금 중인 Attack Owner는 Montage 안정성을 위해 기존 Slot을 우선 보존한다.
- Side 판정은 Player 중심의 Corridor 축 오프셋을 사용한다. 중심에서 `60 cm` 이상 떨어진 Enemy는 현재 실제 위치의 Side가 기존 기록보다 우선한다. 따라서 반대편에 스폰됐거나 외부 우회 경로로 이미 넘어간 Enemy는 그쪽 Slot을 점유할 수 있다. `60 cm` 안에서는 등록 시 Side를 유지해 중심 부근 떨림으로 Side가 왕복하지 않게 한다.
- Enemy에서 예약 Slot까지의 2D 직선이 Player 중심 `Combat Core Radius`를 가로지르면 직접 이동하지 않는다.
- 우회 반경은 `Combat Core + 45 cm`, `Attack Ring + 35 cm` 중 큰 값이다. 기본값에서는 `160 cm`다.
- Enemy는 먼저 현재 방사 방향의 우회 Ring에 정렬한다. 이후 매 단계 최대 `45도`씩 양의 회전과 음의 회전 waypoint를 생성한다.
- waypoint는 NavMesh 투영 오차 `35 cm 이하`, 현재 위치에서 waypoint까지의 비Partial 완전 경로, waypoint에서 최종 Slot까지의 비Partial 완전 경로를 모두 만족해야 한다. 실제 현재 위치→waypoint Nav 경로를 구성하는 모든 선분도 Combat Core를 침범하면 안 된다.
- 양방향이 모두 유효하면 두 경로 길이, 경로 주변 혼잡 패널티, 남은 원호 길이의 합이 낮은 방향을 선택한다. 동점은 Queue Sequence 홀짝으로 분산한다.
- 회전 방향을 선택한 뒤에는 `BypassCorePositive` 또는 `BypassCoreNegative` Route Stage로 잠근다. 현재 방향의 다음 waypoint가 무효가 된 경우에만 반대 방향을 다시 검사한다.
- 우회를 시작한 뒤에는 최종 Slot 방향과의 각도 차이가 `10도 이하`이고 실제 Nav 경로의 모든 선분이 Combat Core를 피할 때만 `Direct`로 전환한다. 고정 Gate Actor는 사용하지 않는다.

#### 현재 한계

- 동적 Row는 각 횡단면의 유효 후보를 만들지만 서로 다른 Row가 굽은 지형에서 같은 NavMesh 위치로 수렴하는 경우까지 전역 중복 검사하지는 않는다.
- 동적 Combat Core 우회는 Corridor에만 적용한다. Pocket은 열린 부채꼴 직접 접근 정책을 유지한다.
- 우회 waypoint의 Nav 경로는 AI 갱신 주기에 동기 조회한다. 12마리 검증에서 비용과 경로 재요청 빈도를 함께 확인해야 한다.

### 36.8 Corridor Lane Queue

**동적 Row Queue로 교체됨, PIE 검증 필요**

#### 양측 균형 조밀 배치

- Corridor의 Wait·Holding·Pending에는 영구 Lane 소유권이 없다. Queue Sequence는 Hero별 하나를 유지하지만 예약 후보는 Side별로 분리한다.
- 각 계층은 먼저 양쪽 Side의 목표 수를 절반씩 확보한다. 한쪽이 부족할 때만 남은 수를 반대쪽으로 넘긴 뒤, 각 Side 안에서 `Player에 가까운 Row → 같은 Row 중앙 Lane` 순서로 고른 Slot을 양쪽 교대로 하나의 배열에 펼친다.
- 최초 예약과 구멍 압축에서는 각 Side 안의 Enemy-Slot 이동 거리가 가장 작은 조합부터 배치한다. 그 결과 가까운 Enemy는 가까운 Wait를 받고, 더 먼 Enemy는 남은 방향의 바깥 Slot을 받는다. 한 Side가 가득 차도 반대 Side 빈 Slot로 넘기지 않는다. Queue Sequence는 이동 비용 동점과 Attack 승격 우선권에 사용한다.
- Pending 순번은 같은 Hero Queue 중 동일 Side에 있는 앞선 미예약 Sequence 수로 계산한다. 양쪽 Pending Slot은 계속 생성되지만 실제 Enemy는 자기 Side의 Slot만 목표로 한다.

#### Attack 승격

- 빈 Attack Slot은 우선 해당 Attack Side와 같은 축 방향에 실제로 놓인 Wait Slot을 후보로 본다.
- 정상 후보는 자기 Wait Slot의 `Promotion Arrival Radius` 안에 도착했고 Attack 재진입 Cooldown이 끝났으며 Attack Slot까지 완전한 Nav 경로가 있어야 한다. 활성 Attack 빈자리가 `0.25초` 이상 유지된 경우에는 도착 반경만 면제한다.
- 같은 Side의 유효 후보가 여러 명이면 Queue Sequence가 가장 빠른 Enemy를 선택한다. Wait의 고정 Lane 일치 여부는 더 이상 조건이 아니다.
- 같은 Side 후보가 없으면 해당 Attack Slot은 비워 둔다. 정상 검사에서는 도착한 Enemy만, `0.25초` fallback 검사에서는 도착 여부와 무관하게 보되 Side 조건은 절대 면제하지 않는다.

#### 외곽 승격

- 빈 Wait가 있으면 같은 Side의 Holding·Pending 전체에서 해당 Wait까지 완전한 경로 비용이 가장 낮은 Enemy를 직접 배정한다. Holding 도착을 기다리지 않는다.
- 빈 Holding이 있으면 같은 Side Pending과 Holding Slot 조합 중 완전한 경로 비용이 가장 낮은 조합을 배정한다.
- 경로 비용이 `1 cm` 이내로 같을 때만 Queue Sequence가 빠른 Enemy를 우선한다.
- Row 토폴로지가 변해 재배치할 때도 같은 Side 안에서 남은 이동 거리를 최소화한다. 역할을 바꾸지 않는 단순 재배치는 기존 Reform 최소 절감 기준을 따른다.

#### 사망·경직·교착 복구

- 사망과 Queue 이탈은 해당 예약과 Queue Sequence를 제거한다.
- 경직 후 재등록되는 Enemy는 새 Queue Sequence를 받아 해당 시점의 후방으로 들어간다.
- 실패 복구를 위해 Queue 위치를 보존한 Enemy는 기존 Sequence를 유지하지만 동적 Row의 Lane Index는 재압축 결과에 따라 달라질 수 있다.
- Attack 교착 교대도 같은 Side 후보만 사용한다. 후보가 없으면 반대 Side Enemy를 끌어오지 않고 기존 실패 Slot Cooldown 및 재예약 복구로 내려간다.
- Attack·Wait·Holding 예약이 해제되거나 유효하지 않은 Actor가 정리되면 같은 서버 Tick 흐름에서 Wait와 Holding을 다시 조밀하게 배치하고 Formation Revision을 증가시킨다.
- 공격·회복 잠금 중인 Enemy는 공간 전환 때문에 강제 중단하지 않는다. 잠금이 끝난 뒤 목표 Attack 수와 Side 규칙에 맞춰 강등한다.

### 36.9 Pocket 공간과 부채꼴 대형

**현행 C++ 구현, PIE 검증 필요**

#### 공간 판정

- `Pocket`은 플레이어 가까이에 벽 또는 구석이 있으면서, 반대쪽에 넓고 연속된 이동 가능 호가 있는 상태다.
- 기본 `16방향` NavMesh 탐침 중 `200 cm` 안에서 막힌 탐침 비율과 `350 cm` 이상 열린 탐침의 최장 연속 호를 함께 계산한다.
- 진입 기준은 가까운 벽 비율 `0.2` 이상, 연속 열린 호 `90도` 이상이다.
- 유지 기준은 벽 비율 `0.1` 이상, 열린 호 `67.5도` 이상으로 낮춰 경계 진동을 방지한다.
- 진입 증거는 `0.4초`, 이탈 증거는 `0.6초` 연속되어야 상태를 바꾼다.
- 양쪽 벽 사이에서 전후 방향만 길게 열린 공간은 연속 열린 호가 부족하므로 기존 `Corridor`로 유지한다.

#### 슬롯 배치

- Pocket의 기준 방향은 가장 긴 연속 열린 호의 중앙 방향이다.
- Attack·Wait·Holding·Pending을 이 방향 중심의 최대 반각 `80도` 부채꼴에 배치한다.
- 같은 반경의 호에는 중심 간격 `95 cm`를 만족하는 수만 놓는다.
- Wait·Holding·Pending이 한 호에 전부 들어가지 않으면 `100 cm` 바깥의 다음 방사형 Row로 넘긴다.
- Attack은 공격 거리 계약을 지키기 위해 항상 `125 cm`의 첫 Row만 사용하며 두 번째 Row로 넘기지 않는다.
- Pocket의 활성 Attack 수는 감지된 열린 호와 `95 cm` 중심 간격으로 첫 Row에 실제 배치 가능한 수를 계산한다. 전체 시스템 상한은 5개지만 기본 최대 반각 `80도`에서는 정상 수용량이 최대 4개다.
- Attack은 Player 현재 위치, Wait·Holding·Pending은 Engagement Anchor를 중심으로 한다.
- 후보 목적지까지 Navigation Raycast가 막히면 같은 Row에서 중앙 방향으로 각도를 줄여 유효한 위치를 찾는다.
- Pocket의 기본은 열린 방향의 계산된 목적지로 직접 NavMesh 경로를 요청한다. 단, 직접 경로가 도착한 Slot 점유자의 Capsule 통로를 관통할 때만 열린 바깥쪽 우회 Ring을 사용한다. 막힌 벽 쪽으로 전체 원을 도는 방식은 사용하지 않는다.
- Pocket Slot 배정은 Nav 경로 길이에 Slot 주변의 `8방향 × 180 cm` Clearance 패널티를 더한다. 코너에 가까운 Slot보다 열린 공간 쪽 Slot을 먼저 채워, 선두가 코너 입구를 일찍 봉쇄하는 상황을 줄인다.

#### Queue와 공격 권한

- Pocket은 좁은 통로의 종대가 아니므로 Corridor Lane 소유권과 같은 Lane 선두 규칙을 사용하지 않는다.
- 중앙 Queue Sequence, 도착 조건, 공격 재진입 Cooldown, 경로 유효성, 사망·경직 반납 규칙은 그대로 유지한다.
- Attack Slot은 최대 `5개`지만 현재 열린 호가 수용하는 수만 활성화한다. 디버그의 `A` 분모와 `ActiveA`도 이 동적 활성 수를 표시한다.
- 공간 전환 순간 공격·회복 중인 Enemy 수가 계산된 수용량보다 많으면 해당 잠금 수만큼 임시 활성 수를 유지하고, 잠금 종료 후 목표 수용량으로 축소한다.
- 새 활성 전열 전체의 NavMesh 투영이 성공하기 전에는 기존 Attack 예약과 활성 수를 변경하지 않는다.
- `Corridor ↔ Pocket ↔ Open` 전환은 공격·회복 중인 Montage를 강제로 중단하지 않는다.

#### 디버그

- `bh.Debug.Slots 1`에서 Pocket의 열린 방향을 주황색 화살표로 표시한다.
- 공간 문자열의 `PocketArc`는 감지된 최장 연속 열린 각도, `Wall`은 가까운 벽 탐침 비율이다.
- 상태 문자열은 `Open`, `Corridor`, `Pocket`을 구분한다.

#### Open 밀도 조정

- Open 기본 반경은 Attack `125 cm`, Wait `250 cm`, Holding `400 cm`, Pending `575 cm`다.
- 이전 `125 / 300 / 500 / 700 cm`보다 외곽 대기열을 안쪽으로 모아 포위 압박감을 강화한다.
- Attack 반경은 공격 거리 계약과 Corridor 전열 계산에 연결되어 있으므로 변경하지 않는다.

### 36.10 출구 통행 우선 단계

- `Corridor → Open`, `Corridor → Pocket`, `Pocket → Open`이 확정되면 출구 뒤에 남은 Enemy를 하나의 통행 그룹으로 포착하고, 최종 Slot보다 `ExitDecompression` 중간 경로를 먼저 사용한다. 짧은 Open/Pocket 분류 변화로 단계를 취소하지 않으며 Corridor로 실제 복귀했을 때만 즉시 취소한다.
- 출구 판정 순간의 Player 이동 방향과 출구 기준점을 고정한다. 이후 Player가 방향을 틀어도 중간 목표는 따라 회전하지 않으므로, 출구에서 전원이 동시에 서로 다른 Slot 쪽으로 꺾이는 군무와 교차 병목을 막는다.
- 최근 `1.5초` 안에 Player가 `80 cm/s` 이상으로 이동했다면 그 방향을 출구 축으로 사용한다. 기록이 없으면 Corridor는 기존 대형의 반대 진행 방향, Pocket은 열린 방향, 마지막으로 Player Forward를 순서대로 사용한다.
- 출구 평면은 전환 시점 Player 위치보다 진행 방향 반대로 `200 cm` 떨어진 곳에 고정한다. 이는 공간 모드가 바뀔 때 Player가 이미 입구를 일부 통과했다는 지연을 보정한다.
- 단계 시작 시 Queue Sequence 순으로 고정 Fan 순번을 부여하고 기본 `3개 Lane × 4개 Row`를 나눈다. Lane은 중앙, 왼쪽, 오른쪽 순서로 채우고 간격은 `110 cm`, Row 간격은 `100 cm`다. 12명을 넘으면 같은 목표를 재사용하지 않고 좌우 바깥 Lane을 교대로 추가한다. 기본 중간 목표는 출구 평면에서 `320 cm` 앞이며, 목표가 NavMesh 밖이거나 완전 경로를 만들 수 없으면 같은 Row의 중앙 Lane을 시도한다.
- 출구 평면부터 기본 `320 cm` 전방까지 중심축 좌우 `90 cm`는 임시 **No-Parking Lane**이다. 한 줄 통행 폭만 비우므로 축 옆의 Attack Slot은 계속 사용할 수 있다. 단계가 활성화된 동안 이 구역 안의 빈 Attack·Wait·Holding Slot에는 새 예약을 주지 않는다. 이미 가진 Slot과 Queue Sequence는 반납시키지 않고 이동 목표만 Fan으로 덮어쓴다.
- Attack Slot 점유자와 Large Enemy도 예외 없이 출구 통행 그룹에 참여한다. 기존 Attack 예약과 Large 우선권은 보존하며, Large 강제 우선 정책은 이 단계에서도 Attack 예약만 선점할 수 있다. 단, 실제 Slot 이동과 Charge·이동 공격·정지 공격은 통행 그룹이 해제될 때까지 시작하지 않는다.
- 각 Enemy는 출구 평면에서 `320 cm` 이상 전진하거나 축 좌우 `300 cm` 밖으로 퍼진 뒤, 출구 축의 좌우를 각각 최대 `250 cm` 검사한 합산 NavMesh 폭을 최소 `250 cm` 확보해야 통과 완료로 기록된다. 비대칭 출구도 좌우 합산 폭으로 인정한다.
- 먼저 넓은 지점에 도착한 Enemy도 뒤따르는 유효 경로의 Enemy가 남아 있으면 최종 Slot으로 되돌아가지 않는다. 포착된 전원이 통과 조건을 만족한 같은 서버 단계에서 그룹 장벽을 해제하고 각자 보존한 최종 Slot 경로를 재개한다.
- 압축 해제 중인 Enemy는 Attack 승격 후보에서 제외한다. 통과가 끝나면 별도 Cooldown 없이 다시 후보가 된다. 단계 도중 새로 Queue에 등록되어 아직 출구 뒤에 있는 Enemy도 같은 그룹에 추가한다.
- `ExitDecompression`은 중간 경유 단계이므로 Detour Crowd의 Goal Slowdown과 Wait 출발 양보 판정을 적용하지 않는다.
- 기본 `3초`는 전체 단계를 강제 종료하는 시간이 아니다. 그 시점에 Fan까지 완전 경로가 없는 Requester만 그룹 장벽에서 제거하는 1회 Fail-safe이며, 유효 경로로 이동 중인 Enemy가 남아 있으면 단계는 계속 유지된다.
- 디버그에서 `ExitDecompression` 경로와 No-Parking Lane 양쪽 경계는 에메랄드색이다. Player 위의 `Egress:N`은 현재 그룹 장벽에 포함된 Enemy 수다.

### 36.11 Open·Pocket 도주 방향 전면 채움

- 이 규칙은 `Open`과 `Pocket`에서 사용한다. Corridor의 물리적 Side 고정은 변경하지 않는다. Pocket에서는 기존 열린 부채꼴 안의 유효 Slot들만 도주 방향 우선순위로 정렬한다.
- Player의 수평 이동 속도가 `80 cm/s` 이상이면 현재 이동 방향을 마지막 도주 방향으로 갱신한다. 방향 기록은 Corridor에서도 계속하지만 실제 전면 우선순위는 Open과 Pocket에서만 소비한다. Player가 한 번도 이 기준을 넘지 않았다면 임의의 전면을 만들지 않는다.
- 이후 Player 속도가 `40 cm/s` 이하로 떨어지면 마지막 도주 방향을 포위망의 전면으로 고정한다. Player의 시선 방향은 사용하지 않는다. 활성화된 전면은 속도가 다시 `80 cm/s` 이상이 될 때까지 유지해 정지 경계의 작은 속도 진동으로 재배치가 반복되지 않게 한다.
- 배정 계층 우선순위는 기존대로 `Attack → Wait → Holding → Pending`이다. Attack 후보 선정과 공격 권한은 변경하지 않는다.
- Wait와 Holding의 빈 Slot은 마지막 도주 방향의 정렬도로 `전면 → 측면 → 후면` 세 구간으로 나눈다. Open은 Ring 고유 각도, Pocket은 Engagement Anchor에서 유효 Fan Slot으로 향하는 실제 방향을 사용하므로 Anchor 지연 오프셋 자체는 등급에 섞이지 않는다. 전면은 마지막 도주 방향을 중심으로 좌우 `75도` 이내다. 후면은 그 반대쪽 `75도` 이내이고 나머지는 측면이다.
- 중앙 승격은 먼저 가장 높은 방향 구간을 선택한다. 같은 구간 안에서 `완전한 Nav 경로 길이 + 경로 주변 혼잡 패널티`를 비교하고, 합성 점수가 `1 cm` 이내로 같을 때 Queue Sequence가 빠른 Enemy를 선택한다. 특정 Requester가 직접 빈 Wait/Holding을 요청하는 경로도 완전한 Nav 경로를 필수로 하되, 같은 방향 구간에서는 Combat Core를 가로지르지 않는 직접 접근을 우선한 뒤 합성 경로 점수를 비교한다. 따라서 가까운 후면 Slot이 도주 방향의 전면 Slot보다 먼저 채워지지 않는다.
- Player가 이동 상태에서 정지 상태로 전환하면 Wait와 Holding 각각의 현재 점유 수만큼 `전면 → 측면 → 후면` 순서의 목표 Slot 집합을 만든다. 같은 구간에서는 도주 방향 정중앙에 가까운 Slot부터 목표 집합에 포함한다. 이미 그 집합 안에 있는 Enemy는 그대로 둔다.
- 집합 밖 점유자와 빈 목표 사이의 완전한 Nav 경로를 모두 검사한다. 후보가 적은 목표부터 저비용 경로 순으로 증대 경로 매칭해, 도달 가능한 전면 목표 수를 먼저 최대로 만든다. 한 Enemy가 여러 목표에 갈 수 있다는 이유로 특정 Enemy만 도달 가능한 목표가 비는 단순 탐욕 배정은 사용하지 않는다.
- 정지 전환 재배치는 역할을 바꾸지 않는다. Wait는 Wait 안에서, Holding은 Holding 안에서만 이동하며 Attack은 건드리지 않는다. 공격 또는 회복 중인 비전열 Enemy도 강제 이동하지 않는다.
- 같은 정지 구간에서 매 Tick 재배치하지 않는다. 속도가 `80 cm/s` 이상으로 다시 올라가 이동 방향을 갱신한 뒤 `40 cm/s` 이하로 멈춘 경우에만 새 전면으로 재평가한다. 기억 방향은 시간만으로 만료하지 않고 다음 명확한 이동으로 교체한다.
- 전면 Slot으로 가는 완전한 Nav 경로가 없는 Enemy는 강제로 배정하지 않는다. 해당 목표는 이후 승격 또는 신규 Queue 후보가 도달 가능할 때 다시 채운다.
- `bh.Debug.Slots 1`에서 정지 후 적용 중인 전면 방향은 Player 위치에서 시작하는 자홍색 화살표로 표시한다.

## 37. 대형 Enemy 크기와 Attack 점유 기반

**현행 C++ 기반 구현, 대형 에셋 연결 및 PIE 검증 필요**

### 크기 설정

- 대형 Enemy도 `ABHEnemy`를 사용한다. 별도 C++ 자식 클래스는 필요하지 않으며 Enemy Data Asset의 `Size Class`로 `Normal`과 `Large`를 구분한다.
- `Capsule Radius Override`와 `Capsule Half Height Override`가 `0`보다 크면 BeginPlay와 Object Pool 재활성화 때 Capsule에 적용한다. `0`은 Enemy Blueprint에 설정한 기존 Capsule 값을 보존한다.
- Capsule 크기를 적용한 뒤 Character Movement의 Nav Agent 속성을 같은 Capsule로 갱신한다. 따라서 Detour Crowd와 경로 추종이 대형 몸체 크기를 읽을 기반을 갖는다.
- 일반 Enemy Data Asset의 신규 설정 기본값은 기존 동작을 보존한다.

### Attack 전열 비용

- 활성 Attack 전열의 총 예산은 해당 공간 모드의 활성 Attack Slot 수다. Open 기본 예산은 `5`, Pocket과 Corridor는 실제 활성 수용량을 사용한다.
- 각 Enemy는 `Attack Slot Cost`를 소비한다. Normal 기본값은 `1`, Large 권장 시작값은 `2`다.
- Normal 후보는 현재 Attack 소유자의 비용 합과 자신의 비용 합이 활성 예산을 넘으면 초기 배정, 직접 예약, Wait 승격 및 교대 후보가 될 수 없다. Large 우선 예약은 필요한 Normal 소유자를 먼저 강등해 예산을 확보한다.
- `Max Concurrent Attackers Of Size`가 `0`보다 크면 같은 `Size Class`의 동시 Attack 소유자 수를 제한한다. Large 권장 시작값은 `1`이다.

### Attack 공간 간격

- 각 Enemy의 `Attack Slot Exclusion Radius`는 자신의 중심 Slot과 다른 점유 Slot 중심 사이에 필요한 최소 거리다.
- 두 점유자의 요구값 중 큰 값을 실제 최소 거리로 사용한다. 둘 다 `0`이면 기존 Slot 간격만 사용한다.
- 간격 검사는 초기 대형, Wait 승격, 직접 예약, 빠른 인계, Combat Core 침입 교대, Corridor/Pocket 재편에 공통 적용한다.
- 비용 또는 간격이 `1`과 `0`이 아닌 Attack 소유자는 일반 거리 절감 Reform에서 Slot을 서로 바꾸지 않는다. 공간 모드의 전체 Layout 재구축이 필요할 때만 새 유효 위치를 찾는다.
- 점유 비용이 활성 예산을 전부 사용했거나 기존 대형의 제외 반경 안에 들어간 빈 Attack Slot은 승격 실패 타이머를 누적하지 않는다. 디버그 구체는 진한 보라색이며 상단에 `Cost:현재/예산`, `Blocked:수`를 표시한다.

### 대형 Enemy 접근 구역과 이동 우선권

- 런타임과 초기 대형 편성 모두에서 `Large`는 Normal보다 먼저 도달 가능한 Attack Slot을 확보한다. Attack 전열이 차 있어도 해당 Slot 소유자, Large의 제외 반경과 충돌하는 소유자, 비용 예산을 초과시키는 Normal 소유자는 Wait·Holding 순으로 물러나며 자리가 없으면 Queue 순서를 유지한 Pending이 된다.
- 이 우선 예약은 Normal이 가진 Attack Slot을 교체할 수 있지만 다른 Large가 가진 Slot은 빼앗지 않는다. `Max Concurrent Attackers Of Size`가 설정되어 있으면 Large 사이의 동시 Attack 상한도 유지한다.
- Troll이 확보한 Attack Slot은 거리 절감 교대와 Combat Core 침입 교대의 양보 대상에서 제외한다. NavMesh 완전 경로와 실제 공격 개시 가능 거리는 계속 필수 조건으로 유지해 도달할 수 없는 Attack Slot을 억지로 점유하지 않는다.
- `Large` Enemy가 Player 수평 거리 `650 cm` 안에 들어오면 Player를 꼭짓점으로 하고 해당 Large Enemy 방향을 중심축으로 하는 전용 부채꼴을 만든다.
- 기본 부채꼴은 Player로부터 최대 반경 `450 cm`, 좌우 반각 `50도`다. 실제 후방 끝은 `Large Enemy 중심 + 100 cm`까지만 허용해 Troll 뒤쪽 대기열을 과도하게 밀어내지 않는다. Player와 Large Enemy의 높이 차이가 `150 cm`를 넘으면 서로 다른 층으로 보고 적용하지 않는다.
- 새 Slot 예약은 전체 부채꼴을 피하지만 기존 Slot 소유자는 경계보다 기본 `8도` 안쪽에 들어왔을 때만 재배치한다. 바깥쪽 대체 Slot이 없으면 기존 예약을 유지해 매 프레임 Slot을 잃고 다시 요청하는 흔들림을 막는다.
- Large Enemy 자신은 이 제한에서 제외한다. Normal Enemy는 부채꼴 안의 Attack·Wait·Holding Slot을 새로 예약할 수 없으며, 이미 점유한 Slot이 부채꼴에 들어오면 같은 계층의 바깥 Slot을 먼저 찾고 필요하면 Attack에서 Wait·Holding 순으로 물러난다.
- Detour Crowd는 Normal과 Large를 다른 회피 그룹으로 구분한다. Normal은 Normal과 Large를 모두 피하지만 Large는 다른 Large만 피하고 Normal은 무시한다. 따라서 Troll의 전역 경로는 NavMesh가 담당하고, 주변 Normal Enemy가 로컬 조향으로 Troll의 진행로를 양보한다.
- Enemy끼리의 Capsule 물리 충돌은 계속 Ignore한다. 예외적으로 겹침 복구가 필요할 때는 Large에 가장 높은 우선순위를 주어 Normal 쪽만 먼저 빠져나오게 한다.
- 이 정책은 Troll 클래스명을 하드코딩하지 않는다. Troll Enemy Data Asset의 `Size Class = Large`가 에디터 적용 조건이다.
- `bh.Debug.Slots 1`에서는 활성 Large Enemy가 확보한 부채꼴 경계를 자홍색으로 표시한다.

### Troll Root Motion Charge

**현행 C++ 기반 구현, 에셋 연결 및 PIE 검증 필요**

- 구현 계약은 “원본 Montage의 Root Motion이 전진을 단독 소유하고, AI `MoveTo`와 Slot 경로는 Charge 동안 Troll을 움직이지 않는다”이다.
- Charge는 `Size Class = Large`, Enemy Data Asset의 `Charge.bEnabled` 활성화, 현재 Attack Slot 점유를 모두 만족한 Enemy만 사용할 수 있다.
- `Charge.Attack Id`는 같은 Data Asset의 `Attacks`에 있는 전용 공격을 가리킨다. 전용 Montage 하나의 전체 Root Motion 이동량을 런타임에 읽으므로 `Montage Sections`는 비워 둔다.
- 전용 Montage의 수평 Root Motion 축은 X/Y와 부호 어느 쪽도 허용한다. 런타임이 실제 이동축을 Player 방향에 맞추되, 해당 이동축 기준 좌우 누적 이탈과 회전이 Data Asset의 허용치를 넘으면 사전 직선 검사와 실제 궤적이 달라지므로 발동을 거부한다.
- 발동 전 Player까지의 수평 거리·높이 차이, Root Motion 총 이동 거리 안에 Player가 들어오는지, 예상 종점의 NavMesh 투영, 시작점부터 종점까지의 Navigation Raycast를 확인한다.
- 같은 직선 구간을 Troll의 실제 Capsule 크기에 수평 여백을 더해 WorldStatic·WorldDynamic Sweep한다. 벽이나 고정 장애물이 있으면 발동하지 않는다. Normal Enemy와 밀치도록 허용한 Large Enemy는 이동 가능한 교통으로 보고 제외하지만, 밀치지 않도록 설정한 Large Enemy는 경로를 막는다.
- 살아 있는 Enemy Capsule은 NavMesh를 동적으로 깎지 않는다. Troll과 Player 사이의 Normal Enemy는 Navigation Raycast나 World Sweep에서 Charge를 막지 않고, 발동 후 밀치기 대상으로 처리한다.
- 발동 시 Player 위치를 향해 방향을 한 번 고정한다. Charge 도중 Player를 유도 추적하거나 Slot 위치에 맞춰 회전하지 않는다.
- Troll의 기존 Attack Slot 예약은 유지하지만 Controller는 Charge가 끝날 때까지 새 경로를 요청하지 않는다. 종료 후 기존 Attack 회복 상태를 거쳐 슬롯 이동을 다시 사용한다.
- 이동한 매 프레임의 구간을 Enemy 전용 Object Channel로 Sweep한다. 처음 맞은 Normal Enemy는 Charge 진행축의 가까운 좌우 방향으로 한 번만 Launch되고 짧은 Stagger로 자신의 Slot을 반납한다. Large Enemy는 기본적으로 밀려나지 않는다.
- Charge 중 Troll Capsule은 Player와 Overlap하도록 잠시 바꿔 Root Motion이 Player Capsule에 막히지 않게 하고, 종료·실패·경직·사망·풀 회수 시 원래 충돌 응답을 복원한다.
- Player 피해는 Charge Montage에 배치한 기존 `BH Enemy Attack Hit` Notify와 Charge 전용 Attack Definition의 Target Cone 수치를 사용한다.
- Montage에 활성 Root Motion이 없거나 수평 Root Motion 이동량이 `0`이면 Charge는 발동하지 않고 경고 로그를 한 번 출력한다.

### 현행 범위와 남은 확장

- 대형도 중심 Attack Slot 하나만 실제 소유한다. 추가 공간은 별도 가짜 예약을 만들지 않고 비용과 중심 거리 검사로 차단한다.
- Attack Ring 반경은 아직 모든 크기가 공간 모드의 공통 위치를 사용한다. 대형 전용 외곽 Attack Ring은 공격 애니메이션의 실제 도달 거리를 확인한 뒤 추가한다.
- Wait·Holding·Pending Row의 Slot 위치는 아직 크기별로 다시 배치하지 않는다. 대형 Capsule에서 갱신된 Nav Agent와 Detour Crowd 간격이 1차 공간 확보를 담당한다.
- Object Pool Manager 하나가 일반 `Enemy Class`와 `Troll Enemy Class`를 함께 관리한다. 기본 구성은 일반 10명당 Troll 1명이며, Troll도 일반 Enemy와 동일한 Pool 생명주기와 시체 회수 규칙을 사용한다.
