# 근접 공격 판정 설계 초안

## 상태

초안. ProjectBH의 첫 전사 수직 슬라이스에서 사용할 방식을 정하기 위한 문서다.

## 결론

ProjectBH는 **애니메이션의 유효 타격 구간에만, 무기 위의 여러 기준점이 이전 프레임에서 현재 프레임까지 이동한 궤적을 Sphere Sweep으로 검사하는 방식**을 사용한다.

- 공격 판정·피해·가드·사망은 서버만 확정한다.
- 클라이언트는 즉시 몽타주·트레일·타격 예상 효과를 재생할 수 있지만 피해를 확정하지 않는다.
- 공격 하나에 이미 맞은 대상은 `HitActors` 집합에 기록해 같은 스윙에 중복 피해를 주지 않는다.
- 무기별로 다중 타격, 방어구 관통, 첫 적에서 멈춤을 데이터로 다르게 설정한다.

이 방식은 긴 대검·창·도끼의 실제 휘두르는 느낌을 살리면서, 물리 충돌 기반보다 예측 가능하고 네트워크 권한에도 맞는다.

## 방법 비교

| 방식 | 내용 | 장점 | 한계 | ProjectBH 판단 |
| --- | --- | --- | --- | --- |
| 무기 Collider Overlap | 무기에 Capsule/Box Collision을 붙여 공격 중 켬 | 가장 빨리 만들 수 있음 | 빠른 휘두름에서 누락, 물리·프레임·네트워크 결과가 흔들림 | 사용하지 않음 |
| 고정 전방 볼륨 | 애님 노티파이 시점에 캐릭터 앞 Box/Capsule/Cone 검사 | 간단하고 가드·발차기·광역기에 좋음 | 칼날 궤적과 어긋남 | 비무장·방패 밀치기·폭발에 한정 |
| 단일 Line Trace | 손·카메라·무기 끝에서 한 줄 검사 | 창 찌르기·총·조준 무기에 좋음 | 넓은 베기에서 빈 공간이 큼 | 찌르기 보조 방식 |
| **다중 Sphere Sweep** | 무기 뿌리·중간·끝의 이전/현재 위치를 연속 스윕 | 빠른 베기에도 안정적, 궤적과 잘 맞음, 서버 검증 가능 | 기준점·반지름 조정 필요 | **주력 방식** |
| 데이터 기반 Sphere/Capsule | 애니메이션 구간에 본/Dummy 위치의 구·캡슐 판정 | 기획자가 공격 범위를 명확히 통제, 무기 외형과 분리 가능 | 실제 칼날과의 일치도는 수작업에 좌우 | 보스·특수기·일부 공격에 병행 |
| 물리 시뮬레이션 충돌 | 실제 강체 무기로 충돌 이벤트 수신 | 이론상 물리적 | 비용·튐·복제·결과 재현 문제가 큼 | 사용하지 않음 |

## ProjectBH 권장 구조

### 1. 애니메이션 타이밍

각 공격 Montage에 `ANS_MeleeHitWindow`(Anim Notify State)를 둔다.

- Notify Begin: 서버에서 현재 공격 ID를 시작하고, 각 추적점의 월드 위치를 저장한다.
- Notify Tick: 서버에서 이전 위치 → 현재 위치로 스윕한다.
- Notify End: 공격 판정을 닫고 추적 상태와 대상 중복 목록을 비운다.

타격 시간은 코드의 고정 시간 대신 애니메이션에서 정한다. 따라서 리타기팅·공격 속도 조정 뒤에도 타격 창을 눈으로 맞출 수 있다.

### 공격 애니메이션 구조 선택

Paragon에 기본 `Primary` 공격 시퀀스와 `Attack`/`Recovery`가 분리된 시퀀스가 함께 있는 경우, ProjectBH의 실제 전투 구현에는 **분리형을 우선 사용**한다.

| 형태 | 용도 | ProjectBH 판단 |
| --- | --- | --- |
| `Primary` 단일 시퀀스 | 빠른 미리보기, 리타게팅 품질 확인, 아주 단순한 프로토타입 | 기준 동작 확인용으로 사용 |
| `Attack` + `Recovery` 분리 시퀀스 | 타격 뒤 경직, 콤보 입력, 회피/방어 캔슬을 독립적으로 제어 | **전투 구현 기본** |

분리형은 다음 상태로 취급한다.

`Startup → Active(ANS_MeleeHitWindow) → Recovery → Locomotion`

- `Attack` 시퀀스 안에는 준비와 유효 타격 창을 둔다.
- `Recovery` 시퀀스는 피해 판정 없이 후딜과 원상복귀만 담당한다.
- 회피·가드·다음 콤보의 허용 시점은 Recovery 안의 Anim Notify 또는 Montage Section으로 연다.

첫 검방 공격은 두 시퀀스를 하나의 Montage 안에서 `Attack`, `Recovery` Section으로 구성한다. 이 방식이면 기획상 후딜을 수치화·조정하고, 추후 방어 캔슬 또는 콤보 연결을 추가할 때도 애니메이션 파일을 다시 자르지 않아도 된다.

#### 현재 확보한 AttackA~D 적용

Greystone으로 리타게팅한 `AttackA`~`AttackD`는 각각의 Montage로 만들지 않고, 우선 하나의 `AM_Greystone_LightCombo`에 순서대로 배치한다.

| Montage Section | 사용하는 Sequence | 역할 |
| --- | --- | --- |
| `Attack_A` | `AttackA` | 콤보 1타 |
| `Attack_B` | `AttackB` | 콤보 2타 |
| `Attack_C` | `AttackC` | 콤보 3타 |
| `Attack_D` | `AttackD` | 콤보 4타·마무리 |

- 각 Sequence의 실제 무기 통과 구간에 `ANS_MeleeHitWindow`를 둔다.
- 전투 컴포넌트에서 `AN_ComboInputOpen`과 `AN_ComboInputClose`를 구현한 뒤, 각 타격의 끝 또는 Recovery 시작점에 배치한다.
- 첫 검증 단계에서는 `Attack_A`만 재생해 타격·후딜·리타게팅 품질을 확인한다. 이후 입력 버퍼와 `Montage_SetNextSection`으로 A → B → C → D 연결을 구현한다.

`AttackA`~`AttackC`와 대응 `Recovery`를 현재 구성할 때의 Montage 타임라인은 아래와 같다.

`AttackA → RecoveryA → AttackB → RecoveryB → AttackC → RecoveryC`

각 구간 시작에 `Attack_A`, `Recovery_A`, `Attack_B`, `Recovery_B`, `Attack_C`, `Recovery_C` Section을 만든다. 입력이 없으면 Recovery까지 재생하고 종료한다. 입력 버퍼가 열려 있으면 `Recovery_A → Attack_B`, `Recovery_B → Attack_C`로만 다음 Section을 연결한다. 마지막 `Recovery_C` 뒤에는 다음 Section을 연결하지 않는다.

### 2. 무기 추적점

전사 대검 기준으로 `BladeBase`, `BladeMid`, `BladeTip` 세 지점을 사용한다. 각 지점은 무기 메시의 Socket이거나 캐릭터 Skeleton의 ProjectBH 전용 Socket이다.

매 틱 세 지점 모두에 Sphere Sweep을 실행한다. 각 결과를 합친 뒤 공격마다 같은 Actor는 한 번만 판정한다.

| 무기/행동 | 추적점 | 판정 성격 |
| --- | --- | --- |
| 한손검·양손검 베기 | Base + Mid + Tip | 다중 타격 가능한 넓은 베기 |
| 도끼·망치 내려치기 | Mid + Tip | 첫 강한 충돌에서 멈추거나 낮은 관통량 |
| 창 찌르기 | Tip 중심 + 짧은 Capsule Sweep | 단일 대상·높은 약점 정밀도 |
| 단검 | Tip 중심 | 짧은 거리·빠른 재공격 |
| 방패 밀치기·킥 | 캐릭터 앞 고정 Capsule | 무기 궤적이 아닌 전방 밀침 |
| 투사체·마법 | 발사체 Collision 또는 단발 Trace | 근접 스윕과 별도 |

### 3. 적중 후 해결 순서

1. Server가 `CombatHitbox` 충돌 채널로 후보를 찾는다.
2. 이미 맞은 Actor, 자신, 아군, 무적 상태를 제외한다.
3. 대상의 가드 방향·패링 창·방패 상태를 먼저 판정한다.
4. 방어가 실패하면 피해, 장갑 피해, 경직, 넉백을 적용한다.
5. 해당 공격의 `CleaveBudget`을 차감한다. 도끼처럼 0이 되면 다음 대상은 맞지 않고, 검처럼 예산이 남으면 다음 적까지 통과한다.
6. 복제된 결과를 통해 각 클라이언트에 피격·사운드·VFX를 재생한다.

## 멀티플레이 규칙

- 클라이언트는 공격 입력과 의도만 서버에 요청한다.
- 서버는 공격 가능 상태·스태미나·쿨다운을 검증하고 Montage/전투 상태를 시작한다.
- 스윕과 피해는 서버 캐릭터의 무기 Socket 위치로 계산한다.
- 클라이언트는 즉시 예상 트레일을 보여도 되지만, 체력·경직·사망은 서버 결과만 반영한다.
- 향후 지연 보정이 필요하면 공격 시작 시각과 대상 위치 이력을 이용한 제한적 서버 재검증을 별도 추가한다. 첫 수직 슬라이스에서 클라이언트 판정 권한은 주지 않는다.

서버가 Socket 위치를 얻을 수 있도록 서버 캐릭터 Mesh의 Pose/Bone 갱신 정책도 확인한다. 리슨 서버 우선 단계에서는 호스트 화면에서 대체로 갱신되지만, 전용 서버 전환 전에는 `Always Tick Pose and Refresh Bones` 등 서버에서도 본 갱신이 보장되는 설정을 검증한다.

## 데이터 설계 원칙 — 시스템 기획 포트폴리오 기준

DataTable을 쓰지 않는 것이 권장이 아니다. ProjectBH는 시스템 기획 포트폴리오이므로, 공격의 수치·규칙·연결을 코드와 블루프린트에 하드코딩하지 않고 **DataTable로 설계자가 읽고 조정할 수 있게 공개**하는 방식을 기본으로 한다.

다만 DataTable 하나에 모든 것을 넣지는 않는다. Montage, Skeletal Mesh Socket처럼 에셋 참조·캐릭터별 외형 설정은 Data Asset과 Animation Notify가 더 안전하고 확인하기 쉽다.

| 책임 | 권장 UE 기능 | 이유 |
| --- | --- | --- |
| 피해·스태미나·가드 피해·경직·Cleave·콤보 연결·공격 태그 | **DataTable** `DT_AttackDefinition` | 공격별 규칙을 행 단위로 비교·조정 가능. 시스템 기획 의도를 가장 명확히 보여 줌 |
| 무기군 공통 수치·장착 제한·기본 Trace Profile | **DataTable** `DT_WeaponDefinition` | 검/도끼/창의 차이를 수치로 설명하고 밸런싱하기 좋음 |
| Montage, 캐릭터별 Socket 이름·반지름 보정, VFX, 카메라 | Data Asset `DA_CharacterCombatVisual` 또는 `DA_WeaponVisual` | Paragon Skeleton별 차이를 에셋 단위로 분리하고, 긴 에셋 참조를 거대한 표에 넣지 않음 |
| 실제 유효 타격 시간 | Animation Montage의 `ANS_MeleeHitWindow` | 애니메이션을 보며 타격 창을 조정 가능. 표의 시간값과 이중 관리하지 않음 |
| 서버 판정, 중복 적중 방지, 가드/패링 우선순위 | C++ Combat Component | 데이터가 지정한 규칙을 공통으로 실행. 모든 무기의 판정 일관성을 보장 |

### 최소 DataTable 구조

`DT_AttackDefinition`의 한 행은 “무기 하나”가 아니라 **콤보 한 타**를 뜻한다.

| 필드 예시 | 의미 |
| --- | --- |
| `AttackId` | 예: `Warrior.Greatsword.Light.01` |
| `WeaponType`, `AttackType` | 양손검 / Light, Heavy, GuardCounter 등 |
| `BaseDamage`, `GuardDamage`, `StaminaCost`, `PoiseDamage` | 밸런싱 수치 |
| `CleaveBudget`, `MaxHitActors`, `bStopOnArmor` | 검·도끼·창의 적중 차이 |
| `TraceProfileId` | 어떤 추적점·반지름 프로필을 쓸지 지정 |
| `NextAttackId` | 허용된 다음 콤보 타 |
| `HitReactionTag`, `DamageTypeTag` | 피격 반응·상태이상 연결 |

Data Asset에는 `AttackId → Montage/Section` 연결과 캐릭터별 Socket 보정만 둔다. `ANS_MeleeHitWindow`는 자신이 실행 중인 `AttackId`를 Combat Component에 알리고, Component는 DataTable 행을 읽어 해당 스윕·피해 규칙을 실행한다.

이 구조의 포트폴리오 장점은 다음과 같다.

- “양손검은 넓게 3명, 도끼는 장갑에 강하지만 1명, 창은 약점 정밀도가 높음”을 코드가 아니라 표로 증명할 수 있다.
- 새 무기·새 콤보는 DataTable 행 추가와 Montage/Visual Asset 연결로 확장되며, 공통 C++ 판정 코드는 바뀌지 않는다.
- 테스트 중 수치 변경 전후를 기록하고, 밸런싱 근거를 설계 문서에 남길 수 있다.

## 첫 수직 슬라이스 범위

### Codex: C++ 구현

- `FCombatAttackRow : FTableRowBase`와 `DT_AttackDefinition`을 만들어 공격별 피해·관통·콤보 규칙을 데이터화한다.
- 캐릭터별 Montage/Socket 보정은 별도 Combat Visual Data Asset으로 두고, `AttackId`로 DataTable 행과 연결한다.
- `UMeleeHitTraceComponent`가 서버에서 이전/현재 Socket 위치를 보관하고 Multi Sphere Sweep을 수행한다.
- 공격별 `HitActors` 중복 방지, 가드 우선 판정, 서버 피해 적용, 디버그 드로잉을 구현한다.
- 공격 결과를 복제하여 원격 클라이언트에서도 타격 반응을 재생하게 한다.

### 사용자: Unreal Editor 작업

1. 전사 무기 또는 파생 Skeletal Mesh에 `BladeBase`, `BladeMid`, `BladeTip` Socket을 놓는다.
2. 첫 양손검 공격 Montage의 실제 칼날 통과 구간에 `ANS_MeleeHitWindow`를 배치한다.
3. 테스트 더미에 `CombatHitbox` 충돌 응답을 설정한다.
4. 호스트와 클라이언트에서 스윕 디버그 선·구를 켜고 거리, 높이, 벽 관통, 중복 적중을 확인한다.

## 참고 사례

### Dark Souls III

FromSoftware는 DS3의 전체 충돌 파이프라인을 공식 공개하지 않았다. 다만 모딩 문서에서 확인되는 데이터 구조는 **애니메이션 이벤트가 공격 행동을 호출하고, Attack Parameter가 피해·스태미나·히트박스를 지정하는 데이터 기반 방식**이다. 해당 파라미터에는 Dummy Polygon ID 두 개와 반지름을 사용해 구 또는 캡슐 히트박스를 배치하는 필드가 확인된다. 즉, 시각 메시의 물리 충돌을 매 프레임 그대로 쓰기보다는 애니메이션·더미 위치·공격 데이터가 결합된 설계로 보는 것이 타당하다.

위 비교표에 직접 대응시키면 **`데이터 기반 Sphere/Capsule` 방식**이다. 히트박스의 두 기준점은 애니메이션을 따라 움직이므로 게임 실행 중에는 움직이는 구/캡슐 판정이 되지만, 공개 자료만으로 내부가 연속 스윕인지 매 프레임 겹침 검사인지는 단정하지 않는다.

ProjectBH가 가져올 점은 “칼 메시와 무조건 1:1일 필요 없는, 공격별로 조절 가능한 데이터 히트박스”와 “애니메이션이 여는 정확한 유효 타격 창”이다. DS3의 내부 스윕 여부·갱신 주기·온라인 지연 보정은 공개 자료만으로 단정하지 않는다.

### Warhammer: Vermintide 2

Fatshark도 정확한 충돌 질의 소스 전체를 공식 공개하지 않았다. 공식 개발 블로그는 무기별 공격 체인 타이밍, 사거리, 공격이 적중할 시점, `sweep` 공격과 방어구 관통 같은 무기 메타데이터가 시스템에 존재함을 설명한다. 공개된 플레이어용·커뮤니티 디버그 자료는 공격 궤적을 여러 ray로 표시하고, 게임 내 문제 보고도 무기 히트박스와 애니메이션의 불일치를 별도의 문제로 다룬다. 따라서 구현 세부를 단정할 수는 없지만, **공격별 데이터·시간·사거리와 스윕/레이 계열 판정을 결합하고, cleave·장갑·약점 결과를 별도로 계산하는 구조**로 보는 것이 근거에 맞다.

위 비교표에 직접 대응시키면 **`다중 Sphere Sweep`과 같은 범주의 스윕/레이 기반 공격 프로필 방식에 가장 가깝다**. 다만 이는 “공격이 넓게 휩쓰는가”를 뜻하는 공식 `sweep` 분류와 커뮤니티 디버그 관찰을 종합한 판단이다. Fatshark가 실제로 Sphere Sweep, Capsule Sweep, 다중 Ray 중 무엇을 쓰는지는 공개하지 않았으므로, ProjectBH가 이를 그대로 복제한다고 표현하지 않는다.

ProjectBH가 가져올 점은 한 공격의 범위만이 아니라 `CleaveBudget`, 장갑 반응, 약점, 스태거를 공격 데이터로 분리하는 것이다. 수십 마리 군중전이 아니므로 첫 단계는 최대 2~3 적중만 지원하고, 대규모 웨이브 단계에서 예산 기반 관통을 확장한다.
