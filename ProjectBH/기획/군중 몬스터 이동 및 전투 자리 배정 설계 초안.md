# 군중 몬스터 이동 및 전투 자리 배정 설계 초안

> 문서 역할: 초기 기획과 설계 변경의 역사 기록이다. **현재 적용되는 몬스터 이동 규칙과 기본값은 [[몬스터 이동 시스템 규칙]]을 단일 기준으로 사용한다.** 이 문서의 과거 수치·단계·후속 아이디어를 현행 구현으로 간주하지 않는다.

## 목표

여러 몬스터가 플레이어를 추격할 때 서로 겹치거나 한 점에 밀집하지 않고, 자연스럽게 둘러싸며 일부만 공격한다.

## 결론

NavMesh를 포기하지 않는다. 다음 세 층을 함께 사용한다.

```text
NavMesh 경로 탐색
        ↓
Detour Crowd 근거리 회피
        ↓
플레이어 주변 전투 슬롯 예약
```

| 층 | 책임 | 해결하는 문제 |
| --- | --- | --- |
| NavMesh | 벽·문·장애물을 피해 목적지까지의 전역 경로 계산 | 길찾기 |
| Detour Crowd | 이동 중인 몬스터끼리 속도·방향을 조절 | 끼임, 겹침, 추월 |
| 전투 슬롯 | 플레이어 주변의 공격 자리와 대기 자리를 한 마리씩 예약 | 전원이 플레이어 중심으로 돌진하는 교통체증 |

RVO와 Detour Crowd는 동시에 켜지 않는다. ProjectBH는 NavMesh 위에서 경로까지 고려하는 **Detour Crowd**를 우선 채택한다. RVO는 NavMesh를 사용하지 않으므로 회피 중 경로 밖으로 나갈 수 있다.

### 2026-08-27 확정 범위

첫 전투 수직 슬라이스의 실제 길찾기는 **UE NavMesh만 사용**한다. 커스텀 격자 A*, Flow Field, `FHordeTraversalGraph`는 현 구현 범위에서 제외한다.

- NavMesh: 실제 이동 경로의 단일 진실 원천
- Detour Crowd: NavMesh 위의 근거리 회피
- ProjectBH 직접 구현: Combat Engagement Slot, 대기열, 동시 공격 제한, 벽 등반 레인 예약
- Smart Nav Link: 지정된 벽면 Traversal의 연결점

커스텀 경로 탐색은 나중에 프로그래머 기술 데모를 별도로 만들 의도가 생겼을 때만 게임 본편과 분리해 검토한다.

## NavMesh 대안 및 채택 판단

| 방식 | 잘 맞는 상황 | 장점 | 한계 | ProjectBH 판단 |
| --- | --- | --- | --- | --- |
| **NavMesh + Detour Crowd** | 8~30마리의 전투 적, 복도·문·장애물이 있는 맵 | 견고한 경로, UE 도구 지원, 전투 슬롯과 결합 쉬움 | 대규모 개체에는 비용 증가 | **핵심 전투 적 채택** |
| Flow Field / Integration Field | 수십~수백 유닛이 하나의 거점으로 집결하는 RTS형 군대 | 같은 목표의 경로 계산을 공유해 대규모에 유리 | 동적 장애물·개별 전투 자리·복잡한 지형 대응을 직접 설계해야 함 | 대규모 군단 게임으로 확장될 때 비교 실험 |
| Steering / Boids / Separation Force | 탁 트인 공간의 무리·동물·비행체 | 유기적인 군집 움직임, 구현 개념이 단순 | 벽·문에서 막히며 전역 길찾기와 전투 규칙이 부족 | Wait Ring의 보조 연출로만 검토 |
| Mass Entity + Mass Navigation/Avoidance | 멀리 보이는 수십~수백 배경 유닛 | 대량 처리 지향 | 핵심 전투 Character/GAS/정밀 애니메이션과 결합 비용이 크고, Mass Avoidance는 Experimental | 배경 군중에만 장기 검토 |
| 직접 만든 Grid/A* 또는 커스텀 Nav Graph | 이동 자체가 게임의 차별점인 경우 | 이동 규칙 전체를 통제 | NavMesh가 이미 해결하는 장애물·경로·디버그를 다시 만들어야 함 | 게임의 저수준 길찾기 대체로는 미채택. 기술 데모 또는 고수준 경로 선택에 사용 |

Flow Field는 많은 몬스터가 동일한 목적지로 이동할 때 강력하지만, ProjectBH의 적은 플레이어 주변의 Attack/Wait Slot처럼 **서로 다른 세부 목적지**를 가져야 한다. 따라서 첫 전투 수직 슬라이스에서는 이점이 작다.

## 대규모 확장 원칙

- 화면 가까이 있고 공격·피격·사망·정밀 애니메이션이 필요한 적: `ABHEnemy` + NavMesh + Detour Crowd + Slot Manager
- 멀리 있고 전투에 직접 참여하지 않는 배경 군중: Mass Entity 또는 저비용 Flow Field를 별도 검토
- 큰 오픈 월드가 필요해지면 NavMesh를 버리는 대신, Navigation Invoker로 플레이어 주변 타일만 런타임 생성하는 방식을 먼저 검토한다.

## 내장 기능과 ProjectBH 고유 시스템의 경계

Detour Crowd는 몬스터들이 서로 부딪힐 때 **어느 방향과 속도로 비켜 갈지**를 계산하는 범용 이동 기능이다. 다음 질문에는 답하지 못한다.

- 누가 지금 플레이어를 공격할 권리가 있는가?
- 몇 마리까지 동시에 공격하면 읽기 쉽고 공정한가?
- 빈자리가 없을 때 몬스터는 어디서 어떤 행동을 해야 하는가?
- 원거리·근접·돌진형 몬스터의 자리는 어떻게 달라져야 하는가?
- 플레이어가 이동하거나 몬스터가 경직·사망했을 때 자리는 누구에게 넘어가는가?

위 질문이 ProjectBH의 **Combat Engagement Director / Slot Manager**가 직접 설계할 영역이다. NavMesh와 Detour Crowd는 이를 구현하기 위한 기반 도구로 사용한다.

| 층 | 구현 성격 | 포트폴리오에서 보여 줄 점 |
| --- | --- | --- |
| NavMesh | UE 내장 | 정적 지형에서 경로를 찾는 기반 |
| Detour Crowd | UE 내장 설정·통합 | Agent 반지름·회피·성능 한계에 맞춘 선택 근거 |
| Slot Manager | **ProjectBH 고유 규칙** | 공격·대기 슬롯, 예약·반납, 우선순위, 재배정 규칙 |
| Combat Engagement Director | **ProjectBH 고유 기획** | 동시 공격자 수, 타입별 압박도, 플레이어가 읽을 수 있는 공격 리듬 |

따라서 Detour Crowd를 직접 재구현하지 않는다. 검증된 범용 회피를 재사용하고, 그 위에 게임의 전투 경험을 바꾸는 의사결정 규칙을 설계·구현·검증한다.

## 포트폴리오 검증 지표

| 지표 | 첫 목표 | 의미 |
| --- | --- | --- |
| 동시 Attack Ring 점유 수 | 4 이하 | 플레이어가 공격을 읽고 대응할 수 있는 상한 |
| Wait Ring 체류 몬스터 | 전체의 40% 이상 허용 | 모든 적이 무의미하게 전진하지 않음 |
| 슬롯 재배정 빈도 | 플레이어가 크게 이동했을 때만 | 흔들림·빙빙 돎 방지 |
| 12마리 접근 시 Capsule 겹침 | 0회가 목표 | 개인 공간 보장 |
| 막힘 상태 복구 | 2초 안에 대기 슬롯 또는 재경로 | 통로·사망체로 인한 교착 방지 |

데모에서는 각 슬롯, 예약자 ID, 상태, 공격 권한, Detour 회피 반경을 디버그로 표시한다. 전/후 비교 영상(모두 Player로 MoveTo vs. Slot Manager 적용)을 제시해 규칙의 효과를 증명한다.

## 시스템 기획 포트폴리오 구현 원칙

UE 내장 기능을 사용하는 것은 약점이 아니다. 단, 어떤 문제를 내장 기능에 맡기고 어떤 문제를 ProjectBH 규칙으로 해결하는지 명확해야 한다.

| 구분 | UE 기능 활용 | ProjectBH 직접 설계·구현 |
| --- | --- | --- |
| 지형 경로 | NavMesh, MoveTo | 어떤 목적지를 선택할지 |
| 근거리 충돌 회피 | Detour Crowd | 회피 반경, 에이전트 규모, 전투 상태별 회피 정책 |
| 특수 이동 연결 | Smart Nav Link, Custom Movement Mode | 어느 벽을 언제 사용할지, 등반 레인·대기열·중단 규칙 |
| 전투 참여 | 없음 | Attack/Wait Slot, 예약·반납, 동시 공격 상한, 우선순위 |
| 행동 흐름 | AI Controller/BT/State Tree 기반 | 상태 전이, 입력 조건, 실패 복구, 난이도 압박 규칙 |

포트폴리오에서 피해야 할 것은 “내장 노드를 연결했다”만 보여 주는 것이다. 대신 다음을 증명한다.

1. 문제 정의: 직접 `MoveTo(Player)`했을 때 생기는 뭉침·동시 공격·벽 앞 교착을 영상과 수치로 제시한다.
2. 설계: Slot 수, 우선순위, 대기·재배정·등반 레인 규칙을 상태도와 표로 제시한다.
3. 구현: C++ `CombatEngagementSlotComponent`, `TraversalWallLink`, 적 AI 상태 전이를 보여 준다.
4. 검증: 동시 공격자 수, 대기 시간, 겹침 수, 교착 복구 시간의 전/후 비교를 제시한다.

NavMesh와 Detour Crowd를 재구현하지 않는다. 이는 이미 검증된 범용 인프라다. ProjectBH는 그 위에서 플레이어가 체감하는 적 군중의 전술·압박·읽기성을 직접 통제한다.

## 프로그래머 포트폴리오 병행 원칙

프로그래머 포트폴리오까지 목표로 할 경우에도 NavMesh 전체나 Detour Crowd 전체를 재구현하지 않는다. 대신 ProjectBH의 문제에 직접 필요한 알고리즘 계층을 C++로 구현하고, 성능·결과를 측정한다.

### 기본 게임 빌드

- NavMesh + Detour Crowd를 사용해 안정적인 전투 적 이동을 확보한다.
- `CombatEngagementSlotComponent`와 `TraversalWallLink`를 직접 구현한다.

### 기술 증명 빌드 또는 비교 레벨

Detour Crowd를 끈 별도 테스트 레벨에서 `UCrowdSteeringComponent`를 구현·검증한다.

```text
NavMesh Path가 주는 Desired Velocity
  + Spatial Hash로 찾은 근접 이웃의 Separation Force
  + 예약 Slot으로 향하는 Attraction Force
  + 벽/교착 회피 보정
  = 최종 조향 벡터
```

- 이웃 탐색은 모든 적을 서로 비교하는 `O(N²)` 대신 Uniform Spatial Hash로 관리한다.
- 각 적은 자기 주변 셀만 조회해 Separation Force를 계산한다.
- 결과를 Debug Draw로 표시하고, 12/30/60 적에서 프레임 시간과 겹침 수를 측정한다.
- 이 실험 레벨은 Detour Crowd와 동시에 사용하지 않는다.

### 포트폴리오에서 보여 줄 코드 포인트

| 시스템 | 직접 구현 내용 | 증명 방법 |
| --- | --- | --- |
| Combat Engagement Slot | 원형 슬롯 생성, 예약 토큰, 우선순위, 반납 | 동시 공격자 상한·대기열 디버그 |
| Spatial Hash Crowd Steering | 셀 삽입/삭제, 이웃 질의, Separation 계산 | `O(N²)` 기준과 성능 비교 |
| Traversal Wall Link | Smart Link 연동, 레인 예약, `MOVE_Custom` 등반 | 4레인 벽 등반 군중 데모 |
| Server Authority | 슬롯·등반 예약을 서버만 확정, 이동 상태 복제 | 리슨 서버 다중 클라이언트 검증 |

이 구성을 따르면 게임 빌드는 검증된 UE 기능을 활용해 안정성을 지키고, 기술 데모는 ProjectBH가 직접 만든 군중 조향·예약 알고리즘을 명확히 보여 줄 수 있다.

### 직접 길찾기 구현의 권장 범위

일반적인 2D Grid A* 구현은 알고리즘 기초를 증명할 수 있지만, 단독으로는 ProjectBH의 군중 전투 문제를 해결하지 못한다. 다음 두 용도로 한정해 사용한다.

1. **기술 데모 레벨**: Grid A*, 동적 장애물 재탐색, Flow Field를 비교 구현하고, 다수 에이전트의 탐색 시간·경로 품질을 측정한다.
2. **게임 고수준 경로 선택**: `FHordeTraversalGraph`를 직접 구현한다. 노드는 지상 진입 구역, 벽 등반 Entry/Exit, 상단 전투 구역, 대기 구역이고, 간선 비용은 거리뿐 아니라 등반 레인 대기열, 슬롯 점유, 위험도, 막힘 상태를 포함한다.

고수준 그래프가 “어느 벽·어느 진입로·어느 전투 구역으로 갈지”를 A*로 고르면, 각 구역 안의 실제 보행 경로는 NavMesh에 맡긴다.

```text
FHordeTraversalGraph A* : 전략 경로 선택
          ↓
NavMesh MoveTo            : 구역 내부의 실제 보행 경로
          ↓
Crowd Steering            : 근거리 간격 확보
```

이 하이브리드 구조는 범용 보행 NavMesh를 불필요하게 재구현하지 않으면서도, ProjectBH만의 벽면 침입·대기열·전투 슬롯 비용을 직접 코드와 알고리즘으로 표현한다.

## 전투 슬롯 규칙

플레이어를 중심으로 안쪽 `Attack Ring`과 바깥쪽 `Wait Ring`을 만든다.

```text
      Wait Ring: 공격 대기·측면 이동
  ○   ○   ○   ○   ○   ○

        Attack Ring: 예약자만 진입
       ●   ●   ●   ●
             Player
```

- `Attack Ring` 슬롯 수는 무기 사거리와 몬스터 Capsule 반지름으로 결정한다. 첫 단계는 근접 몬스터 4~6자리로 시작한다.
- 공격 슬롯을 예약한 몬스터만 해당 위치까지 `MoveTo`하고, 사거리·방향 조건이 맞으면 공격한다.
- 슬롯이 없으면 플레이어 자체가 아니라 `Wait Ring`의 빈 슬롯으로 이동한다.
- 정상적인 공격과 회복이 끝나도 Attack Slot을 유지한다. 슬롯은 한 번의 공격권이 아니라 전열의 교전 위치다.
- 사망·경직·타깃 상실·경로 실패·교착 시에만 슬롯을 즉시 반납한다.
- 신규 예약은 Enemy에서 슬롯까지의 직선이 Player 중심의 `Combat Core`를 통과하지 않는 전방 슬롯을 우선한다.
- 안쪽 Ring으로 진입할 때는 목표 Slot 각도와 맞는 바깥 Ring 지점으로 먼저 이동한다. 각도 정렬 후 방사형으로 진입하여 이미 정지한 Slot 점유자 사이를 직선으로 관통하지 않는다.
- Combat Core는 Player를 NavMesh 동적 장애물로 만들지 않고도 Enemy가 Player Capsule을 가로지르는 직접 경로를 피하게 하는 고수준 전투 규칙이다.
- 플레이어가 조금 이동하면 기존 슬롯 소유권과 인덱스를 유지한 채 목적지만 따라간다.
- 플레이어가 마지막 재편성 기준점에서 500 cm 이상 이동하면 Reform을 실행한다. Attack/Wait 역할은 유지하되 각 Ring 내부에서 현재 위치와 가장 가까운 슬롯으로 일괄 재배치한다.
- 우선순위는 거리만으로 정하지 않는다. 이미 대기한 시간, 특수 공격 준비, 현재 플레이어를 공격 중인 수를 함께 고려한다.

### Holding Ring과 중앙 승격 대기열

Attack 4개와 Wait 8개가 모두 점유됐을 때 추가 Enemy를 정지시키지 않고 기본 500 cm의 `Holding Ring`으로 보낸다.

```text
Attack Ring  4명: 공격 전열
Wait Ring    8명: 다음 공격 후보
Holding Ring 16명: 전투 대형 바깥의 생존 대기자
Pending Queue: Holding까지 가득 찼을 때 순번만 보유
```

- 모든 Enemy는 처음 슬롯을 요청할 때 서버 중앙 순번을 하나 받는다.
- 빈 Attack Slot은 Wait Slot에 실제 도착한 Enemy 중 순번이 가장 빠른 대상에게 준다.
- 빈 Wait Slot은 Holding Slot에 실제 도착한 Enemy 중 순번이 가장 빠른 대상에게 준다.
- 빈 Holding Slot은 아직 어떤 슬롯도 받지 못한 Pending Enemy 중 순번이 가장 빠른 대상에게 준다.
- 승격 도착 판정 기본값은 현재 슬롯 위치에서 60 cm 이내다.
- AI Controller의 0.5초 갱신 순서가 아니라 Slot Component가 0.1초 주기로 승격을 확정한다.
- 사망·경직·타깃 소실·경로 실패로 예약을 반납하면 기존 순번도 제거한다. 다시 참여할 때는 대기열 뒤에서 새 순번을 받는다.
- Holding Enemy는 공격할 수 없으며 Holding 반대편 자리로 갈 때는 Holding Ring 자체를 따라 선회한다.

공격 슬롯의 초기 반지름은 `몬스터 공격 사거리 + 몬스터 Capsule 반지름 + 안전 여유`로 둔다. 슬롯 간 호 길이는 최소 `몬스터 지름 + 안전 여유`를 만족해야 한다.

## AI 상태

```text
Chase → RequestSlot → MoveToAttackSlot → Attack → Recovery
                  └→ MoveToWaitSlot ──────────────────────┘
```

- `Chase`: 전투권 바깥일 때만 플레이어를 향한 NavMesh 경로를 사용한다.
- `RequestSlot`: Target의 Slot Manager에 공격 슬롯을 요청한다.
- `MoveToAttackSlot`: 예약한 공격 슬롯으로 이동한다.
- `MoveToWaitSlot`: 공격 슬롯이 없을 때 외곽 대기 슬롯을 점유하고, 빈 공격 슬롯을 주기적으로 요청한다.
- `MoveToHoldingSlot`: Attack/Wait가 모두 찼을 때 외곽 Holding Slot을 점유한다. 중앙 관리자가 승격하기 전까지 공격하지 않는다.
- `ApproachRing`: 목표 Slot보다 한 단계 바깥 Ring으로 이동한다.
- `AlignOnRing`: 바깥 Ring을 따라 목표 Slot의 각도까지 최대 45도 단위로 선회한다.
- `Ingress`: 각도 정렬을 끝낸 후 안쪽 Slot까지 방사형으로 진입한다. 같은 예약을 유지하는 동안은 다시 바깥 Ring으로 되돌아가지 않는다.
- `Direct`: 이미 정렬되었거나 Ring 진입이 필요 없는 경우 최종 Slot으로 바로 이동한다. Combat Core를 관통하는 직선은 여전히 Ring 우회로 바뀐다.
- `Attack`/`Recovery`: 예약을 유지하고 회복 후 같은 Attack Slot에서 다음 공격을 준비한다. 공격 직전에만 타격 가능 여부를 다시 검사한다.

Detour Crowd Agent는 프로젝트 기본값으로 Obstacle Avoidance, Separation, Anticipate Turns를 사용한다. Separation Weight 2.0, Avoidance Quality High, Collision Query Range 500 cm, Avoidance Range Multiplier 1.2에서 첫 군중 검증을 시작한다. RVO Avoidance는 함께 사용하지 않는다.

## Attack Admission과 진입 통로

- 초기 0.5초는 Enemy 등록을 모으는 단계이며, Enemy를 Wait/Holding에 임시 배치한다.
- 초기 단계 종료 시 전체 후보와 빈 Attack Slot의 Nav 경로 길이를 비교해 가장 진입 비용이 낮은 네 명을 Attack으로 선정한다.
- 런타임에는 현재 Wait Slot에 도착했고 Attack 재진입 쿨다운이 끝난 Enemy만 Attack 후보가 된다.
- 후보 우선순위는 Attack Slot까지의 유효한 Nav 경로 길이이며, 경로 길이가 사실상 같으면 기존 중앙 대기 순번이 빠른 Enemy를 우선한다.
- Wait Ring은 Attack 진입선과 겹치지 않도록 기본 22.5도 회전한다.
- Attack 예약자가 2초 교착 Watchdog에 걸리면 대기열에서 제거하지 않고, 도착한 최적 Wait 후보와 Attack/Wait 예약을 한 틱에 교환한다.
- Wait로 강등된 Enemy는 기본 2초 동안 Attack 재승격 후보에서 제외한다.
- `Holding -> Wait`는 Holding Ring에서 목표 Wait Slot 각도를 맞춘 뒤 안쪽으로 진입한다.
- `Wait -> Attack`은 Wait Ring에서 목표 Attack Slot 각도를 맞춘 뒤 안쪽으로 진입한다.
- 진입점은 모든 Enemy가 공유하는 Gate가 아니라 최종 Slot 각도별로 분산된다.
- 중간 Ring Waypoint는 최종 Slot보다 작은 수용 반경을 사용해 충분히 정렬되기 전에 진입하지 않는다.
- Debug 경로선은 `ApproachRing` 청록, `AlignOnRing` 파랑, `Ingress` 주황, `Direct` 흰색으로 표시한다.

## 시체 누적형 Enemy Pool 후속 방침

시체가 전장에 쌓이는 연출을 유지하기 위해 전체 Pool 수와 동시 활성 Enemy 수를 분리한다.

- `Pool Capacity`: 미리 생성해 둘 전체 Enemy 수
- `Active Enemy Limit`: 동시에 살아서 AI와 전투를 수행할 수 있는 수
- `Corpse Budget`: 전장에 남겨 둘 시체의 상한
- `Free Reserve`: 즉시 활성화할 수 있도록 남겨 둘 비활성 Enemy 수
- 사망한 Enemy는 최소 5초 동안 마지막 자세를 유지한 뒤 회수 후보가 된다.
- 회수는 카메라 밖, 플레이어에게 먼 시체, 오래된 시체 순으로 한 명씩 수행한다.
- 여러 시체의 일괄 회수는 전투 종료, 웨이브 전환, 플레이어가 전투 구역을 떠난 경우에만 사용한다.
- 시체는 AI, Movement, Nav/Crowd 참여, Capsule, 타게팅, 공격 피격 판정, 애니메이션 Tick에서 제외한다.

첫 권장 검증값은 `Pool Capacity 40`, `Active Enemy Limit 12`, `Corpse Budget 24`, `Free Reserve 4`이며 실제 성능 측정 후 조절한다.

## 구현 분담

### Codex: C++

- `AKnight` 등 타깃 캐릭터에 `UCombatEngagementSlotComponent`를 구현한다.
  - 슬롯 생성, NavMesh 투영, 예약/반납, 우선순위, 디버그 드로잉을 담당한다.
- `ACrowdMonsterAIController`를 `ADetourCrowdAIController` 기반으로 구현하거나 `UCrowdFollowingComponent`를 사용한다.
- 몬스터 행동 코드가 플레이어가 아닌 예약 슬롯 위치로 `MoveTo`하도록 연결한다.
- 사망·경직·타깃 전환 시 예약 해제를 보장한다.
- 서버가 슬롯 예약과 이동 목표를 결정한다. 클라이언트는 복제된 이동 결과만 본다.

### 사용자: Unreal Editor

1. 전투 구역을 덮는 `NavMeshBoundsVolume`을 배치하고 `P` 키로 NavMesh를 확인한다.
2. 몬스터 Blueprint의 AI Controller Class에 `BP_CrowdMonsterAIController`를 지정한다.
3. Project Settings → Crowd Manager에서 `Max Agents`를 동시에 활성화할 몬스터 수보다 여유 있게 설정하고, `Max Agent Radius`가 가장 큰 몬스터 Capsule 반지름보다 작지 않은지 확인한다.
4. 몬스터 Character Movement의 `Use RVOAvoidance`는 끈다.
5. Capsule Collision은 최후의 물리 안전장치로 유지하되, 군중 간격의 주 제어 수단으로 쓰지 않는다.
6. PIE에서 Enemy 머리 위 `Route` 텍스트와 경로선을 보며 Ring 진입 단계를 검증한다.

## 단계별 범위

### 1단계: 전투 수직 슬라이스

- 근접 몬스터 8~12마리
- Detour Crowd + Attack Ring 4개 + Wait Ring 8개
- 고정된 플레이어와 이동하는 플레이어 양쪽에서 겹침·교착을 테스트

### 2단계: 전투 읽기성

- 몬스터 타입별 공격 슬롯 우선순위
- 강공격 준비 중인 몬스터의 슬롯 확보
- 통로에서 한 줄 대기, 넓은 공간에서 포위하는 행태

### 3단계: 대규모 배경 군중

수십~수백 마리의 비전투 배경 군중은 Mass Entity/Mass Avoidance를 별도로 검토한다. UE 5.7의 Mass Avoidance는 Experimental이므로 첫 전투 수직 슬라이스의 핵심 적 AI에는 사용하지 않는다.

## 구현 순서

### 0. 현재 완료된 기반

- `ABHEnemy`가 `ABHBaseCharacter`를 상속하고 Detour Crowd AI Controller를 기본으로 사용한다.
- `UBHEnemyAnimInstance`가 공통 이동 데이터(`GroundSpeed`, `Direction`, `bHasAcceleration`)를 받는다.
- AnimBP 확인용 좌측 이동 디버그가 있다. 실제 AI 테스트를 시작할 때 `bWalkLeftForAnimationPreview`를 끈다.

### 1. 단일 적 추적

1. `ABHCrowdEnemyAIController`를 만들고 플레이어 타깃 획득과 이동 명령의 공통 진입점을 구현한다. **C++ 완료**
2. `BP_Enemy_Base`에서 디버그 좌측 이동을 끄고, NavMesh 위에서 한 마리가 플레이어 근처까지 이동하는지 확인한다.
3. 적 AnimBP에서 GroundSpeed와 Direction이 올바르게 바뀌는지 확인한다.

이 단계의 목적은 전투가 아니라 `Enemy → AI Controller → NavMesh/Detour → AnimBP` 연결 검증이다.

### 2. 단일 적 전투 거리

1. 플레이어와의 거리를 검사한다. **C++ 완료**
2. 공격 시작 거리 밖에서는 추적하고, 안에서는 멈춰 바라본다. **C++ 완료**
3. 공격 Montage와 Recovery가 끝날 때까지 재공격하지 않는다. **C++ 완료**
4. 타격 Notify 순간 서버가 거리·높이·전방 각도를 재검사한 뒤 GAS 피해를 적용한다. **C++ 완료**
5. 공격 Montage, Slot, Notify의 에디터 연결과 PIE 검증은 사용자 작업으로 남아 있다.

### 3. 전투 슬롯

1. `UCombatEngagementSlotComponent`가 Player 주변 Attack/Wait Slot을 만든다.
2. 적은 Player Actor가 아닌 예약된 Slot 위치로 이동한다.
3. 슬롯이 없으면 Wait Slot에서 대기하고, 빈 Attack Slot이 생길 때만 진입한다.

### 4. 군중 검증

1. 4마리로 슬롯·반납·사망 복구를 검증한다.
2. 8~12마리로 Detour Crowd 회피, 통로, 플레이어 이동을 검증한다.
3. 디버그 시각화와 전/후 비교 영상을 포트폴리오 증거로 남긴다.

## 검증 시나리오

1. 넓은 평지에서 12마리가 정지한 플레이어에게 접근한다.
2. 플레이어가 원을 그리며 이동한다.
3. 좁은 문·복도에서 선두가 멈추거나 사망한다.
4. 공격 중인 몬스터가 경직·사망할 때 즉시 빈 슬롯이 다른 몬스터에 넘어간다.
5. 공격 슬롯 수보다 많은 몬스터가 동시에 공격 상태가 되지 않는다.
6. Holding과 Wait를 모두 채운 후 승격을 발생시켜, 승격 Enemy가 `ApproachRing -> AlignOnRing -> Ingress`로 이동하는지 확인한다.
7. 각 Enemy의 중간 목표가 하나의 공유 지점에 모이지 않고 목표 Slot 각도별로 분산되는지 확인한다.
